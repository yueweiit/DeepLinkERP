# PLM 数据库架构图（业务视角）

## 1. 任务理解

本文件用于把当前 PLM PostgreSQL 数据库结构用业务语言画清楚，重点回答三件事：

- 这套数据库分成了哪些层
- 核心表之间怎么关联
- 每一层分别支撑什么功能

本图只描述当前 PLM 数据库，不把 ERP、MES、WMS、CRM 的正式业务实现画进来。后续外部系统接入，仅通过映射表、编码快照和日志预留实现。

## 2. 所属 PLM 业务链路

本架构图覆盖：

- 新产品线：Product 主线 + BOM/工艺/文件/质量资料沉淀
- 新型号线：Product 自关联扩展 + 差异版本资料管理
- 样品与试制：Order -> ProductionOrder -> Process -> Workstation
- 模具治具与物料：Inventory 统一承接
- 审批冻结与追溯：Approval + OperationLog + AttachmentDownloadLog
- 后续接 ERP/MES：IntegrationMapping + IntegrationLog + ERP 对照预留字段

## 3. 涉及前端页面

这份数据库架构主要支撑的页面包括：

- Product 列表、详情、版本历史、型号颜色矩阵
- Order、ProductionOrder 执行看板
- BOM 编辑器、BOM 对比、BOM 发布审批
- Process 工艺路线、工序详情、变更追溯
- Inventory 物料/模具治具档案、条码、单位换算、供应商映射
- Attachment 文件中心、对象文件页签、下载日志
- 审批待办、日志追溯、导入结果、集成映射预留

## 5. 涉及数据对象 / 状态 / API

七个核心对象状态机仍然保持统一：

| 对象 | 状态机 |
| --- | --- |
| Customer | `draft -> active -> inactive` |
| Product | `draft -> developing -> reviewing -> released -> archived` |
| Order | `draft -> confirmed -> in_production -> completed -> closed` |
| ProductionOrder | `draft -> scheduled -> in_progress -> completed -> closed` |
| Process | `draft -> confirmed -> locked -> changed -> archived` |
| Inventory | `draft -> available -> reserved -> consumed -> closed` |
| Workstation | `draft -> available -> in_use -> maintenance -> inactive` |

API 资源建议仍围绕七个核心对象展开：

- `/api/v1/customers`
- `/api/v1/products`
- `/api/v1/orders`
- `/api/v1/production-orders`
- `/api/v1/processes`
- `/api/v1/inventories`
- `/api/v1/workstations`

## 6. 不确定点

- `Project`、`Routing`、`Warehouse`、`Account`、`Price List` 当前只做编码/名称快照预留，没有建独立主表。
- `Attachment` 采用多态归属，数据库层无法直接对 7 个核心对象全部加真实外键。
- ERP 参考字段已经补充到 `V1.2`，但正式接库时仍要按对方实际字段再做一次映射确认。

### 7.3 每层负责什么

| 层 | 负责内容 |
| --- | --- |
| 核心主表层 | 承载 7 个一级业务对象，是整个 PLM 的主骨架 |
| 业务扩展层 | 承载成本、质量、报价、变更等非根对象能力 |
| BOM / 物料扩展层 | 承载 Product 版本化 BOM 和 Inventory 的 ERP 友好扩展 |
| 文件与追溯层 | 承载图纸、SOP、测试报告、客户确认资料及下载/操作留痕 |
| 审批与系统配置层 | 承载用户权限、审批流、字典、编码规则、系统参数 |
| 导入与集成预留层 | 承载基础数据导入、后续 ERP/MES 映射与外发日志预留 |

### 7.4 `Inventory` 的职责边界

```text
plm_inventory
  ├─ material         原材料
  ├─ semi_finished    半成品
  ├─ finished         成品
  ├─ packaging        包材
  ├─ tooling          模具
  └─ fixture          治具
```

这张表不是简单库存表，而是 PLM 里的统一物料主数据对象。它同时承担三类职责：

- PLM 内部研发资料引用对象
- 成本核算和 BOM 明细挂接对象
- 后续 ERP Item 映射源对象

### 7.5 `plm_product_bom` 的职责边界

```text
plm_product_bom
  ├─ ebom
  ├─ mbom
  └─ packaging_bom
```

它不是新的一级根对象，而是 `Product` 下的版本化正式资料。它承担：

- 研发 BOM 资料沉淀
- 制造 BOM 资料沉淀
- 包装 BOM 资料沉淀
- 成本计算基础
- 后续 ERP `tabBOM` 映射基础

### 7.6 ERP 预留关系图

```text
PLM 内部对象                         后续 ERP 参考对象
────────────────────────────────────────────────────────────────
plm_inventory                    ->   tabItem
plm_inventory_barcode            ->   tabItem Barcode
plm_inventory_reorder_rule       ->   tabItem Reorder
plm_inventory_uom_conversion     ->   tabUOM Conversion Detail
plm_inventory_default            ->   tabItem Default
plm_inventory_supplier_item      ->   tabItem Supplier
plm_inventory_tax                ->   tabItem Tax

plm_product_bom                  ->   tabBOM
plm_product_bom_item             ->   tabBOM Item
plm_product_bom_operation        ->   tabBOM Operation

```

这里的含义是“后续可映射”，不是“当前已经实现 ERP 同步”。

## 8. 风险点

- 如果后续代码把 `plm_product_bom` 当成独立领域根对象来设计，很容易偏离当前 7 个核心对象边界。
- `Inventory` 承担了 PLM 物料主数据和 ERP 友好字段预留两种职责，代码层需要明确哪些字段是本期业务字段，哪些是映射预留字段。
- `Attachment` 的多态归属在数据库层无法强外键兜底，后端一定要做归属对象存在性校验。
- `project_code`、`routing_code`、`default_warehouse_code`、`expense_account_code` 等只是外部参考字段，不能在本期误演化成新的业务主对象。
