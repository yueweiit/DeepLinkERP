## 3. 任务理解

截图中弹窗为：

```text
确认批量投产颜色
```

现象是：弹窗里已经有 1 条可选记录，且底部显示“已选择 1 个颜色”，但是颜色名称/颜色编码列没有清晰展示；用户只能看到 BOM 版本和成本信息，例如 `...-V1`、`CNY 0`。

该问题属于 Product 下 BOM 路线颜色和投产颜色确认链路，不新增任何根对象。涉及对象：

- Product
- Product 下的 BOM 版本资料
- Product 下的 Process 工艺路线
- Product 下的投产颜色确认记录

## 4. 所属业务链路

本问题发生在新型号线或产品线末期的投产发布阶段：

```text
敲定工序 -> 确认使用 BOM 与适用颜色 -> 确认批量投产颜色 -> 创建/同步 SKU -> 最终节点完成并发布
```

其中“确认批量投产颜色”只应展示已经在“敲定工序”中确认使用的 BOM 路线颜色，不应展示未确认颜色，也不应把 BOM 版本、路线名称、路线编码误当作颜色。

## 7. 当前代码检查结论

### 7.1 投产颜色弹窗的数据来源

`ProductionConfirmationDialog.vue` 中投产颜色来自 `colorOptions`：

```ts
const colorOptions = computed<ColorOption[]>(() => {
  const values = new Map<string, ColorOption>()
  formalRouteRows.value.forEach(({ selection, route }) => {
    const colors = selection.applicableColors?.length
      ? selection.applicableColors.map((color) => ({
        codeItemId: color.codeItemId,
        codeValue: color.colorCode || color.colorName,
        codeName: color.colorName || color.colorCode
      }))
      : (route.colorItems || [])
    // ...
  })
  return [...values.values()]
})
```

这里同时兼容两套颜色结构：

```ts
// BOM route color
{ codeItemId, codeValue, codeName }

// Production route selection color
{ codeItemId, colorCode, colorName }
```

该兼容逻辑能跑通，但局部映射散落在组件内，缺少统一格式化和兜底字段，出现真实接口数据为空、字段缺失、只带名称、只带编码、颜色名与编码混用时，UI 很容易显示不完整。

### 7.2 弹窗 UI 结构存在可维护性风险

当前投产颜色列表模板：

```vue
<el-checkbox-group v-model="selectedColors" class="color-list">
  <div v-for="item in colorOptions" :key="`${item.codeItemId}-${item.codeValue}`" class="color-row">
    <el-checkbox :value="item.codeValue" />
    <strong class="color-label">{{ colorLabel(item) }}</strong>
    <span class="route-label">{{ routeLabel(item.route) }}</span>
    <code v-if="item.route.routeCode">{{ item.route.routeCode }}</code>
    <span v-else class="subtle-text">--</span>
    <span>{{ item.route.costSnapshot?.currencyCode || 'CNY' }} {{ item.route.costSnapshot?.totalCost ?? '--' }}</span>
  </div>
</el-checkbox-group>
```

风险：

- `el-checkbox-group` 下直接放 `div`，再把 `el-checkbox` 和展示列拆成兄弟节点；视觉上可做表格，但选择控件和展示文本没有绑定到同一个 label 区域。
- 点击颜色文字不一定等价于点击 checkbox，影响可用性。
- 如果 CSS 网格列宽、文本颜色或 Element Plus 内部结构变化，容易出现“checkbox 有，文本列空/挤压/看不清”的问题。

### 7.3 后端返回结构没有问题但字段语义分裂

后端 `ProductionConfirmationVO`：

```java
private List<RouteSelectionVO> routeSelections;

public static class RouteSelectionVO {
    private Long processId;
    private Long productBomId;
    private Long productBomRouteId;
    private String routeName;
    private String bomVersionNo;
    private List<Long> operationProcessIds;
    private List<ApplicableColorVO> applicableColors;
}

public static class ApplicableColorVO {
    private Long codeItemId;
    private String colorCode;
    private String colorName;
}
```

BOM workbench 颜色返回：

```java
public class ProductBomRouteColorVO {
    private Long codeItemId;
    private String codeValue;
    private String codeName;
}
```

字段本身都能表达颜色，但前端需要在多个地方手工转换 `colorCode/colorName` 和 `codeValue/codeName`。这就是本次同类问题的核心风险源。

### 7.4 同类情况 1：操作模式与颜色模式共用同一组件，字段转换重复

`ProductionConfirmationDialog.vue` 里有三处颜色相关转换：

```ts
selection.applicableColors.map((color) => ({
  codeValue: color.colorCode || color.colorName,
  codeName: color.colorName || color.colorCode
}))
```

```ts
selection.applicableColors.map((color) => color.colorCode)
```

```ts
const colors = colorOptions.value.filter((value) => selectedColors.value.includes(value.codeValue)).map((value) => ({
  codeItemId: value.codeItemId,
  colorCode: value.codeValue,
  colorName: value.codeName,
  productBomId: value.route.productBomId,
  productBomRouteId: value.route.productBomRouteId!
}))
```

风险：

- 如果 `colorCode` 为空但 `colorName` 有值，默认勾选和提交的 key 可能不一致。
- 如果不同颜色名称重复但编码不同，按名称去重或匹配会误选。
- 如果后端历史数据里 `colorCode/colorName` 混入 BOM 版本号或路线名，前端没有防错提示。

### 7.5 同类情况 2：BOM 复制/继承仍按颜色名称匹配

`ProjectBomPanel.vue` 中复制版本传的是：

```ts
const colors = workbench.value.routes.flatMap((route) => route.colors)
await copyBomVersion(selectedBomId.value, { versionNo: `${workbench.value.versionNo}-COPY`, selectedColors: colors })
```

`BomInheritanceService` 和 `ProcessRouteInheritanceService` 中按 `colorName` 匹配：

```java
.filter(color -> selected.contains(color.getColorName()))
```

```java
.map(ProductBomRouteColor::getColorName)
.anyMatch(selectedColors::contains)
```

风险：

- 颜色名称可能有中西文、大小写、空格、同名不同编码问题。
- 当前系统里颜色字典主键是 `codeItemId`，稳定业务编码是 `colorCode/codeValue`，名称更适合展示，不适合作为传参主键。

### 7.6 同类情况 3：单元测试覆盖了理想数据，没有覆盖截图里的异常形态

当前 `ProductionConfirmationDialog.spec.ts` 覆盖了：

- 已发布 BOM 可进入投产确认。
- 草稿 BOM 不进入投产确认。
- 同一工艺路线可确认多份 BOM。
- 投产颜色只来自已确认路线颜色。

但没有覆盖：

- `applicableColors` 为空时 fallback 到 `route.colorItems` 的 UI 展示。
- `colorCode/colorName` 只有一个字段存在时仍显示。
- 颜色文字必须在弹窗可见，不只展示 checkbox/BOM/成本。
- 点击颜色行文字也能勾选。
- selected key 用 code/name 混用导致的误选。

## 8. 建议修改范围

本次建议只做窄范围修复，不改业务模型，不新增接口：

1. 前端 `ProductionConfirmationDialog.vue` 增加统一颜色归一化方法。
2. 投产颜色列表改成 checkbox 内包裹完整行内容，保证文字、点击区域和选择值绑定。
3. `selectedColors` 改为稳定的颜色 key，避免直接用 `codeValue` 在重复或空值场景误匹配。
4. 保留后端 API 合同，但前端类型增加注释或局部类型，明确两种颜色结构。
5. 补充前端组件测试覆盖异常数据和 UI 可见性。
6. 后续单独治理 BOM 复制/继承的 `selectedColors`，从颜色名称升级为颜色编码或 `codeItemId`。

新增统一颜色 key 与归一化：

```ts
type NormalizedColor = {
  codeItemId: number
  codeValue: string
  codeName: string
  colorKey: string
}

function normalizeColor(input: {
  codeItemId?: number | null
  codeValue?: string | null
  codeName?: string | null
  colorCode?: string | null
  colorName?: string | null
}): NormalizedColor | null {
  const codeItemId = Number(input.codeItemId || 0)
  const codeValue = String(input.codeValue || input.colorCode || '').trim()
  const codeName = String(input.codeName || input.colorName || codeValue).trim()
  if (!codeItemId && !codeValue && !codeName) return null
  return {
    codeItemId,
    codeValue: codeValue || codeName,
    codeName: codeName || codeValue,
    colorKey: `${codeItemId || 'NO_ID'}|${codeValue || codeName}`
  }
}
```

调整 `ColorOption`：

```ts
type ColorOption = NormalizedColor & {
  route: RouteCandidate
}
```

调整 `colorOptions`：

```ts
const colorOptions = computed<ColorOption[]>(() => {
  const values = new Map<string, ColorOption>()
  formalRouteRows.value.forEach(({ selection, route }) => {
    const sourceColors = selection.applicableColors?.length
      ? selection.applicableColors
      : (route.colorItems || [])
    sourceColors.forEach((source) => {
      const color = normalizeColor(source)
      if (!color) return
      const key = `${route.productBomRouteId || route.productBomId}|${color.colorKey}`
      if (!values.has(key)) values.set(key, { ...color, route })
    })
  })
  return [...values.values()]
})
```

## 10. 目标效果

改造完成后应达到：

- “确认批量投产颜色”弹窗第一列明确展示颜色编码和颜色名称，例如 `02 · Negro`。
- 点击颜色文字、路线文字所在行即可勾选/取消勾选，不再只有小 checkbox 可操作。
- 当 `routeSelections[].applicableColors` 为空时，前端能从 `workbench.routes[].colorItems` 兜底展示。
- 当颜色接口只返回编码或只返回名称时，仍可显示可读文本。
- 提交给后端的颜色仍包含 `codeItemId/colorCode/colorName/productBomId/productBomRouteId`，不破坏后端接口。
- 不展示未在“敲定工序”确认过的 BOM 路线颜色。
- BOM 复制/继承后续按颜色编码治理，减少类似错配。

## 11. 前后端可用性要求

前端：

- 弹窗在桌面宽度下保持五列信息：选择、颜色、BOM/路线、路线编码、成本。
- 移动端或窄弹窗下文字不重叠，颜色名优先可见。
- 空数据展示 `请先在敲定工序中确认使用 BOM 与适用颜色`。
- 异常数据展示至少一个可读兜底，不出现只有 checkbox 的空行。

后端：

- `GET /api/v1/projects/{projectId}/production-confirmation` 继续返回 `routeSelections[].applicableColors`。
- `GET /api/v1/boms/{bomId}/workbench` 继续返回 `routes[].colorItems`。
- `POST /api/v1/projects/{projectId}/production-confirmation/colors` 入参不变。
- 后端继续校验颜色属于所选 BOM 路线，不能由前端绕过。
