# 2026-08-07 PLM 产品线工艺路线编码占位与 SKU 替换方案

## 1. 文档目的

本文用于解决产品线 `PRD-HD-0005` 保存工艺路线时出现的 `50001 / 服务器内部错误`，并明确产品线、型号变体和具体 SKU 在手机型号编码、颜色编码以及工序业务编码上的处理边界。

本方案已完成代码实施与验证，**未修改数据库结构、未执行历史数据修数、未执行生产部署**。

## 2. 已确认问题

### 2.1 运行时异常

2026-08-07 当前 Docker 后端日志确认：

```text
org.springframework.dao.DataIntegrityViolationException
ERROR: value too long for type character varying(20)
ProcessRouteServiceImpl.rebuildOperations(ProcessRouteServiceImpl.java:451)
ProcessRouteServiceImpl.create(ProcessRouteServiceImpl.java:120)
```

请求最终被全局异常处理器包装为：

```json
{
  "code": 50001,
  "message": "服务器内部错误"
}
```

### 2.2 触发数据

产品 `PRD-HD-0005` 当前数据：

| 字段 | 当前值 |
| --- | --- |
| `product_type` | `product_line` |
| `product_specific_code` | 空 |
| `phone_model_code` | 空 |
| `color_code` | 空 |
| `color` | `["02 Negro","03 Humo","04 Blanco"]` |
| `color` 字符串长度 | 34 |

数据库字段：

```text

```

后端当前在 `ProcessRouteServiceImpl.resolveCodeGenerationContext()` 中按以下顺序取值：

```text
dto.colorCode
product.colorCode
product.color
```

当产品线没有单一颜色编码时，最后会错误使用多颜色 JSON 字符串作为单个 `colorCode`，导致数据库插入失败。

## 3. 方案结论

### 3.1 不建议使用 `0000000`

不建议把 `0000000` 作为手机型号编码和颜色编码直接保存，原因如下：

1. 当前正式编码规则中，手机型号编码按 4 位解析，颜色编码按 2 位解析，不是一个 7 位字段。
2. `0000000` 会被误认为是真实业务编码，可能生成错误的工序业务编码。
3. 产品线可能有多个颜色，无法用一个颜色占位值表达真实适用范围。
4. 占位编码可能参与唯一索引、成品编码和 BOM/工艺路线关联，后续替换容易形成脏数据。
5. 业务人员无法从数据库值判断该编码是正式值还是临时值。

### 3.2 推荐采用 NULL 表示“待 SKU 确定”

产品线阶段不生成具体 SKU 级编码：

| 字段 | 产品线阶段 |
| --- | --- |
| `product_specific_code` | 有正式产品特定编码时保存，否则为空 |
| `phone_model_code` | `NULL` |
| `color_code` | `NULL` |
| `business_operation_code` | `NULL` |
| `generated_finished_product_code` | `NULL` |
| `code_generation_context` | `product_line_route` |

界面如需展示，应显示“待具体型号/颜色确定”，不要把 `NULL` 显示为 `0000000`。

## 4. 业务阶段规则

### 4.1 产品线阶段

产品线工艺路线只表达通用工序结构，例如：

```text
注塑成型
修边去披锋
组装
```

此阶段允许保存：

- 工序主数据关联；
- 工序顺序；
- 工艺编码；
- 材料/状态；
- 质量要求；
- 工艺参数；
- 路线版本和状态。

此阶段不生成：

- 具体手机型号工序编码；
- 具体颜色工序编码；
- SKU 成品编码；
- 依赖型号和颜色的正式业务操作编码。

产品的 `color` 字段可以继续作为产品展示或适用范围信息，但不得作为工序表的 `color_code`。

### 4.2 型号变体阶段

创建具体手机型号变体后，补充：

```text
phone_model_code = 4 位正式型号编码
color_code = 2 位正式颜色编码
```

如果型号变体仍然包含多个颜色，应继续保持颜色编码为空，直到进入具体颜色或 SKU 阶段。

### 4.3 SKU/具体颜色阶段

进入具体 SKU 或单一颜色阶段后：

1. 读取真实产品特定编码；
2. 读取真实手机型号编码；
3. 读取真实颜色编码；
4. 生成正式工序业务编码；
5. 对成品工序生成正式成品编码；
6. 保留来源工艺路线和版本追溯关系。

正式业务编码生成前必须满足：

```text
productSpecificCode != null
operationCraftCode != null
phoneModelCode != null
colorCode != null
```

## 6. 数据库方案

本方案原则上不新增数据库字段，也不扩大 `color_code` 字段长度。

原因：

- `color_code` 语义上就是单个颜色编码，长度 20 已足够；
- 多颜色属于产品适用范围，不应塞入单值编码字段；
- 现有字段允许保存空值；
- 使用 `NULL` 可以准确表达“尚未进入 SKU/颜色编码阶段”。

后续实施前应执行只读检查：

```sql

       phone_model_code, color_code, color
from plm.plm_product
where product_code = 'PRD-HD-0005';
```

不得直接把多颜色 JSON 写入：

```text

```

## 12. 实施代码要点

以下逻辑已写入业务源码，代码以当前工作区实际实现为准。

### 12.1 后端：只从编码字段读取型号和颜色

已修改文件：

```text
plm-server/src/main/java/com/yuewei/plm/module/process/service/impl/ProcessRouteServiceImpl.java
```

核心逻辑如下：

```java
private CodeGenerationContext resolveCodeGenerationContext(
    Product product,
    ProcessOperationDTO dto,
    String operationCraftCode
) {
    String productType = normalizeCode(product.getProductType());
    String contextName = switch (productType == null ? "" : productType) {
        case "SKU" -> "sku_route";
        case "MODEL_VARIANT" -> "model_variant_route";
        default -> "product_line_route";
    };

    String productSpecificCode = firstText(
        dto.getProductSpecificCode(),
        product.getProductSpecificCode()
    );
    productSpecificCode = normalizeCompactCode(productSpecificCode);

    // 只能读取编码字段，不能回退到 product.color 展示字段。
    String phoneModelCode = firstText(
        dto.getPhoneModelCode(),
        product.getPhoneModelCode()
    );
    String colorCode = firstText(
        dto.getColorCode(),
        product.getColorCode()
    );

    phoneModelCode = normalizeCodeOrNull(phoneModelCode);
    colorCode = normalizeCodeOrNull(colorCode);

    if ("product_line_route".equals(contextName)) {
        // 产品线可以保存通用工艺，但不生成具体 SKU 编码。
        phoneModelCode = null;
        colorCode = null;
    } else {
        validateConcreteCodeContext(phoneModelCode, colorCode);
    }

    return new CodeGenerationContext(
        productSpecificCode,
        normalizeCodeOrNull(operationCraftCode),
        phoneModelCode,
        colorCode,
        contextName
    );
}

private void validateConcreteCodeContext(String phoneModelCode, String colorCode) {
    if (!StringUtils.hasText(phoneModelCode)
        || !phoneModelCode.matches("[A-Z0-9]{4}")) {
        throw new BusinessException(
            ErrorCodeConstants.VALIDATION_ERROR,
            "具体型号或 SKU 必须提供 4 位手机型号编码"
        );
    }
    if (!StringUtils.hasText(colorCode)
        || !colorCode.matches("[A-Z0-9]{2}")) {
        throw new BusinessException(
            ErrorCodeConstants.VALIDATION_ERROR,
            "具体颜色或 SKU 必须提供 2 位颜色编码"
        );
    }
}
```

现有 `resolveBusinessOperationCode()` 的 `context.ready()` 判断应继续保留。这样：

- 产品线：`phoneModelCode` 和 `colorCode` 为空，业务操作编码返回 `null`；
- 型号变体/SKU：编码完整时才生成正式业务操作编码；
- 多颜色 JSON 永远不会进入 `plm_process.color_code`。

function refreshBusinessOperationCode(operation: ProcessOperationSavePayload) {
  operation.operationCraftCode = findOperationCraftCode(operation)
  operation.productSpecificCode = normalizeBusinessCode(
    operation.productSpecificCode || props.productSpecificCode || deriveProductSpecificCode(),
    ''
  )

  if (isProductLineRoute.value) {
    operation.phoneModelCode = ''
    operation.colorCode = ''
    operation.businessOperationCode = ''
    operation.generatedFinishedProductCode = ''
    operation.codeGenerationContext = 'product_line_route'
    operation.businessOperationCodeManualFlag = false
    return
  }

  operation.phoneModelCode = normalizeBusinessCode(
    operation.phoneModelCode || props.phoneModelCode,
    ''
  )
  operation.colorCode = normalizeBusinessCode(
    operation.colorCode || props.colorCode,
    ''
  )

  operation.businessOperationCode = previewBusinessOperationCode(operation)
  operation.generatedFinishedProductCode =
    operation.operationCraftCode === '4030'
      ? operation.businessOperationCode
      : ''
  operation.codeGenerationContext =
    props.productType === 'sku'
      ? 'sku_route'
      : props.productType === 'model_variant'
        ? 'model_variant_route'
        : 'product_line_route'
  operation.businessOperationCodeManualFlag = false
}

| `plm.plm_process.color_code` 数据库字段 | 单个颜色编码长度 20 已足够，不应通过扩大字段容纳多颜色 JSON |
| API 路径 | 现有接口已能表达可选编码，不需要新增接口 |
| `Product.color` 字段 | 该字段继续承担展示/适用范围语义，不改作编码字段 |
| `0000000` 占位数据 | 不写入数据库，避免形成不可追溯的伪编码 |

## 14. 完整业务逻辑

### 14.1 产品线新建工艺路线

```text
产品详情
  -> productType = product_line
  -> 打开工艺路线编辑
  -> 选择工序主数据
  -> 生成通用工序结构
  -> phoneModelCode = NULL
  -> colorCode = NULL
  -> businessOperationCode = NULL
  -> generatedFinishedProductCode = NULL
  -> POST /api/v1/projects/{productId}/process-routes
  -> 后端插入路线和工序
  -> 保存成功
```

### 14.2 型号变体新建工艺路线

```text
新型号需求
  -> productType = model_variant
  -> 传入真实 phoneModelCode
  -> 如果仍是多颜色，colorCode 保持 NULL
  -> 不生成带颜色的正式业务操作编码
  -> 创建或继承型号级工艺路线
```

### 14.3 SKU/具体颜色生成编码

```text
具体 SKU
  -> productType = sku
  -> phoneModelCode = 4 位正式编码
  -> colorCode = 2 位正式编码
  -> 后端校验编码格式和长度
  -> 生成 businessOperationCode
  -> 成品工序生成 generatedFinishedProductCode
  -> 保存 SKU 级路线或新版本
```

### 14.4 异常处理逻辑

```text
产品线 + 多颜色展示值
  -> 不读取 product.color
  -> 颜色编码为空
  -> 允许保存通用工艺

SKU + 缺少型号/颜色编码
  -> 后端返回 40001 业务校验错误
  -> 前端显示具体缺失字段
  -> 不执行数据库 INSERT

任意编码超过字段上限
  -> 后端格式校验拦截
  -> 不再由 PostgreSQL 抛出 50001
```
