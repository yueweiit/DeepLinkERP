# PLM BOM 冻结方式灵活调整方案

日期：2026-08-05  
状态：方案沉淀，未实施  
范围：BOM 冻结流程调整；先沉淀规则，不改代码。

## 1. 背景

当前 BOM 管理里，冻结后的 BOM 不能再调整绑定的工艺路线。

这会带来一个实际问题：

```text
本来应该绑定这条线的 BOM
但在冻结时绑错了
冻结后就改不了了
```

在现有流程里，冻结更像“半发布锁定”，但用户真实业务希望它更灵活一些：只要还没有正式发布，就允许在受控范围内回退、调整、再冻结。

## 2. 目标

把 BOM 冻结从“不可回退的一刀切锁定”调整为“可撤回的受控锁定”。

目标效果：

1. 冻结前可继续调整工艺路线、颜色和 BOM 绑定；
2. 冻结后，如果还未发布，允许撤销冻结后再修正；
3. 只有真正发布后的 BOM 才进入不可修改状态；
4. 修正过程必须留痕，可追溯。

## 3. 现状问题

现有问题主要是：

1. BOM 一旦冻结，界面和接口都不再允许改路线；
2. 如果冻结时绑定错路线，只能重新做版本；
3. 对于“还没发布、只是冻错了”的情况，当前操作成本太高；
4. 业务上会出现“明明是同一条线，只是绑错了”的低风险错误，却被迫走完整版本重建。

## 4. 方案原则

冻结不是最终态，发布才是最终态。

建议把状态理解为：

```text
draft -> reviewing -> frozen -> released
```

其中：

- `frozen` 表示资料已经锁定，原则上不再随意编辑；
- 但 `frozen` 不是终局，只要还没 `released`，允许受控撤销；
- `released` 才是最终正式资料，不允许直接改。

补充边界：

```text
frozen 可回退
released 不回退
```

## 5. 灵活冻结的规则

### 5.1 冻结前

在冻结前，允许继续做以下调整：

1. 工艺路线绑定；
2. BOM route 绑定；
3. 颜色适用关系；
4. BOM 明细；
5. 成本重算；
6. 版本说明修正。

### 5.2 冻结后未发布

如果 BOM 已经冻结，但尚未发布，允许：

1. 撤销冻结；
2. 回到可编辑状态；
3. 修正绑定路线；
4. 重新冻结；
5. 再进入发布流程。

建议把这一步定义成明确动作：

```text
撤销冻结 / 解除锁定 / reopen
```

而不是直接改数据库字段。

### 5.3 已发布后

一旦 BOM 已发布：

1. 不允许直接修改；
2. 不允许撤销冻结后覆盖原版本；
3. 只能复制新版本再修正；
4. 历史版本保留追溯。

## 6. 建议的操作口径

### 6.1 错绑路线但未发布

推荐流程：

```text
冻结状态 -> 撤销冻结 -> 修正路线绑定 -> 重新冻结 -> 重新发布
```

适用场景：

- BOM 绑错了工艺路线；
- 颜色选错了；
- 还没进入正式发布；
- 只是流程中途冻结，不是最终出货版本。

### 6.2 已发布后发现路线绑错

如果 BOM 已经是 `released`，就不能再撤销冻结后直接改原版本。

推荐流程：

```text
保留旧发布版本
复制新版本
修正新版本的路线绑定
重新提交审核
重新冻结
重新发布
```

处理原则：

1. 旧发布版本不回改；
2. 旧发布版本保留追溯；
3. 新版本作为纠正版本；
4. 修正原因写入版本备注或操作日志；
5. 如果历史版本已经被下游引用，更不能物理修改。

适用场景：

- 发布后才发现路线绑错；
- 发布后才发现颜色适用关系有误；
- 发布后才发现 BOM route 选错；
- 发布后才发现需要重新走正式版本流程。

### 6.3 已发布版本发现其他问题

推荐流程：

```text
复制版本 -> 修正新版本 -> 重新冻结 -> 重新发布
```

不要回改旧发布版本。

## 7. 权限和门禁建议

为了避免冻结过于随意，建议保留门禁：

1. 冻结按钮继续保留；
2. 撤销冻结按钮只给工程、项目经理、管理员；
3. 已发布版本不显示撤销冻结；
4. 冻结和撤销冻结都要写操作日志；
5. 撤销冻结要填写原因，例如“路线绑错”。

## 8. 数据留痕建议

每次冻结/撤销冻结都记录：

```text
对象ID
版本号
原状态
新状态
操作者
操作时间
原因
requestId
```

建议至少保留：

1. 冻结时间；
2. 冻结人；
3. 撤销冻结时间；
4. 撤销冻结人；
5. 撤销原因；
6. 最终发布人。

## 9. 对现有业务的影响

### 9.1 好处

1. 冻结错路线可以修正；
2. 不必为了小错误重做整版 BOM；
3. 更贴近真实业务节奏；
4. 对钉钉新型号继承更友好；
5. 能降低“冻错后只能重来”的操作成本。

### 9.2 风险

1. 如果撤销冻结过于自由，容易破坏版本纪律；
2. 已发布资料如果也允许回改，会破坏追溯；
3. 多人并发修正时，可能出现路线被重复切换。

所以核心边界必须明确：

```text
冻结可回退，发布不可回退
```

## 10. 推荐落地顺序

1. 先支持未发布 BOM 的撤销冻结；
2. 冻结后允许重新绑定路线；
3. 冻结/撤销冻结写操作日志；
4. 发布后彻底锁死；
5. 后续再考虑页面上的“解冻”按钮和提示文案。

## 11. 结论

本次要调整的不是 BOM 的主业务模型，而是冻结的可逆性。

最终口径建议定为：

```text
冻结阶段允许受控回退
发布阶段才是真正锁定
```

这样既能保留正式版本的严肃性，也能解决“BOM 绑错线但已经冻结”的实际操作痛点。
