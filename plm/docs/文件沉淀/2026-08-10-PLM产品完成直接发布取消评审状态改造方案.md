# PLM 产品完成直接发布取消评审状态改造方案

## 1. 文档目的

本文件用于沉淀“项目完成后直接进入发布状态，不再经过评审中 reviewing 状态”的前后端改造方案。

本次只记录排查结论、影响范围、目标逻辑、拟修改文件和代码草稿，当前不修改业务代码。

## 2. 已读取资料与代码范围

已按要求读取：

- `D:\work\资料\PLM\docs\文件沉淀\开发提示词.md`
- 当前仓库沉淀目录：`docs/文件沉淀`
- 当前代码中与 `reviewing`、`评审中`、`submit-review`、发布门禁、时间轴完成动作相关的前后端与数据库文件

需要特别说明：开发提示词中的原标准状态机仍写着 `Product: draft -> developing -> reviewing -> released -> archived`。本需求属于状态机业务规则变更，后续落地时必须同步更新标准文档、字典、数据库约束、前端状态枚举和后端门禁，不能只改某一个按钮或接口。

## 3. 任务理解

用户口径是：完成之后直接到发布状态，不经过评审。

结合现有代码，仓库中没有独立的“代码评审”业务模块；当前真正影响用户流程的是产品和 BOM 生命周期里的 `reviewing / 评审中` 状态。它现在承担了“最后节点已完成、等待发布/冻结”的中间态。

目标不是绕过发布门禁，而是把门禁绑定到“时间轴最后节点已确认、资料风险已确认、BOM/工艺/附件满足规则”这些真实条件上。也就是说，去掉 `reviewing` 后，系统仍然要保证发布、冻结、归档、版本、日志和权限可控。

## 4. 所属 PLM 业务链路

本需求影响两条主线：

- 新产品线：客户/市场需求 -> 新产品线立项 -> Product 建档 -> 工艺与样品验证 -> BOM 资料确认 -> 文件与质量资料冻结 -> Product 发布 -> 历史追溯。
- 新型号线：已有 Product -> 新型号/颜色需求 -> Product 版本扩展 -> 样品或工艺差异确认 -> BOM 资料差异确认 -> 文件冻结 -> Product 子版本发布。

核心对象仍然只使用 `Product`。BOM 继续作为 Product 下的版本资料和明细数据，不新增 BOM 根对象。

## 6. 目标效果

改造完成后的目标状态机：

```text
Product: draft -> developing -> released -> archived
```

目标行为：

- 时间轴推进到最后节点并确认后，Product 直接进入 `released`。
- 前端不再出现“评审中”筛选项、状态标签、提交评审按钮、只有评审中才可发布的提示。
- 发布门禁不再检查 `PRODUCT_STATUS_NOT_REVIEWING`，改为检查最后节点、确认状态、归档/废弃状态和资料风险。
- 已发布产品保持只读，后续修改走版本/变更流程，不允许通过取消评审绕过发布控制。
- 操作日志仍记录最后节点确认、自动发布、手动补发布、风险确认等动作。
- 历史库中已有 `reviewing` 数据通过迁移处理，不在新流程中继续生成。

## 7. 建议范围决策

建议本次按“产品状态 + BOM 可见评审入口”一起改，原因是用户明确提到“不经过评审这些”。如果只去掉 Product.reviewing，BOM 页面仍显示“提交评审/评审中”，前后端体验会割裂。

需要业务确认的点：

- 新型号线当前最后节点会归档。建议改成 `released`，否则“完成即发布”只对产品线生效。
- BOM 是否引入 `confirmed` 中间态。建议正式 BOM 使用 `draft -> released -> archived`，测试 BOM 可继续使用已有 `confirmed` 表示试算确认。
- 附件、质量、成本表里也存在 `reviewing` 约束。建议本轮先不强行删除这些非 Product 生命周期状态，除非页面也显示“评审中”。可以在后续资料冻结模块统一治理。

建议保留，用于历史数据、手动补发布或发布风险确认。产品已发布时应保持幂等，不应报“状态流转非法”。

### 11.3 BOM 动作


旧接口：

```text

```

短期保留兼容，标记 deprecated，前端不再调用。

## 13. 风险点

- 历史 `reviewing` 数据必须迁移，否则数据库约束收紧后会失败。
- 前端如果只改状态标签，不改发布门禁条件，会导致完成后看不到发布入口或按钮误禁用。
- 后端如果只允许 `developing -> released`，但时间轴最后节点仍先写 `reviewing`，会继续产生旧状态。
- BOM 如果继续保留 `reviewing`，用户仍会在 BOM 操作中看到“评审中/提交评审”，需求体验不完整。
- 新型号线原先完成即归档的逻辑与本需求冲突，需要业务确认后统一。
- 字典、数据库初始化脚本、Flyway 迁移、测试数据、Mock 数据要一起改，避免新环境仍种出 `reviewing`。

## 14. 推荐实施顺序

1. 先确认范围：Product 必改；BOM 是否同步取消评审；新型号线是否由完成即归档改为完成即发布。
2. 修改后端状态机、时间轴最终节点、发布门禁和发布接口幂等。
3. 修改数据库迁移和字典，处理历史 `reviewing` 数据。
4. 修改前端类型、状态标签、权限、筛选、门禁面板和 BOM 操作入口。
5. 更新测试用例和 Mock 数据。
6. 跑后端测试、前端类型检查和构建。
7. 灰度验证：找一个产品线项目和一个新型号项目，确认最终节点完成后都能直接进入 `released`。

## 15. 最终交付目标

落地后应达到：

- 产品完成后直接发布，不再生成或展示 `reviewing / 评审中`。
- 前端项目中心、产品详情、发布门禁、BOM 操作都能正常使用。
- 后端状态机、发布门禁、数据库约束一致。
- 历史数据有明确迁移路径。
- 发布、冻结、归档、版本只读、操作日志和权限仍然受控，代码保持清晰、集中、可测试。
