# PLM 钉钉连接器问题解决方案与配置方案

日期：2026-08-04  
范围：方案文档与问题沉淀，本次不修改业务代码、不修改数据库

## 1. 背景

本次排查涉及三类现象：

1. 钉钉连接器调试结果显示 HTTP 200，但工作台没有新建项目。
2. 之前测试 PLM 完成流程后自动代同意失败。
3. 钉钉审批成功创建新型号项目后，新项目没有继承来源产品的工艺路线。

需要注意：HTTP 200 只代表 HTTP 请求到达并被接口处理，不代表钉钉业务动作成功。必须同时判断响应体中的 `code`、`data.status`、`data.projectId` 和 `data.idempotentHit`。

## 2. 已确认的测试结果

### 2.1 重复审批实例不会创建新项目

以下返回表示命中了历史集成记录，而不是创建了新项目：

```json
{
  "dingTalkApprovalNo": "1111",
  "projectId": 43,
  "status": "success",
  "idempotentHit": true
}
```

`idempotentHit=true` 时，服务会按照 `externalInstanceId` 找到原来的集成记录并直接返回历史项目。连接器每次测试必须使用真实且唯一的钉钉审批实例 ID，不能固定传 `1111`、`112` 等测试值，也不能重复回放同一个审批实例期待创建新项目。

### 2.2 使用新审批实例后可以创建项目

以下返回表示本次确实创建了新项目：

```json
{
  "dingTalkApprovalNo": "112",
  "integrationRecordId": 29,
  "projectId": 19206,
  "status": "success",
  "idempotentHit": false
}
```

其中：

- `projectId=19206`：新型号项目已经创建。
- `integrationRecordId=29`：入站集成记录已写入。
- `idempotentHit=false`：不是历史记录重复命中。
- `moldMatches` 已显示已有模具资料匹配成功。

因此，当前“没有工艺路线”不是钉钉入站创建失败，而是创建链路缺少工艺路线和 BOM 继承步骤。

## 3. 根因分析

### 3.1 工作台手工新建和钉钉新建走了不同逻辑

工作台手工新建新型号的主要流程是：

```text
ProductServiceImpl.create
  -> 创建 Product
  -> 创建新型号颜色快照
  -> ProcessRouteInheritanceService
  -> BomInheritanceService
```

钉钉审批入站创建新型号的主要流程是：

```text
DingTalkModelVariantService.receive
  -> 幂等检查
  -> 校验审批、来源产品和已确认生产颜色
  -> 创建 Product
  -> 模具编码匹配
  -> 附件元数据归档
  -> 创建 RequirementForm
  -> 创建新型号颜色快照
  -> 创建 IntegrationRecord
```

当前钉钉链路没有调用：

```text
ProcessRouteInheritanceService
BomInheritanceService
```

所以会出现以下结果：

- 新型号项目存在；
- 钉钉审批记录存在；
- 模具匹配结果存在；
- 新型号颜色快照存在；
- 新型号项目下没有来源产品的工艺路线；
- 新型号项目下没有对应的正式 BOM；
- 工作台项目详情无法展示继承后的工艺路线。

### 3.2 继承条件

即使补上继承调用，来源产品仍需满足以下条件：

1. 来源产品存在。
2. 来源产品类型为 `product_line`。
3. 来源产品状态为 `released`。
4. 来源产品存在已确认的生产颜色。
5. 来源产品存在最新已发布的正式 BOM。
6. 正式 BOM 关联有效工艺路线。
7. 工艺路线的适用颜色能够匹配新型号继承的颜色。

任一条件不满足，都应该返回明确的业务错误，不能只返回“创建成功”。

## 4. 目标方案

### 4.1 统一新型号继承编排

建议抽取一个内部公共服务，例如：

```text
ModelVariantInheritanceOrchestrator
```

该服务统一负责：

1. 根据来源产品和已确认颜色生成继承颜色清单。
2. 继承来源产品最新已发布正式 BOM 对应的工艺路线。
3. 建立来源工艺路线与新型号工艺路线的 ID 映射。
4. 按颜色继承正式 BOM。
5. 将新型号 BOM 路线中的 `process_id` 指向新型号自己的工艺路线。
6. 返回继承的路线数量、BOM 数量和颜色数量。

两个入口都调用该公共服务：

```text
ProductServiceImpl.create
DingTalkModelVariantService.receive
```

这样可以避免手工新建和钉钉新建长期出现规则不一致。

### 4.2 钉钉入站调用时机

钉钉新型号项目创建完成颜色快照后，调用继承编排服务，再写入成功的入站集成记录：

```text
创建项目
  -> 模具匹配
  -> 附件归档
  -> 创建需求表
  -> 创建颜色快照
  -> 继承工艺路线
  -> 继承正式 BOM
  -> 写入 success 集成记录
```

建议采用强一致方案：

```text
工艺路线或 BOM 继承失败
  -> 整个钉钉入站事务回滚
  -> 不写入 success 集成记录
  -> 返回明确失败原因
```

这样可以避免出现“钉钉返回成功，但项目缺少核心工艺资料”的半成品项目。

## 5. 已创建项目的补偿方案

项目 `projectId=19206` 已经创建成功，但可能缺少工艺路线和正式 BOM。不能简单重复发送同一个钉钉审批实例，因为会触发幂等命中，不会重新执行创建逻辑。

建议增加一次性后台补偿服务或管理接口，例如：

```text
POST /api/v1/projects/{projectId}/inherit-parent-process-bom
```

补偿流程：

1. 查询目标项目。
2. 校验目标项目是 `model_variant`。
3. 查询 `parent_product_id`。
4. 查询来源产品已确认的生产颜色。
5. 查询目标项目已有工艺路线和正式 BOM。
6. 已存在的内容默认不重复复制。
7. 缺少的内容执行继承。
8. 写入操作日志和补偿结果。

补偿接口必须幂等，重复调用不能产生重复路线、重复 BOM 或错误的 `process_id` 关联。

## 6. 当前配置方案

代码通过 Spring 环境变量占位符读取钉钉配置，配置前缀为：

```text
plm.integrations.dingtalk
```

生产或测试部署时，建议配置为环境变量，而不是直接把密钥提交到 Git：

```text
DINGTALK_INTEGRATION_ENABLED=true
DINGTALK_MODEL_VARIANT_PROCESS_CODE=<钉钉真实新型号审批模板 processCode>
DINGTALK_APP_KEY=<钉钉企业内部应用 AppKey>
DINGTALK_APP_SECRET=<钉钉企业内部应用 AppSecret>
DINGTALK_AUTO_APPROVER_USER_ID=<当前等待节点的真实审批人 userId>
DINGTALK_OUTBOUND_ENDPOINT=<可从 PLM 服务访问的出站中转地址>
```

### 6.1 配置位置

根据部署方式选择对应位置：

- Docker Compose：服务的 `environment` 或同目录 `.env` 文件。
- Kubernetes：Deployment 的 `env`、Secret 或 Helm values。
- Windows 服务或脚本启动：启动进程的系统环境变量。
- 本地 Spring Boot：运行配置中的 Environment variables，或本地未提交的 `.env`/启动脚本。
- `application.yml`：仅作为默认映射位置，不建议把 AppSecret 明文写入仓库。

当前 `application.yml` 已定义上述环境变量映射。环境变量名称必须保持一致，不能把入站回调地址和出站中转地址混用。

### 6.2 地址和参数注意事项

1. `DINGTALK_MODEL_VARIANT_PROCESS_CODE` 必须与钉钉当前实际使用的新型号审批模板完全一致。
2. 每次真实回调必须携带真实且唯一的审批实例 ID。
3. `DINGTALK_AUTO_APPROVER_USER_ID` 必须是当前等待节点的审批人，而不是任意企业用户。
4. `DINGTALK_OUTBOUND_ENDPOINT` 必须从 PLM 服务所在网络访问，不是从开发者电脑访问。
5. 地址末尾不能带中文分号 `；`，只能使用合法 URL。
6. 配置修改后必须重启服务，确认启动日志中加载了新配置。
7. 出站地址为空时，当前代码可能进入 `dry_run`，不能把 `dry_run` 当成真实代同意成功。

用户此前在对话中暴露过 AppSecret。该密钥不应继续使用，建议在钉钉管理后台重置后，再将新密钥写入部署 Secret，并清理聊天记录、日志和脚本中的旧密钥。

## 7. 代同意问题的解决方向

### 7.1 调试判断标准

代同意不能只判断 HTTP 200，至少要记录并判断：

```text
HTTP status
response.code 或 errcode
data.status
externalStatus
errorCode
message
processInstanceId
taskId
actionerUserId
requestId
```

### 7.2 需要重点核验的实现

1. PLM 出站中转接口当前可能使用 HTTP 200 包装业务失败，连接器必须读取 `data.status=failed`。
2. 未配置出站地址时可能返回 `dry_run`，应明确标记为“未真实调用钉钉”。
3. 钉钉审批任务同意接口的请求路径和字段必须与当前实际 API 版本一致，重点核对 `actioner_userid`、`task_id` 和 `process_instance_id`。
4. 查询运行中任务时，不应在找不到指定审批人任务后盲目回退到第一条任务。
5. 查询 taskId 的异常不能直接吞掉，应保留钉钉返回码和原始错误信息。

## 8. 验收标准

### 8.1 新型号入站

使用一条新的真实钉钉审批实例测试，必须满足：

```text
HTTP 200
顶层 code = 0
data.status = success
data.idempotentHit = false
data.projectId 有值
```

数据库应能查到：

```text
目标项目 Product
目标项目颜色快照
目标项目 routing 工艺路线
目标项目 formal BOM
目标 BOM route
目标 BOM route.process_id 指向目标项目工艺路线
inbound IntegrationRecord
```

### 8.2 重复回调

重复发送同一个审批实例，必须满足：

```text
data.status = success
data.idempotentHit = true
data.projectId = 第一次创建的项目 ID
```

并且不能新增第二个项目。

### 8.3 代同意

至少验证三种结果：

1. 正确审批人、正确 taskId：真实返回成功。
2. 审批人无权限：返回明确业务失败，不能只显示 HTTP 200 成功。
3. 未配置出站地址：明确显示 `dry_run` 或配置错误，不能记为真实成功。

## 9. 推荐实施顺序

1. 先在部署环境核对 processCode、审批实例 ID、出站地址和审批人 userId。
2. 对 `projectId=19206` 执行一次性数据检查，确认缺少的是工艺路线、BOM，还是来源产品本身没有可继承数据。
3. 增加公共继承编排服务，并让工作台和钉钉两个入口共用。
4. 增加钉钉入站继承测试、幂等测试和失败回滚测试。
5. 增加已创建项目补偿能力。
6. 修正代同意接口的真实 API 契约和错误透传。
7. 使用新的真实审批实例做端到端验收。

## 10. 当前结论

当前已确认：

- `projectId=19206` 的钉钉入站创建是成功的。
- `idempotentHit=false` 说明这次确实创建了新项目。
- 模具资料匹配成功不是工艺路线继承成功的证明。
- 新型号没有工艺路线的直接原因是钉钉入站创建链路漏调工艺路线和 BOM 继承服务。
- 重复使用固定审批实例会触发幂等返回，不会创建新项目。
- 代同意的 HTTP 200 不能证明钉钉审批动作成功。

本方案先作为实施依据，后续代码修改、历史项目补偿和现场配置核验应按本文档的验收标准执行。
