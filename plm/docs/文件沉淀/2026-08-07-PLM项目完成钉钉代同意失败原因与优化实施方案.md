## 1. 任务理解

本次任务围绕“项目完成后钉钉没有代同意成功”的原因排查和优化沉淀。按照现有代码理解，PLM 在项目时间轴最后节点确认完成后，会触发钉钉回传：

- 新型号线：`MODEL_VARIANT_MOLD_TRANSFER` 完成后，尝试自动同意钉钉等待节点。
- 新产品线：`PRODUCT_LINE_PRODUCTION_DECISION_STEP` 完成后，当前设计是完成通知/抄送，不是代同意。

已验证的失败主因是钉钉官方接口 IP 白名单限制。早期出站请求返回钉钉错误 `60020`，当前后端出口 IP 已确认为 `113.102.239.122`。在白名单处理后，使用同一个审批实例手工执行：

- `workflow-task-lookup` 成功取得 `taskId=102880206736`。
- `agree` 成功返回 `status=success`。
- 后续再次查找运行中任务返回 `DINGTALK_RUNNING_TASK_NOT_FOUND`，符合等待节点已处理后的表现。

因此，业务主流程本身能够触发代同意；真正需要优化的是失败可观测性、重试入口、任务状态展示、错误持久化和接口边界。

## 2. 所属 PLM 业务链路

本方案归属“新型号线”和“新产品线”的项目时间轴完成回传链路。

- 核心对象：`Product`
- 新型号线链路：已有产品线下创建型号/颜色需求，完成样品或工艺差异、BOM 差异、文件冻结，最终在 `MODEL_VARIANT_MOLD_TRANSFER` 节点归档，并回传钉钉审批等待节点。
- 新产品线链路：产品线立项到生产决策完成后，PLM 内部发布/完成，并预留钉钉完成通知能力。
- 不新增 `IntegrationJob` 等根对象。集成流水继续复用现有 `plm_integration_record`，作为 `Product` 相关的外部系统交互记录。

## 3. 涉及前端页面

建议涉及以下页面或组件：

- 项目中心 / 项目详情：展示项目时间轴完成状态。
- 项目时间轴最后节点确认弹窗：确认完成后提示“PLM 项目已完成，钉钉回传处理中/成功/失败”。
- 项目详情钉钉回传状态区域：展示最近一次出站记录、错误信息、重试按钮。
- 集成记录诊断页面或调试入口：供管理员查看钉钉入站/出站记录，不作为新的核心业务对象页面。

建议不要让“钉钉代同意失败”阻断 PLM 项目完成。PLM 的项目完成是内部事实，钉钉代同意是外部回传结果，两者需要分离展示。

## 4. 涉及后端模块

现有相关模块：

- `TimelineActionServiceImpl`：项目时间轴节点确认，最后节点完成后注册 afterCommit 回调触发钉钉回传。
- `DingTalkProjectCompletionReturnService`：根据项目类型和完成节点组装回传 payload，保存出站集成记录。
- `DingTalkOutboundRelayService`：统一处理 `workflow-task-lookup`、`agree`、`cc` 等出站动作。
- `DingTalkOfficialApprovalClient`：调用钉钉官方审批实例和任务执行接口。
- `IntegrationRecordRepository` / `IntegrationRecord`：保存钉钉入站、出站和错误信息。
- `OperationLogService`：保存项目维度操作日志。

建议新增或扩展：

- 钉钉完成回传查询接口：返回某个 `Product` 的最新回传状态。
- 钉钉完成回传重试接口：允许管理员或项目负责人在修复 IP 白名单、taskId、权限配置后重试。
- 回传状态 VO / 重试 DTO：封装前端展示和重试请求。

## 5. 涉及数据对象 / 状态 / API

### 数据对象

- `Product`：项目本体，仍是唯一核心对象。
- `plm_integration_record`：钉钉入站/出站记录，作为集成流水，不提升为业务根对象。
- `operation_log`：记录自动回传、重试、失败原因等操作日志。

### 建议状态

沿用 `plm_integration_record.processing_status`：

- `success`：钉钉代同意或通知实际成功。
- `failed`：钉钉接口失败、配置缺失、taskId 查询失败、权限失败。
- `dry_run`：仅联调演练，不应被当作真实成功。
- `pending` / `sending`：如后续引入异步 outbox，可作为过程态。

### 现有触发 API

项目完成触发仍由时间轴确认接口间接触发：

```http
POST /api/v1/projects/{projectId}/timeline/{nodeKey}/confirm
```

当 `nodeKey=MODEL_VARIANT_MOLD_TRANSFER` 且 `Product.productType=model_variant` 时，后端在事务提交后调用钉钉代同意。

### 建议新增 API

```http
GET /api/v1/projects/{projectId}/dingtalk-completion-return
```

用于查询项目最近一次钉钉完成回传状态。

```http
POST /api/v1/projects/{projectId}/dingtalk-completion-return/retry
```

用于在失败后手工重试钉钉回传。

## 6. 不确定点

- 钉钉“自动代同意”的执行人是否固定为配置项 `autoApproverUserId`，还是需要从入站审批任务节点动态解析。
- 钉钉任务查询 fallback 是否允许取第一个运行中任务。当前逻辑有兜底能力，但严格业务上更建议按 `actionerUserId` 精确匹配，避免误同意其他等待节点。
- 新产品线完成后是否只需要抄送，还是未来也要触发钉钉审批动作。目前代码里的 `cc` 尚未接入官方消息 API。
- 前端重试按钮的权限范围：建议仅管理员、项目负责人、流程负责人可见。

## 7. 实施方案

### 7.1 现状触发流程

当前系统触发项目完成代同意的流程如下：

1. 用户在项目详情时间轴点击最后节点确认。
2. `TimelineActionServiceImpl.confirm` 校验当前节点、业务门禁、资料提醒。
3. 新型号线在 `MODEL_VARIANT_MOLD_TRANSFER` 完成时执行归档逻辑。
4. `productRepository.updateById(product)` 保存项目状态。
5. 事务提交后执行 `triggerDingTalkCompletionReturn`。
6. `DingTalkProjectCompletionReturnService.handleProjectCompleted` 根据产品类型路由：
   - 新型号线：查询钉钉入站记录，组装 `agree` payload。
   - 新产品线：组装 `cc` payload。
7. 如果入站记录没有 `taskId`，调用 `workflow-task-lookup` 查询运行中任务。
8. 调用 `agree` 代同意钉钉等待节点。
9. 保存 `plm_integration_record` 出站记录，并写入操作日志。

### 7.2 优化目标

1. 项目完成状态和钉钉回传状态分离，外部失败不回滚 PLM 内部完成。
2. 页面可看到“钉钉回传成功/失败/待重试”的明确结果。
3. 失败时保存钉钉官方错误码和错误信息，例如 `60020 IP whitelist`。
4. 支持在白名单、权限、taskId 等问题修复后从系统内重试。
5. 入站回调中的 `taskId` 要尽量保存和复用，减少后续查询官方接口的依赖。
6. `dry_run` 不能标记为真实成功，避免出现“页面成功但钉钉没动作”的假成功。
7. 修复当前部分中文消息乱码，便于业务人员理解。

### 7.3 推荐实施步骤

1. 后端先补齐状态查询和重试接口。
2. 服务层调整失败记录：保存 `taskLookupError`、官方 `errorCode`、官方原始返回摘要。
3. 钉钉任务查询策略调整为优先精确匹配 `actionerUserId`，fallback 需要在记录中标记。
4. 前端在项目详情增加钉钉回传状态块和失败重试按钮。
5. 增加单元测试和 Playwright 场景测试。
6. 上线前执行一次钉钉白名单和自动审批人配置健康检查。

## 8. 风险点

- IP 白名单仍是外部依赖，服务器出口 IP 变更后会再次失败。
- 钉钉审批实例如果已结束，再重试会返回无运行中任务，此时应展示为“无需重试/已处理”，不能无限失败。
- fallback 到第一个运行中任务存在误操作风险，建议默认关闭或至少记录 `taskIdSource=fallback`。
- 若 `autoApproverUserId` 不是当前任务处理人，钉钉会拒绝执行。
- `cc` 当前未正式实现，不能把新产品线完成通知展示为真实已发送。

```java
@Transactional(readOnly = true)
public DingTalkCompletionReturnStatusVO getCompletionReturnStatus(Long projectId) {
    Product product = getProductOrThrow(projectId);
    IntegrationRecord record = latestOutboundRecord(project);
    if (record == null) {
        return DingTalkCompletionReturnStatusVO.builder()
            .projectId(projectId)
            .productType(product.getProductType())
            .processingStatus("not_triggered")
            .retryable(false)
            .build();
    }
    Map<String, Object> payload = fromJson(record.getSourcePayloadJson());
    return DingTalkCompletionReturnStatusVO.builder()
        .integrationRecordId(record.getIntegrationRecordId())
        .projectId(record.getProjectId())
        .productType(product.getProductType())
        .nodeKey(record.getNodeKey())
        .externalInstanceId(record.getExternalInstanceId())
        .taskId(text(payload.get("taskId")))
        .taskIdSource(text(payload.get("taskIdSource")))
        .processingStatus(record.getProcessingStatus())
        .externalStatus(record.getExternalStatus())
        .errorCode(record.getErrorCode())
        .errorMessage(record.getErrorMessage())
        .retryCount(record.getRetryCount())
        .lastTriggeredAt(record.getLastTriggeredAt())
        .retryable(PROCESSING_FAILED.equals(record.getProcessingStatus()))
        .build();
}
```

```java
@Transactional
public DingTalkOutboundTriggerResultVO retryCompletionReturn(
    Long projectId,
    DingTalkCompletionReturnRetryDTO dto
) {
    Product product = getProductOrThrow(projectId);
    TimelineNodeDefinition finalNode = resolveCompletedFinalNode(product);
    requireRetryPermission(product);

    if (Boolean.TRUE.equals(dto == null ? null : dto.getRefreshTaskId())) {
        clearStoredTaskIdForNextLookup(projectId, finalNode);
    }

    DingTalkOutboundTriggerResultVO result = handleProjectCompleted(
        product,
        finalNode,
        currentOperatorName()
    );
    writeRetryOperationLog(product, finalNode, dto, result);
    return result;
}
```

```java
private String effectiveErrorMessage(String errorMessage, Map<String, Object> payload) {
    String lookupError = text(payload == null ? null : payload.get("taskLookupError"));
    if (!StringUtils.hasText(errorMessage)) {
        return StringUtils.hasText(lookupError) ? lookupError : null;
    }
    if (!StringUtils.hasText(lookupError) || errorMessage.contains(lookupError)) {
        return errorMessage;
    }
    return errorMessage + " (" + lookupError + ")";
```

## 14. 测试和验收方案

### 后端单元测试

- 入站记录没有 `taskId` 且钉钉查询失败时，出站记录为 `failed`，并保存官方错误信息。
- 入站记录没有 `taskId` 但 `workflow-task-lookup` 成功时，后续 `agree` 使用查询到的 `taskId`。
- 已存在 `success` 出站记录时，重复触发返回幂等命中，不重复代同意。
- `dry_run` 返回时不标记为真实 `success`。
- 钉钉审批已结束时，返回明确的“无运行中任务”状态，前端不持续提示无意义重试。

### API 测试

- `GET /api/v1/projects/{projectId}/dingtalk-completion-return` 能返回最新状态。
- `POST /api/v1/projects/{projectId}/dingtalk-completion-return/retry` 能复用现有项目完成回传逻辑。
- 无权限用户调用重试接口时返回权限错误。
- 非新型号线或未完成最终节点的项目不能执行代同意重试。

### Playwright 场景测试

- 项目最后节点确认完成后，页面显示 PLM 项目已完成。
- 钉钉失败时，页面显示失败原因和重试按钮。
- 修复白名单后点击重试，状态从 `failed` 变为 `success`。
- 成功后重试按钮隐藏或变为不可用。

## 15. 目标效果

实施后期望达到以下效果：

- 用户完成 PLM 项目时，不会因为钉钉接口失败导致项目状态不清晰。
- 业务人员能在项目详情直接看到钉钉代同意是否成功。
- 管理员能从系统内重试，不需要手工调用接口。
- 钉钉官方错误码、错误信息、taskId 来源都能沉淀到记录里，方便定位。
- IP 白名单、自动审批人、审批实例已结束等常见问题可以快速判断。
- 新产品线的 `cc` 未实现状态不会被误认为已通知成功。
