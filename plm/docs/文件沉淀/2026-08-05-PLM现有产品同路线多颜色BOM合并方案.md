# PLM 现有产品同路线多颜色 BOM 合并方案

日期：2026-08-05  
状态：方案沉淀，第一阶段已实施  
范围：现有产品历史数据合并；不修改当前 BOM 主业务模型；不新增 BOM 组对象。

## 1. 背景

当前导入后的部分产品存在“同一产品、同一条工艺路线、不同颜色拆成多份 BOM”的情况。

以 `NHA4030 / 超队Súper Capitán` 为例，当前存在：

```text
V1-02 -> Negro     -> 超队标准路线
V1-07 -> Rojo      -> 超队标准路线
V1-08 -> Azul Rey  -> 超队标准路线
V1-13 -> azul real -> 超队标准路线
```

这些 BOM 都是正式 BOM，只是颜色不同。业务上，这类数据不应该被理解为四套完全独立 BOM，而应理解为：同一条工艺路线下的一套 BOM，适用于多个颜色；不同颜色可能只在色粉、色母、颜色相关物料上存在差异。

当前系统 BOM 模型已经支持“一份 BOM 关联一条工艺路线，并挂多个适用颜色”的表达方式。因此本方案不新增 BOM 组、不修改 BOM 主流程，只对现有历史数据做归并整理。

## 2. 目标

将现有产品中满足条件的多份颜色 BOM 合并成一份 BOM：

```text
合并前：
同一产品下，多份 BOM 分别对应不同颜色，但共用同一条工艺路线。

合并后：
同一产品下，一份 BOM 关联该工艺路线，并在 BOM route 上挂多个适用颜色。
```

合并后应保留：

1. 产品不变；
2. 工艺路线不变；
3. BOM 主版本口径可追溯；
4. 多个适用颜色；
5. 共用物料；
6. 色粉、色母等颜色差异物料；
7. 成本和明细来源可审计；
8. 已发布正式资料的业务含义。

## 3. 不做的事情

本方案明确不做以下事情：

1. 不新增 BOM 组主对象；
2. 不修改 BOM 主业务模型；
3. 不修改工艺路线主模型；
4. 不把不同工艺路线的 BOM 强行合并；
5. 不把主体物料结构明显不同的 BOM 强行合并；
6. 不用简单 SQL 直接删除历史 BOM；
7. 不破坏已有 BOM 明细、颜色、成本、正式发布状态的可追溯性。

## 4. 合并对象

合并对象是系统中已经存在的产品 BOM 数据，重点处理导入产生的同路线多颜色 BOM。

候选数据范围：

```sql
plm_product_bom.product_id = 同一产品
plm_product_bom.bom_scope in ('candidate', 'formal')
plm_product_bom.status in ('draft', 'reviewing', 'released')
plm_product_bom.deleted_flag = 0
plm_product_bom_route.status = 'active'
plm_product_bom_route.deleted_flag = 0
```

优先处理已经发布的正式 BOM：

```sql
bom_scope = 'formal'
status = 'released'
```

## 5. 合并判定规则

### 5.1 必须满足

一组 BOM 可以合并，需要同时满足：

1. 同一个产品；
2. 同一条工艺路线，优先按 `process_id` 判断；
3. 同一 BOM route 变体口径，例如 `route_variant_no = BASE`；
4. 每份 BOM 的适用颜色不同或部分不同；
5. 主体 BOM 结构一致；
6. 差异主要来自颜色相关物料，例如色粉、色母、颜色件；
7. BOM 类型一致，例如都为 `mbom` 或都为 `ebom`；
8. 发布状态可兼容，例如同为 `released` 或均处于可整理状态。

### 5.2 主体 BOM 结构一致的判断

主体 BOM 结构一致，建议按“排除颜色差异物料后”的明细签名判断。

签名字段建议包括：

```text
item_code
item_name
specification
unit
quantity
line_no 或 normalized_line_no
material_source
```

颜色差异物料需要从签名中排除或单独归类。判断方式可以组合使用：

1. 物料名称包含色粉、色母、颜料、color powder、masterbatch 等关键字；
2. 物料分类为颜色相关物料；
3. 物料编码落在颜色物料编码段；
4. Excel 导入列中存在明确颜色差异标记；
5. 人工确认的颜色差异物料白名单。

### 5.3 不允许合并

以下情况不合并：

1. 工艺路线不同；
2. 主体结构件不同；
3. 关键物料用量不同，且不是颜色差异物料；
4. BOM 类型不同；
5. 一个 BOM 覆盖多条路线，另一个只覆盖单路线，无法一一对应；
6. 成本结构差异来自工艺、包装、结构物料，而不是颜色；
7. 已经被下游 SKU、订单、成本报表强依赖，且无法安全迁移引用；
8. 人工标记为禁止合并。

## 6. 合并后的数据形态

合并后保留一份主 BOM。

### 6.1 ProductBom

选择一份 BOM 作为主 BOM，其他 BOM 作为被合并来源。

主 BOM 建议选择优先级：

1. 当前正式关系 active 的 BOM；
2. 最新 released 的 formal BOM；
3. 版本号排序最靠后的 BOM；
4. 明细最完整的 BOM；
5. 人工指定的 BOM。

主 BOM 保持：

```text
bom_scope
status
frozen_flag
released_at
released_by
version_no
bom_type
```

版本号建议不要简单保留单一颜色版本号。可选方案：

```text
V1          推荐，表示合并后的主版本
V1-MULTI    可读性更强
V1-02+07+08+13  可追溯但偏长
```

建议采用 `V1` 或人工确认后的版本号，并在 remark 或审计表中记录来源版本：

```text
mergedFrom: V1-02,V1-07,V1-08,V1-13
```

### 6.2 ProductBomRoute

合并后主 BOM 下保留一条 BOM route：

```text
product_bom_id = 主 BOM ID
process_id = 原共同工艺路线 ID
route_code = 原路线编码
route_name = 原路线名称
route_variant_no = BASE
status = active
```

如果多份来源 BOM route 的 `shared_bom_group_code` 不一致，以主 BOM route 为准，并记录来源关系。

### 6.3 ProductBomRouteColor

将来源 BOM route 的颜色全部合并到主 BOM route 下：

```text
Negro
Rojo
Azul Rey
azul real
```

要求：

1. 按 `color_code + color_name` 去重；
2. 保留 `code_item_id`；
3. 保留 active 状态；
4. 颜色名称只做 trim，不做随意翻译；
5. 如果同一 `color_code` 对应多个名称，进入人工复核。

### 6.4 ProductBomItem

物料明细合并分两类处理。

共用物料：

```text
同一 item_code / specification / unit / quantity
只保留一条
```

颜色差异物料：

```text
保留多条
需要能表达适用颜色
```

如果当前 `ProductBomItem` 没有适用颜色字段，则有两种处理口径：

1. 保留多条颜色差异物料，并在 remark 或 source_snapshot_json 中记录适用颜色；
2. 暂不合并存在颜色差异物料但无法表达适用颜色的 BOM，先进入人工复核清单。

推荐第一阶段采用保守策略：

```text
共用物料自动合并；
颜色差异物料如果系统无法结构化表达适用颜色，则保留来源 BOM 不合并，或只生成待处理报告。
```

避免合并后出现“所有颜色都使用所有色粉”的错误。

### 6.5 ProductBomCostSnapshot

成本快照不能简单相加。

处理建议：

1. 主 BOM 保留主 BOM 原成本快照；
2. 被合并 BOM 的成本快照归档保留；
3. 合并完成后重新计算主 BOM 成本；
4. 如果颜色差异物料成本无法按颜色区分，则合并结果标记为需要复核。

## 7. 正式关系处理

合并后，正式关系应指向主 BOM route。

处理规则：

1. 主 BOM route 对应的正式关系保留 active；
2. 被合并 BOM route 对应的正式关系置为 invalidated 或 merged；
3. 被置为失效的正式关系需要记录合并目标；
4. 不删除历史正式关系。

如果当前表没有 `merged_to_*` 字段，则先通过 `remark` 记录：

```text
mergedToProductBomId=主BOMID; mergedToProductBomRouteId=主RouteID
```

## 8. 被合并 BOM 的处理

不建议物理删除被合并 BOM。

推荐处理方式：

```text
status = archived
deleted_flag = 0
remark 记录 mergedToProductBomId
```

原因：

1. 保留历史导入结果；
2. 保留审计链；
3. 避免已有引用直接断掉；
4. 出问题可以回滚。

如果业务要求页面不再展示被合并 BOM，可以在列表查询中隐藏 `status=archived`，但这属于后续展示优化，不在本方案第一阶段强制处理。

## 9. 处理流程

建议分三阶段执行。

### 9.1 预分析

生成待合并报告，不写库。

报告字段：

```text
product_id
product_code
product_name
process_id
route_name
candidate_bom_ids
candidate_versions
colors
common_item_count
color_diff_item_count
risk_level
can_auto_merge
reason
```

### 9.2 人工确认

对报告中的合并组做人工确认：

1. 确认可合并；
2. 确认主 BOM；
3. 确认版本号；
4. 确认颜色差异物料处理方式；
5. 确认是否归档来源 BOM。

### 9.3 执行合并

执行顺序：

1. 锁定合并组；
2. 选择主 BOM；
3. 合并 BOM route color；
4. 合并共用物料；
5. 处理颜色差异物料；
6. 重算成本；
7. 更新正式关系；
8. 归档被合并 BOM；
9. 写操作日志；
10. 输出合并结果报告。

## 10. 示例

以产品 `NHA4030 / 超队Súper Capitán` 为例。

合并前：

```text
BOM 32 / V1-02 / Negro     / route 228
BOM 33 / V1-07 / Rojo      / route 228
BOM 34 / V1-08 / Azul Rey  / route 228
BOM 35 / V1-13 / azul real / route 228
```

合并后：

```text
主 BOM：BOM 33 或人工指定 BOM
版本号：V1
路线：route 228 / 超队标准路线
适用颜色：
  - Negro
  - Rojo
  - Azul Rey
  - azul real
共用物料：去重保留
颜色差异物料：按颜色保留或进入复核
来源 BOM：归档并记录 mergedTo
```

## 11. 对钉钉新型号继承的影响

合并完成后，钉钉新型号继承会更顺：

```text
来源产品一份正式 BOM
一条 BOM route 覆盖多个颜色
新型号按来源产品确认颜色继承
复制一份目标 BOM
复制一条目标工艺路线
目标 BOM route 挂多个颜色
```

这样可以避免“只继承最新一份颜色 BOM”的问题，也避免同一条路线被重复复制多次。

## 12. 风险点

### 12.1 色粉物料适用颜色丢失

最大风险是：不同颜色使用不同色粉，合并后如果没有结构化记录适用颜色，会导致所有颜色看起来都使用所有色粉。

解决原则：

```text
不能表达颜色适用关系时，不自动合并颜色差异物料。
```

### 12.2 成本口径变化

颜色差异物料会影响单色成本。

合并后如果 BOM 成本只保留一个总成本，需要明确：

1. 是平均成本；
2. 是主颜色成本；
3. 是重新计算后的标准成本；
4. 还是按颜色另行展示。

第一阶段建议保留来源成本，合并后标记成本需复核。

### 12.3 下游引用断链

已有 SKU、订单、报表可能引用了被合并 BOM。

执行前必须检查：

```text
SKU 默认 BOM
订单引用 BOM
成本报表引用 BOM
文件归档引用 BOM
操作日志引用 BOM
```

有引用时，不删除，只归档，并建立 mergedTo 追溯。

## 13. 验证口径

合并后至少验证：

1. 产品详情 BOM 管理只看到目标主 BOM；
2. 主 BOM route 下能看到多个适用颜色；
3. 工艺路线仍然是原来的同一条路线；
4. 共用物料没有重复；
5. 颜色差异物料没有错误混用；
6. 成本显示符合预期；
7. 被合并 BOM 可追溯；
8. 正式关系指向主 BOM route；
9. 钉钉新型号继承能继承合并后的 BOM；
10. 新型号继承后工艺路线、BOM、颜色数据完整。

## 14. 推荐实施顺序

1. 先做只读分析报告；
2. 选 1 个产品试点，例如 `NHA4030 / 超队Súper Capitán`；
3. 人工确认合并组；
4. 在测试库执行合并；
5. 验证页面、接口、钉钉继承；
6. 再扩展到其他产品；
7. 最后把同样规则沉淀到后续导入流程，避免再次导入成多份颜色 BOM。

## 15. 后期维护建议

1. 导入时优先按“同产品 + 同路线 + 同主体结构”归并；
2. 色粉、色母等颜色差异物料必须有明确适用颜色；
3. BOM 页面应区分“BOM 发布状态”和“适用颜色”；
4. 历史合并必须保留来源 BOM 追溯；
5. 钉钉继承逻辑应优先使用合并后的正式 BOM；
6. 对不能自动合并的数据输出人工复核清单，不要强行处理。

## 16. 已实施内容

本次代码已落地第一阶段保守治理能力：

1. 新增历史 BOM 合并分析接口；
2. 新增历史 BOM 保守自动合并接口；
3. 自动合并仅处理“单路线、同产品、同状态、同结构、无危险颜色差异”的候选组；
4. 合并后保留主 BOM，来源 BOM 归档并写入 `mergedToProductBomId`；
5. 合并后保留主路线颜色集合，并补齐正式关系；
6. 前端工作台候选 BOM 列表已默认隐藏 `archived` 版本；
7. 已补充合并结果类型与 API 定义，方便后续在页面加分析面板或操作按钮。

1. 未实现人工确认面板；

4. 未对历史导入批次自动执行全量合并，只提供可调用接口。
