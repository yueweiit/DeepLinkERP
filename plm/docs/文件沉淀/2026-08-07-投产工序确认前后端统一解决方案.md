# 投产工序确认前后端统一解决方案

## 1. 文档目的

针对项目 `Alterna幻甲 SM S280` 在第 10 步确认时报错：

```text
路线 Alterna幻甲 工艺路线 - SM S280 尚未确认有效投产工序
```

本方案用于统一前端操作、后端校验、投产工序落库和后续 SKU 生成之间的逻辑。

本文件只记录排查结果和拟修改方案，当前不修改业务代码。

## 2. 当前实际状态

项目数据：

| 项目 | 值 |
|---|---|
| projectId | 19240 |
| 项目名称 | Alterna幻甲 SM S280 |
| productType | model_variant |
| 当前步骤 | 10 |
| 当前节点 | MODEL_VARIANT_PROCESS_CONFIRM |
| 正式 BOM | productBomId=62 |
| 正式 BOM 路线 | productBomRouteId=104 |
| 工艺路线 | processId=404 |

工艺路线 `processId=404` 已存在 4 个有效子工序：

```text
409、410、411、412
```

但生产确认接口返回：

```json
{
  "selectedOperationCount": 0,
  "selectedColorCount": 0,
  "routeSelections": [
    {
      "productBomRouteId": 104,
      "operationProcessIds": [],
      "applicableColors": []
    }
  ]
}
```

因此，本次错误的直接原因是：

> 正式 BOM 路线已经确认，但 `plm_process_production_operation_selection` 中没有当前项目、当前 BOM 路线对应的 `confirmed` 有效工序记录。

## 3. 前后端现有逻辑核对

### 3.1 后端第 10 步门禁

文件：

```text
plm-server/src/main/java/com/yuewei/plm/module/project/service/impl/TimelineActionServiceImpl.java
```

当前逻辑：

```java
case "PRODUCT_LINE_PROCESS_CONFIRM", "MODEL_VARIANT_PROCESS_CONFIRM" ->
    productionConfirmationService.requireOperationsConfirmed(projectId);
```

产品线和新型号线都会执行投产工序门禁。

### 3.2 后端“有效投产工序”判定

文件：

```text
plm-server/src/main/java/com/yuewei/plm/module/bom/service/ProductionConfirmationService.java
```

`requireOperationsConfirmed` 的判断条件：

1. 项目存在 active 正式 BOM 路线选择。
2. 路线有效、未删除，且属于当前项目。
3. 投产工序选择记录满足：
   - `product_id = projectId`
   - `product_bom_route_id = routeId`
   - `status = confirmed`
   - `deleted_flag = 0`
4. 工序必须是当前工艺路线的子工序：
   - `operation.parentProcessId = route.processId`
   - 工序未删除。
5. 投产工序记录的路线版本与当前工艺路线版本一致；任一版本为空时兼容通过。

当前后端实际只要求每条 active 正式 BOM 路线至少有一条有效投产工序，不要求必须选择全部子工序。

### 3.3 后端确认接口

接口：

```http
POST /api/v1/projects/{projectId}/production-routes/confirm
```

后端会校验：

1. `operationProcessIds` 不能为空。
2. BOM 必须属于当前项目，状态为 `reviewing` 或 `released`。
3. BOM 路线必须 active，且属于当前 BOM 和项目。
4. 工艺路线必须与 BOM 路线的 `processId` 一致。
5. 每个工序必须是当前工艺路线的子工序。
6. 路线必须有 current 或 baseline 成本快照。
7. 至少存在一个有效适用颜色，且颜色必须属于该 BOM 路线。

确认成功后，后端在同一事务内写入：

```text
plm_product_bom_route_formal_selection
plm_process_production_operation_selection
plm_product_production_color_decision
```

工序记录状态为 `confirmed`。

### 3.4 前端现有提交逻辑

文件：

```text
plm-web/src/views/project/components/ProductionConfirmationDialog.vue
```

前端当前并不是让用户逐条选择子工序，而是自动读取：

```ts
const operationProcessIds =
  group.process.operations.map(operation => operation.processId)
```

然后把当前路线的全部子工序提交给后端。

这与后端“允许至少一条有效工序”的判定并不矛盾，但界面表达不准确：界面展示了“工序名称”，实际没有工序选择控件。

### 3.5 已发现的前端入口不一致

文件：

```text
plm-web/src/views/project/ProjectCenterView.vue
```

当前按钮只判断：

```vue
node.nodeKey === 'PRODUCT_LINE_PROCESS_CONFIRM'
```

但后端第 10 步同时使用：

```text
PRODUCT_LINE_PROCESS_CONFIRM
MODEL_VARIANT_PROCESS_CONFIRM
```

这意味着新型号线项目可能无法从当前项目详情页正常打开“敲定投产工序”对话框。`Alterna幻甲 SM S280` 正是新型号线项目，属于该不一致场景。

## 4. 解决方案

采用“保留第 10 步工序确认语义，但统一前后端入口和提交契约”的方案。

不建议仅在前端绕过错误，也不建议只删除后端门禁。原因是：

- 后续颜色确认要求颜色关联 active 正式 BOM 路线；
- 工序确认接口同时建立正式路线、工序和适用颜色的关联；
- 只取消门禁会让项目可以跳过工序确认，但会保留空的投产确认数据；
- 审计上无法区分“用户确认了工序”和“系统跳过了工序”。

### 4.1 前端统一第 10 步入口

修改文件：

```text
plm-web/src/views/project/ProjectCenterView.vue
```

拟修改逻辑：

```ts
const processConfirmNodeKeys = new Set([
  'PRODUCT_LINE_PROCESS_CONFIRM',
  'MODEL_VARIANT_PROCESS_CONFIRM'
])
```

模板统一使用：

```vue
<el-button
  v-if="processConfirmNodeKeys.has(node.nodeKey)"
  size="small"
  type="primary"
  plain
  @click="openProductionConfirmation('operations')"
>
  敲定投产工序
</el-button>
```

目标：

- 产品线和新型号线都能打开同一个投产工序确认对话框；
- 不再出现后端有门禁、前端没有操作入口的情况。

### 4.2 前端明确展示工艺路线下的子工序

修改文件：

```text
plm-web/src/views/project/components/ProductionConfirmationDialog.vue
```

拟修改逻辑：

1. 根据 `process.operations` 展示所有子工序。
2. 使用稳定的 `processId` 作为工序选择值。
3. 默认选中当前路线下已确认的工序。
4. 新确认时默认选中全部有效子工序，保持现有自动确认体验。
5. 用户可以取消不投产的子工序。
6. 如果某条路线最终没有选中工序，前端禁止提交并提示具体路线。

提交参数保持统一：

```json
{
  "routes": [
    {
      "processId": 404,
      "productBomId": 62,
      "productBomRouteId": 104,
      "operationProcessIds": [409, 410, 411, 412],
      "applicableColors": [
        {
          "codeItemId": 1,
          "colorCode": "31",
          "colorName": "透明"
        }
      ]
    }
  ],
  "remark": "确认投产工序、使用 BOM 与适用颜色"
}
```

### 4.3 后端补强确认接口的数据一致性

修改文件：

```text
plm-server/src/main/java/com/yuewei/plm/module/bom/service/ProductionConfirmationService.java
```

拟修改逻辑：

1. 对 `operationProcessIds` 去重并按工艺路线顺序保存。
2. 后端继续强制校验工序必须属于当前路线，不能信任前端传入的 ID。
3. 后端返回每条路线的：
   - 已确认工序 ID；
   - 工序名称；
   - 工序数量；
   - 适用颜色。
4. 对已经确认过的路线重新确认时，先归档旧批次，再保存新批次，保持当前批次语义。
5. 错误信息明确到路线和缺失原因，例如：

```text
路线 xxx 尚未选择投产工序
路线 xxx 缺少适用颜色
路线 xxx 缺少有效成本快照
```

### 4.4 第 10 步门禁保持与确认数据一致

修改文件：

```text
plm-server/src/main/java/com/yuewei/plm/module/project/service/impl/TimelineActionServiceImpl.java
```

保持以下逻辑：

```java
case "PRODUCT_LINE_PROCESS_CONFIRM", "MODEL_VARIANT_PROCESS_CONFIRM" ->
    productionConfirmationService.requireOperationsConfirmed(projectId);
```

只有用户在对话框中提交成功并生成 `confirmed` 工序记录后，才允许推进第 10 步。

如果业务最终决定取消门禁，应单独设计“系统跳过确认”的审计事件和后续数据补全机制，不能只删除这一行调用。

## 5. SKU 生成逻辑

颜色确认接口仍为：

```http
POST /api/v1/projects/{projectId}/production-colors/confirm
```

后端确认颜色后会调用：

```java
syncModelVariantConfirmedColorsAndSkus(project)
```

对于 `model_variant` 项目：

1. 读取当前项目已确认颜色。
2. 按颜色查找已有 SKU。
3. 没有 SKU 时创建新 SKU。
4. 已存在时更新颜色及相关编码字段。
5. 将颜色确认记录关联到创建出的 SKU。

因此，统一方案不会破坏不同颜色 SKU 自动生成。前提是：

- 第 10 步完成正式 BOM 路线和适用颜色确认；
- 后续颜色确认步骤提交有效颜色；
- 颜色仍然关联已确认的正式 BOM 路线。

## 7. 目标效果

完成后应满足：

1. 产品线和新型号线都能从当前第 10 步打开确认窗口。
2. 页面明确显示当前工艺路线的全部子工序。
3. 用户可确认全部或部分有效投产工序。
4. 前端不会提交空工序或空适用颜色。
5. 后端不会接受不属于当前路线的工序。
6. 成功确认后，接口返回的 `operationProcessIds` 不为空。
7. 第 10 步确认不再出现“尚未确认有效投产工序”。
8. 后续确认不同颜色时，能够继续自动创建或更新对应 SKU。
9. 重复确认不会产生重复有效记录，旧批次会被归档。
10. 审计记录能够区分用户确认的 BOM 路线、工序和适用颜色。

## 8. 验收用例

### 用例一：当前项目

项目 `19240`：

- 正式 BOM 路线 `104`；
- 工艺路线 `404`；
- 子工序 `409/410/411/412`；
- 至少选择一个适用颜色；
- 提交投产工序确认；
- 第 10 步确认成功。

### 用例二：部分工序

只提交 `[409, 410]`：

- 后端应接受；
- 第 10 步应允许推进；
- 后续颜色确认不应因为未选择全部子工序而失败。

### 用例三：非法工序

提交不属于 `processId=404` 的工序：

- 后端必须拒绝；
- 不得写入正式确认记录。

### 用例四：不同颜色 SKU

确认颜色 `31`、`32`：

- 每个颜色生成或复用一个 SKU；
- 重复提交同一颜色不得创建重复 SKU。

### 用例五：路线版本变化

旧路线版本的工序确认记录不能误通过新路线版本门禁；版本为空的历史兼容记录按现有兼容规则处理。

## 9. 结论

当前错误的根本问题是：

> 后端要求确认投产工序，但新型号线前端没有提供与后端一致的第 10 步确认入口；同时前端工序界面没有真实呈现工序选择状态，导致正式 BOM 路线和实际投产工序确认记录脱节。

推荐实施“前后端统一确认契约”方案：前端补齐新型号线入口并明确子工序选择，后端继续作为最终校验方，确认成功后再进入第 10 步和后续颜色 SKU 流程。

## 11. 工作台流程入口迁移方案

### 11.1 背景

当前“敲定投产工序”入口已经在项目详情弹窗的新型号流程区可用，但用户的主要操作路径是工作台首页的“项目进度”弹窗。实际截图显示第 10 步“敲定工序”位于工作台流程弹窗中，底部操作区仍展示“确认当前节点 / 返回上一步 / 强制推进 / 新建工艺路线 / 上传节点资料”。

这会造成操作认知不一致：业务用户在工作台看到第 10 步，却找不到主操作“敲定投产工序”，只能进入项目详情后再操作。

### 11.2 目标效果

将“敲定投产工序”按钮迁移到工作台“项目进度”弹窗的流程操作区，作为第 10 步“敲定工序”的主操作入口。

目标交互：

1. 工作台点击项目卡，打开“项目进度”弹窗。
2. 当前小节点为第 10 步 `MODEL_VARIANT_PROCESS_CONFIRM` / `PRODUCT_LINE_PROCESS_CONFIRM` / 节点名“敲定工序”时，底部显示“敲定投产工序”。
3. 点击后直接打开现有 `ProductionConfirmationDialog`。
4. 弹窗内展示使用 BOM、投产工序、适用颜色。
5. 确认后刷新工作台时间轴和项目列表。
6. 工作台不再把第 10 步误判为“新建工艺路线”。

function isProcessConfirmationStep(step?: { nodeKey?: string; stepNo?: number; title?: string; stepName?: string; nodeName?: string } | null) {

  const key = step.nodeKey || ''
  const name = step.title || step.stepName || step.nodeName || ''
  return processConfirmationNodeKeys.has(key)
    || key.endsWith('_PROCESS_CONFIRM_STEP')
    || name.includes('敲定投产工序')
    || name.includes('敲定工序')
}
