# 2026-07-29 PLM 归档产品/SKU导入与展示问题排查沉淀

## 1. 文档目的

本文用于沉淀项目管理中“已归档（产品）”“已归档（SKU）”导入数据无成功提示、数据未写入、SKU管理中已有归档新型号未展示的问题排查结论与后续修复范围。

本阶段只记录原因和修复方案，不修改业务代码。

## 2. 问题现象

1. 在项目管理的已归档产品或已归档SKU页面点击“导入数据”，可以选择并上传数据文件。
2. 点击“开始导入”后页面没有成功、失败或校验结果提示。
3. 导入后列表未刷新，也没有看到新增归档数据。
4. SKU管理中后端或数据表里已有归档的新型号/SKU，但前端页面没有展示出来。

## 3. 主要结论

### 3.1 归档导入弹窗未接入真实导入流程

位置：

- `plm-web/src/views/project/ProjectCenterView.vue`

当前归档导入弹窗里的 `el-upload` 使用了 `:auto-upload="false"`，但页面没有保存选中的文件，也没有调用导入接口。底部“开始导入”按钮只是关闭弹窗：

```vue
<el-button type="primary" @click="importVisible = false">开始导入</el-button>
```

因此当前行为不是“导入成功但没有提示”，而是导入入口只完成了界面展示，没有执行预校验、提交入库、成功提示和列表刷新。

### 3.2 系统导入页已有可复用闭环

位置：

- `plm-web/src/views/system/SystemImportExportView.vue`
- `plm-web/src/api/modules/importExport.ts`

系统导入页已经实现了：

1. 选择文件。
2. 调用 `previewImport`。
3. 展示预览结果和错误行。
4. 调用 `commitImport`。
5. 成功后清理文件、刷新批次并给出提示。

归档导入弹窗应复用或对齐这套交互，不建议另起一套行为。

### 3.3 后端导入对象没有独立 `sku` objectType

位置：

- `plm-server/src/main/java/com/yuewei/plm/module/importexport/service/impl/MasterDataImportExportServiceImpl.java`

后端通用导入对象类型为：

```java
Set.of("product", "inventory", "process", "attachment")
```

但产品导入行里的 `product_type` 支持：

```java
Set.of("product_line", "model_variant", "sku")
```

所以 SKU 历史归档导入本质上应走 `product` 导入接口，通过文件字段 `product_type=sku` 或 `product_type=model_variant` 区分业务类型。

如果前端直接调用 `/import-export/sku/preview`，后端会认为对象类型不支持。

### 3.4 前端项目接口会把 `sku` 误映射为 `product_line`

位置：

- `plm-web/src/api/modules/project.ts`

当前 `ProductType` 只定义为：

```ts
type ProductType = 'product_line' | 'model_variant'
```

并且归一化逻辑为：

```ts
return value === 'model_variant' ? 'model_variant' : 'product_line'
```

当后端返回 `productType=sku` 时，前端会把它误判为 `product_line`。这会影响归档分类、详情弹窗类型、流程模式和完成率计算。

### 3.5 归档列表使用完成率作为硬过滤条件，导致 SKU 被过滤

位置：

- `plm-web/src/views/project/ProjectCenterView.vue`

归档项目计算逻辑目前要求：

```ts
['released', 'archived'].includes(item.status) && item.completionRate >= 1
```

后端历史导入对终态产品设置当前步骤：

- `product_line`：22
- `model_variant` 或 `sku`：18

如果 `sku` 被前端误映射为 `product_line`，完成率会按 22 步计算，得到 `18 / 22 = 0.82`，因此即使状态是 `archived`，也会被前端过滤掉。

归档判断不应依赖前端推导完成率。`released` 和 `archived` 本身就是归档视图的核心准入条件。

### 3.6 SKU卡片依赖父产品也在当前分页结果中

位置：

- `plm-web/src/views/project/ProjectCenterView.vue`

归档SKU产品卡片通过归档SKU反查父产品：

```ts
const parent = rows.value.find((row) => row.productId === item.parentProductId)
```

但 `rows` 当前只加载：

```ts
getProjects({ page: 1, size: 100 })
```

如果父产品不在这100条中，即使SKU存在，也不会生成产品卡片入口。用户会感知为“SKU管理没有展示”。

### 3.7 独立 SKU 管理页同样存在分页和本地过滤风险

位置：

- `plm-web/src/views/product/SkuView.vue`

该页面同样只加载：

```ts
getProductList({ page: 1, size: 100 })
```

然后在前端本地按产品和SKU关系过滤。数据量超过100、父产品不在同一页、归档状态未按接口筛选时，都可能导致真实存在的SKU没有展示。

## 4. 需要关联修改的范围

### 4.1 前端必须修改

1. `plm-web/src/views/project/ProjectCenterView.vue`
   - 接通归档导入弹窗。
   - 保存选中文件。
   - 点击开始导入时调用预览和提交接口。
   - 提交成功后展示成功/失败数量。
   - 提交后刷新归档列表。
   - 归档筛选去掉 `completionRate >= 1` 硬门槛，或至少对 `released/archived` 直接放行。
   - SKU卡片不能只依赖当前第一页里的父产品。

2. `plm-web/src/api/modules/project.ts`
   - `ProductType` 增加 `sku`。
   - `normalizeProductType` 保留 `sku`。
   - `getCompletionRate` 对 `model_variant` 和 `sku` 都按18步计算。
   - `productFlowMode` 和 `moldAction` 对 `sku` 做明确兜底，避免被当成新产品线。

3. `plm-web/src/views/product/SkuView.vue`
   - 独立SKU管理页不能只取第一页100条后本地筛选。
   - 建议按父产品、状态、类型调用后端分页接口。
   - 至少需要覆盖 `productType=sku` 和 `productType=model_variant` 两类历史数据。

4. `plm-web/src/api/modules/importExport.ts`
   - 若归档SKU按钮仍走 `product` 导入，不需要新增 `sku` objectType。
   - 若希望前端语义上支持 `sku`，则需要把 `ImportExportObjectType` 增加 `sku`，并由后端兼容映射。

### 4.2 后端视方案修改

1. `plm-server/src/main/java/com/yuewei/plm/module/importexport/service/impl/MasterDataImportExportServiceImpl.java`
   - 短期可不改，前端统一调用 `product` 导入。
   - 如果希望接口支持 `/import-export/sku/preview`，需要将 `sku` 作为对象类型别名映射到 `product`。
   - 需要保证模板、预览、提交、批次记录中的对象类型展示口径一致。

2. `plm-server/src/main/java/com/yuewei/plm/controller/dto/ProductCreateDTO.java`
   - 当前普通新建接口只允许 `product_line|model_variant`。
   - 如果SKU只允许由投产确认或历史导入生成，则不需要修改。
   - 如果未来支持手动新增SKU，则需要放开 `sku`，并补齐父产品、颜色、型号等校验。

3. 项目列表接口
   - 当前 `/projects` 支持分页、状态、产品类型过滤，但前端未充分使用。
   - 建议后续提供归档SKU专用查询能力，或者返回SKU及父产品摘要，减少前端拼装和分页遗漏。

## 5. 推荐修复方案

### 5.1 短期最小修复

1. 归档导入按钮统一调用 `previewImport('product', file)`。
2. 对导入类型为SKU时，在弹窗说明中提示文件字段 `product_type` 填 `sku` 或 `model_variant`。
3. 预览无错误后调用 `commitImport(importToken)`。
4. 成功后提示：
   - 导入成功条数。
   - 导入失败条数。
   - 如有失败，提示查看错误行。
5. 提交完成后调用 `loadData()` 刷新项目管理列表。
6. `project.ts` 支持保留 `sku` 类型。
7. 归档列表基于 `status in released/archived` 展示，不再用完成率阻断。

### 5.2 中期结构优化

1. 抽取归档导入组件，复用系统导入页的预览、提交、错误表格逻辑。
2. 为归档SKU新增查询接口或前端分页策略：
   - 先查 `status=released/archived` 且 `productType=sku/model_variant`。
   - 再按 `parentProductId` 批量补父产品。
   - 或由后端直接返回父产品卡片聚合。
3. 独立SKU管理页与项目归档SKU页共用同一套SKU查询服务，避免两边口径不同。

### 5.3 长期口径收口

1. 明确 `model_variant` 与 `sku` 的业务边界：
   - `model_variant`：新型号项目线。
   - `sku`：颜色、成品编码、正式投产后的SKU视图。
2. 明确归档页“已归档（SKU）”到底展示：
   - 只展示 `sku`。
   - 还是同时展示 `model_variant` 与其生成的 `sku`。
3. 后端统一提供类型常量，前端不要散落硬编码。
4. 导入模板中增加字段说明页，减少用户把SKU文件导到错误对象类型。

## 6. 关联风险

1. 如果只接通导入，不修 `sku` 类型映射，数据可能已经入库但仍不展示。
2. 如果只修类型映射，不修导入弹窗，用户仍会看到“上传后无提示、无数据变化”。
3. 如果只取消完成率过滤，不修分页和父产品补全，部分SKU仍没有产品卡片入口。
4. 如果前端直接把导入对象改成 `sku`，但后端不兼容，接口会返回“不支持的导入导出对象”。
5. 如果放开手动创建 `sku`，需要额外处理父产品、颜色编码、成品编码唯一性、BOM/工艺继承等规则，不能只改 DTO 校验。

3. `productType=sku` 不再被前端映射为 `product_line`。
4. `released/archived` 的SKU不会因为完成率小于1被过滤。
5. 数据量超过100时，归档SKU仍能通过分页或查询展示。

3. 已放弃项目不被归档页误收。

1. BOM、工艺路线、投产确认中的SKU逻辑已有独立分支，除非修复展示后发现明细联动异常，否则不先动。

## 11. 2026-07-29 二次修复记录

### 11.1 二次排查补充根因

用户反馈第一轮修改后仍不可用，继续沿真实链路复核后发现还有三个高概率断点：

1. 归档页导入弹窗使用 `el-upload` 手动上传模式，页面没有复用系统导入页的原生文件输入链路，存在文件未稳定进入提交函数的风险。
2. 前端文案和文件选择允许 `.xls`，但后端 `readExcelRows` 使用 `new XSSFWorkbook(input)`，实际只支持 `.xlsx`；上传旧版 `.xls` 会解析失败。
3. SKU管理页多路查询使用 `Promise.all`，任一路查询失败会进入 `catch` 并把 `rows` 清空，导致已有归档SKU也不展示。

### 11.2 二次修改内容

1. `plm-web/src/views/project/ProjectCenterView.vue`
   - 归档导入控件从 `el-upload` 改为原生 `<input type="file">`，与系统导入页稳定链路保持一致。
   - 归档项目三路加载从 `Promise.all` 改为 `Promise.allSettled`，部分接口失败时仍展示已成功返回的数据。
   - 产品类型标签增加 `sku -> SKU`，方便确认数据口径。

2. `plm-web/src/views/product/SkuView.vue`
   - SKU管理页多路加载从 `Promise.all` 改为 `Promise.allSettled`，避免单个筛选接口失败导致全页清空。
   - 产品卡片加入父产品兜底：如果只有 `model_variant/sku` 子行返回、父产品行未返回，也生成只用于展示分组的产品卡片入口。

3. `plm-server/src/main/java/com/yuewei/plm/module/importexport/service/impl/MasterDataImportExportServiceImpl.java`
   - Excel读取从 `XSSFWorkbook` 改为 `WorkbookFactory.create(input)`。
   - 导入解析错误提示调整为支持 `.xlsx/.xls/.csv`。
   - 这样页面允许的 `.xls` 与后端真实能力一致。

4. 测试补充：
   - `ProjectCenterView` 增加“选择文件后调用 `previewImport('product', file)` 并提交”的测试。
   - `MasterDataImportExportServiceImplTest` 增加 `.xls` 产品导入预览测试。

## 14. 2026-07-30 工艺导入“工艺状态不支持”排查与修正

### 14.1 截图现象

`系统管理 > 数据导入 > Process 工艺记录` 上传 `工艺导入模板_已转换.xlsx` 后：

- 总行数：37
- 可导入：0
- 失败：37
- 失败提示：`工艺状态不支持`

### 14.2 直接原因

实际 Excel 的 `status` 列 37 行全部为 `active`。当前 PLM 的 Process 状态机只允许：

`draft / confirmed / locked / changed / archived`

因此预览校验在 `MasterDataImportExportServiceImpl.validateProcessRow()` 中全部拒绝。

### 14.3 关联数据问题

该转换文件中的 `product_code` 包含 `NHA3020`、`NBD1010` 等工序/产品特征编码，不全部等同于 PLM 的 `Product.product_code`。如果只修状态，部分 standalone `operation` 行仍会因为找不到 Product 而无法提交。

### 14.4 本次代码修正

修改 `plm-server/src/main/java/com/yuewei/plm/module/importexport/service/impl/MasterDataImportExportServiceImpl.java`：

1. 历史状态 `active/enabled/valid/current` 归一化：
   - Process -> `confirmed`
   - Product -> `archived`
   - Inventory -> `available`
2. 增加中文状态别名，例如 `已确认`、`已锁定`、`已归档`。
3. 允许 `operation_master` 作为 Process 类型。
4. standalone `operation/operation_master/route_template` 不强制绑定 Product。
5. Process 提交时 Product 不存在不再触发空指针；原始编码保留到 `product_specific_code`，用于追溯。

修改 `plm-server/src/test/java/com/yuewei/plm/module/importexport/service/impl/MasterDataImportExportServiceImplTest.java`：
