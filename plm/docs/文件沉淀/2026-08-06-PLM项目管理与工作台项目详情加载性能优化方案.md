# PLM 项目管理与工作台项目详情加载性能优化方案

日期：2026-08-06

## 一、问题背景

当前用户反馈两个入口加载慢：

1. 点击进入「项目管理」页面时，每次都要等待较久。
2. 从「工作台」打开对应项目的项目详情时，也需要等待较久。

本方案先基于现有代码静态排查形成优化设计，不直接改代码。后续实施时建议先加埋点确认各接口耗时，再按阶段改造。

## 二、现状排查结论

### 1. 项目管理首屏一次请求过多

前端入口：`plm-web/src/views/project/ProjectCenterView.vue`

现状：

- `onMounted(loadData)` 进入项目管理页即加载全量业务数据。
- `loadData` 中并发请求：
  - 全部项目：`getProjects({ page: 1, size: 200 })`
  - released 项目：`getProjects({ page: 1, size: 200, status: 'released' })`
  - archived 项目：`getProjects({ page: 1, size: 200, status: 'archived' })`
  - released 产品线多页：`loadAllProjectPages(...)`
  - archived 产品线多页：`loadAllProjectPages(...)`
  - archived 新型号/SKU 多页：`loadAllProjectPages(...)`
- `loadAllProjectPages` 最多循环 30 页，每页 200 条。即使用户只看「进行中」，也会预先加载归档数据。

影响：

- 首屏被归档数据拖慢。
- 数据量越大，页面每次进入越慢。
- 多个列表结果合并到 `rows` 后，前端还需要做 computed 过滤、映射和表格渲染。

### 2. 项目详情重复请求 timeline

前端入口：`ProjectCenterView.vue` 的 `openDetail(row)`

现状：

- 打开详情先调用 `getProjectDetail(row.productId)`。
- 后端 `ProjectServiceImpl.getDetail` 内部已经组装 `.timeline(timelineService.getTimeline(projectId))`。
- 前端随后又单独调用 `getProjectTimeline(row.productId)`。

影响：

- 同一个项目详情打开时，timeline 至少查两遍。
- 如果 timeline 查询慢，重复查询会直接放大等待时间。

### 3. timeline 查询存在按节点 N 次 count

后端入口：`plm-server/src/main/java/com/yuewei/plm/module/project/service/impl/TimelineServiceImpl.java`

现状：

- `getTimeline` 获取流程节点定义后，`definitions.stream().map(...)` 逐个节点转 VO。
- 每个节点都会调用 `countDocuments(productId, nodeCode)`。
- `countDocuments` 对 `plm_attachment` 执行一次 `selectCount`。

影响：

- 一个项目如果有 18-22 个流程节点，就会产生 18-22 次附件 count 查询。
- `getProjectDetail` 调一次 timeline，前端又调一次 timeline，相当于打开详情可能触发 36-44 次附件 count。
- 工作台进度弹窗也会调用 `getProjectTimeline`，同样受影响。

### 4. 详情弹窗内多个重型面板提前挂载

前端入口：`ProjectCenterView.vue` 详情弹窗模板

现状：

- `ProjectBomPanel`、`ProjectProcessRoutePanel`、`ProjectCostPanel` 多处使用 `v-show`。
- 这些子组件内部有 `watch(..., { immediate: true })` 或 `onMounted(load)`。
- 只要详情弹窗渲染，隐藏 tab 下的组件也可能提前请求：
  - BOM：`getProjectBoms`、`getProjectProcessRoutes`
  - 工艺路线：`getProjectProcessRoutes`、模板、工序库
  - 成本：`getProjectCostSummary`、`getProjectCostItems`

影响：

- 用户只是打开详情看当前节点或基础信息，也会提前加载 BOM、工艺、成本等数据。
- 网络并发多，后端查询多，弹窗首屏体感慢。

### 5. 后端列表查询仍有优化空间

后端入口：`ProjectServiceImpl.pageProducts`

现状：

- 列表查询使用 `selectPage`。
- 查询后批量补 ownerName、moldCodes，整体比 N+1 好，但项目管理页一次发多组列表请求，仍会放大后端压力。
- 项目列表当前没有返回专门的轻量统计接口，前端为了多个 tab 数量和归档视图一次拉很多数据。

影响：

- 页面首屏为了“各视图数据齐全”牺牲了进入速度。
- 列表数据量增长后，分页查询、排序和前端合并都会更重。

## 三、优化目标

### 体验目标

- 进入「项目管理」首屏优先展示当前 tab，目标首屏接口完成时间控制在 1 秒内。
- 从「工作台」打开项目详情，先展示基础信息和当前节点，目标 1 秒内可见主体内容。
- BOM、工艺路线、成本、资料等重型区块切到对应 tab 时再加载。

### 技术目标

- 减少项目管理首屏接口数量。
- 消除详情打开时 timeline 重复请求。
- 将 timeline 附件数统计从 N 次 count 改成一次 group by。
- 为项目列表和附件统计补齐更贴近查询条件的索引。
- 增加前端轻量缓存，避免工作台已查过的数据跳到项目管理后立刻重复查。

## 四、整体方案

### 阶段 P0：先加性能观测

目的：先确认瓶颈，不靠感觉改。

前端：

- 在 request 拦截器中记录接口耗时，仅开发环境输出。
- 对这些接口重点观察：
  - `GET /api/v1/projects`
  - `GET /api/v1/workbench/projects/in-progress`
  - `GET /api/v1/projects/{projectId}`
  - `GET /api/v1/projects/{projectId}/timeline`
  - `GET /api/v1/projects/{projectId}/boms`
  - `GET /api/v1/projects/{projectId}/process-routes`
  - `GET /api/v1/projects/{projectId}/cost-summary`
  - `GET /api/v1/projects/{projectId}/cost-items`

后端：

- 增加接口耗时日志，至少覆盖 controller 方法或使用 Spring interceptor。
- 对慢接口开启 SQL 日志或临时打印关键查询耗时。

验收：

- 能清楚看到项目管理首屏发了几个接口、每个接口耗时多少。
- 能清楚看到项目详情打开共触发几个接口，以及 timeline 内附件 count 的总耗时。

### 阶段 P1：项目管理首屏只加载当前视图

改造点：`ProjectCenterView.vue`

当前 `loadData` 一次拉全部项目和归档多页，应改为按当前 tag 加载：

- 默认进入 `tab=in_progress` 时，只请求：
  - `getProjects({ page: currentPage, size: pageSize, status: in_progress 对应条件 })`
  - 或继续用 `getWorkbenchInProgressProjects`
- 切换到「全部项目」时再请求全部项目。
- 切换到「已归档产品」时再请求 archived product_line。
- 切换到「已归档 SKU」时再请求 archived model_variant/sku。
- 切换到「已停止」时再请求 abandoned/archived + abandon 标识对应数据。

关键设计：

- 引入 `projectListState`，按视图 key 缓存：
  - `rows`
  - `page`
  - `size`
  - `total`
  - `loaded`
  - `loading`
- 搜索 keyword 变化时只刷新当前视图。
- 不再使用 `loadAllProjectPages` 预取最多 30 页。
- 页面数量展示从当前已加载 rows 改为后端分页 total。

预期收益：

- 项目管理首屏接口从最多十几个请求降到 1 个请求。
- 大量归档数据不再阻塞进行中列表展示。

### 阶段 P2：详情打开拆成轻详情 + 懒加载 tab

改造点：`ProjectCenterView.vue`

当前 `openDetail` 串行执行：

1. `getProjectDetail`
2. `getProductPresentation`
3. `getProjectTimeline`

建议改为：

- 弹窗立即打开，先用列表 row 渲染骨架和基础字段。
- 首屏只加载：
  - `getProjectSummary` 或新增 `getProjectDetailLite`
  - `getProjectTimeline`
- 如果 `getProjectDetail` 已包含 timeline，则前端不要再调用 `getProjectTimeline`。
- 更推荐后端拆接口：
  - `GET /projects/{id}/detail-lite`：基础字段、状态、成本摘要可选，不含 timeline。
  - `GET /projects/{id}/timeline`：只负责流程。
  - `GET /projects/{id}/detail-full` 或保留旧 `/projects/{id}`：兼容旧页面。

详情 tab 懒加载：

- 把重型组件从 `v-show` 改成 `v-if="activeDetailSection === 'xxx'"`。
- 已加载过的 tab 保持 `loadedSections` 标记，避免来回切换重复请求。
- 当前节点、基础信息保持首屏加载；BOM、工艺、成本、资料切换后再加载。

建议规则：

- `current_node`：随 timeline 加载。
- `basic`：使用列表 row + lite detail。
- `bom_manage` / `bom`：切 tab 后加载 `ProjectBomPanel`。
- `process_detail` / `process`：切 tab 后加载 `ProjectProcessRoutePanel`。
- `cost`：切 tab 后加载 `ProjectCostPanel`。
- `materials` / `production_docs`：切 tab 后加载附件列表。

预期收益：

- 打开项目详情时首屏接口减少。
- 用户未看的 BOM、工艺、成本不再抢首屏时间。
- 从工作台跳转到项目详情时可以更快看到项目主体。

### 阶段 P3：后端 timeline 附件数批量统计

改造点：`TimelineServiceImpl`

当前每个节点调用一次：

```java
attachmentRepository.selectCount(
    owner_object_type = Product,
    owner_object_id = productId,
    timeline_node_key = nodeCode,
    deleted_flag = 0
)
```

建议改为一次查询：

```sql
select timeline_node_key, count(*) as document_count
from plm_attachment
where owner_object_type = 'Product'
  and owner_object_id = :productId
  and deleted_flag = 0
  and timeline_node_key in (:nodeKeys)
group by timeline_node_key;
```

实现建议：

- 在 `AttachmentRepository` 增加 `countByProductAndTimelineNodes(productId, nodeKeys)`。
- 返回 `Map<String, Integer>`。
- `TimelineServiceImpl.getTimeline` 先批量查询 counts，再在 `toNodeVO` 中取 map。
- 保留空节点默认为 0。

预期收益：

- timeline 附件统计从 N 次 SQL 降为 1 次 SQL。
- 工作台进度弹窗和项目详情都会受益。

### 阶段 P4：消除详情接口重复 timeline

改造点：

- `ProjectServiceImpl.getDetail`
- `ProjectCenterView.vue/openDetail`

有两个可选方案：

方案 A：保守兼容

- 后端 `/projects/{id}` 继续返回 timeline。
- 前端 `openDetail` 如果 `projectDetail.timeline` 存在，直接使用它，不再额外调用 `getProjectTimeline`。
- 缺点：详情接口仍偏重。

方案 B：推荐

- 后端 `/projects/{id}` 默认不带 timeline，避免详情接口隐式重。
- 新增参数：`GET /projects/{id}?includeTimeline=true`。
- 前端项目详情明确并行请求 lite detail 和 timeline。
- 旧调用方如依赖 timeline，可临时使用 `includeTimeline=true` 迁移。

推荐先落地方案 A，风险最低；后续再演进到方案 B。

### 阶段 P5：项目管理列表接口服务端分页和统计

前端不应为拿 tab 数量或归档入口一次拉全量数据。建议后端提供：

```http
GET /api/v1/projects/metrics
```

返回：

```json
{
  "all": 1280,
  "inProgress": 37,
  "archivedProduct": 215,
  "archivedSku": 980,
  "abandoned": 12
}
```

列表接口保持分页：

```http
GET /api/v1/projects?page=1&size=20&status=archived&productType=product_line&keyword=xxx
```

前端展示数量使用 metrics，不再靠已加载 rows 计算。

预期收益：

- 页面切 tab 时只请求当前页。
- 数量仍准确。
- 归档数据增长后页面不会越来越慢。

### 阶段 P6：数据库索引补强

已有索引：

- `plm_product(status)`
- `plm_product(parent_product_id)`
- `plm_product(status, lock_status) where deleted_flag = 0`
- `plm_attachment(owner_object_type, owner_object_id, timeline_node_key, deleted_flag)`

建议新增或调整：

```sql
create index if not exists idx_plm_product_project_list
    on plm_product (status, product_type, updated_at desc)
    where deleted_flag = 0;

create index if not exists idx_plm_product_project_type_updated
    on plm_product (product_type, updated_at desc)
    where deleted_flag = 0;

create index if not exists idx_plm_attachment_product_node_active
    on plm_attachment (owner_object_id, timeline_node_key)
    where owner_object_type = 'Product' and deleted_flag = 0;
```

说明：

- 项目管理列表高频条件是 `status + productType + updatedAt desc`。
- timeline 附件统计高频条件固定为 Product + productId + nodeKey + deletedFlag。
- 索引需以真实 PostgreSQL `EXPLAIN ANALYZE` 为准，避免重复和无效索引。

## 五、推荐实施顺序

### 第 1 天：快速体感优化

1. 加前端接口耗时日志和后端接口耗时日志。
2. 项目管理 `loadData` 改为当前 tab 分页加载。
3. 移除 `loadAllProjectPages` 首屏预加载。
4. 详情弹窗重型 tab 改懒加载。
5. 前端复用 `getProjectDetail` 返回的 timeline，避免重复 `getProjectTimeline`。

验收重点：

- 进入项目管理默认只发 1 个列表接口。
- 打开详情首屏不主动请求 BOM、工艺、成本接口。
- 打开详情不重复请求 timeline。

### 第 2 天：后端根因优化

1. `TimelineServiceImpl` 附件数改批量 group by。
2. 新增 timeline 批量统计 repository 方法和单元测试。
3. 增加项目列表索引迁移。
4. 对 `/projects`、`/projects/{id}/timeline` 跑 SQL explain。

验收重点：

- timeline 接口附件统计 SQL 从 N 次降为 1 次。
- 项目详情打开耗时明显下降。
- 工作台项目进度弹窗打开更快。

### 第 3 天：接口形态优化

1. 新增 `/projects/metrics`。
2. 前端 tab 数量改用 metrics。
3. 设计 `/projects/{id}/detail-lite` 或 `includeTimeline` 参数。
4. 逐步迁移旧详情调用。

验收重点：

- 项目管理数量准确。
- 归档数据很多时，进行中列表首屏不受影响。
- 旧入口无兼容性问题。

## 六、验收指标

建议记录优化前后数据：

| 场景 | 优化前记录 | 优化目标 |
| --- | --- | --- |
| 进入项目管理默认页 | 接口数、总耗时 | 1 个列表接口，1 秒内可见 |
| 切换已归档产品 | 接口数、总耗时 | 只请求当前页 |
| 工作台打开进度弹窗 | timeline 耗时 | 附件统计 1 次 SQL |
| 工作台跳项目详情 | 首屏接口数 | 不重复 timeline，不加载隐藏 tab |
| 打开 BOM tab | BOM/工艺接口耗时 | 仅切 tab 时加载 |
| 打开成本 tab | 成本接口耗时 | 仅切 tab 时加载 |

## 七、风险与兼容

1. `v-show` 改 `v-if` 后，组件切换会销毁内部状态。需要用 `loadedSections` 或 keep-alive 风格缓存避免用户编辑中丢状态。
2. `/projects/{id}` 是否保留 timeline 要谨慎。第一阶段建议前端先复用已有 timeline 字段，不急着改后端契约。
3. 项目管理数量如果从前端 rows 计算改为后端 metrics，需要确认「已停止」的业务口径，是独立 status 还是 archived + abandonedAt。
4. 索引新增前要检查现网数据量和已有索引，避免重复索引增加写入成本。
5. 工作台跳转依赖 query：`/projects?tab=in_progress&productId=xxx&section=xxx`，项目管理懒加载后要保证目标项目可被单独 summary/detail 查到，不依赖当前页刚好包含该项目。

## 八、建议最终改造清单

前端：

- `ProjectCenterView.vue`
  - `loadData` 拆成 `loadCurrentProjectView`
  - 删除首屏 `loadAllProjectPages`
  - 增加按 tab 缓存的分页状态
  - `openDetail` 避免重复 timeline
  - 详情重型 tab 懒加载
  - 支持 query productId 目标项目不在当前页时单独查 summary/detail
- `DashboardView.vue`
  - 工作台跳详情时可携带已知 row 信息或使用轻缓存
  - 进度弹窗 timeline 可短时缓存，关闭后跳详情时复用
- 子组件
  - `ProjectBomPanel`
  - `ProjectProcessRoutePanel`
  - `ProjectCostPanel`
  - `TimelineAttachmentPanel`
  - 增加“首次显示才 load”的触发方式

后端：

- `TimelineServiceImpl`
  - 附件数批量统计
- `AttachmentRepository`
  - 增加按 productId + nodeKeys group by count
- `ProjectServiceImpl`
  - 详情接口去重 timeline 或支持 include 参数
  - 项目列表保持分页轻量化
- `ProjectController`
  - 新增 metrics 或 detail-lite 接口
- migration
  - 新增项目列表组合索引
  - 新增附件节点统计局部索引

## 九、结论

本次慢加载主要不是单点 bug，而是页面加载策略和 timeline 查询方式叠加导致：

- 项目管理首屏加载了用户暂时不看的大量数据。
- 项目详情重复加载 timeline。
- timeline 内部按节点逐条 count 附件。
- 详情隐藏 tab 的重型组件提前请求数据。

推荐先做 P1/P2/P4 的前端体感优化，再做 P3/P6 的后端根因优化。这样能最快让用户感觉“打开快了”，同时避免后续数据量继续增长后再次变慢。
