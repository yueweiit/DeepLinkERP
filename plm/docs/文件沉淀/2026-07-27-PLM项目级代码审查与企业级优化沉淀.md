## 2. 总体结论

当前项目处于“核心链路可联调的 MVP 中期”，尚未达到企业级生产可上线标准。

亮点：

- 技术栈方向符合规划：Vue 3 + Spring Boot + PostgreSQL + Docker。
- `/api/v1` 前缀基本落地，`ResponseVO`、`PageVO`、Flyway、操作日志、部分发布门禁已经有雏形。
- 项目时间轴、BOM、工艺、附件、发布门禁等核心闭环已有真实接口接入。

主要短板：

- 仓库污染严重：`git status --short` 统计 3083 条状态记录，其中约 2787 条集中在 `.codex_tmp`、日志、上传文件、构建产物、压缩包等污染路径。
- 权限只有认证，没有企业级授权：用户固定授予 `ROLE_ENGINEER`，前端权限和后端权限模型不闭环。
- 外部集成越界：钉钉、快递已经从“预留/草案”进入正式回调、创建对象、外发触发。
- 数据库迁移存在两套入口、schema 漂移、重复版本、JSON 类型不一致、FK/CHECK 约束不足。
- 前端仍有大量 `notConnected()`、运行时静态业务数据和字段默认值，部分页面会展示“看似真实但未由后端计算”的结果。
- 测试以 mock/文本契约为主，缺少真实 PostgreSQL、HTTP 契约、权限越权、并发版本和端到端验收测试。

企业级成熟度判断：

- 后端：MVP 中期，不能直接生产上线。
- 前端：C+ / 试点联调级。
- 数据治理：L2 到 L3 之间，偏 L2。
- 工程治理：可演示、可联调，但质量门禁和安全治理不足。

### P0-2 认证授权不满足企业级系统

证据：

- `plm-server/src/main/java/com/yuewei/plm/common/config/SecurityConfig.java:55-60`
- `plm-server/src/main/java/com/yuewei/plm/common/security/SimpleTokenAuthenticationFilter.java:56-60`
- `plm-server/src/main/java/com/yuewei/plm/module/auth/service/impl/InMemoryTokenSessionService.java:16-17`
- `plm-web/src/api/modules/auth.ts:47-49`
- `plm-web/src/router/index.ts:387-390`

问题：

后端认证开启时只校验 token，所有用户固定 `ROLE_ENGINEER`；认证关闭时 `/api/v1/**` 全放行。前端只从 `allPermissions` 推导 `['*']` 或 `[]`，无法表达 `dashboard:view`、`project:view`、`cost:view` 等细粒度权限。

理由：

PLM 包含图纸、BOM、成本、供应商、审批、附件下载等敏感资产。仅登录不授权，会产生横向越权和关键动作越权。

优化方式：

1. 后端落地 RBAC + 对象级权限：模块权限、项目归属、节点推进权限、成本字段权限。
2. 关键接口添加 `@PreAuthorize` 或服务层 `permissionService.require(...)`。
3. token/session 改 Redis 或 JWT + 撤销表，避免多实例失效。
4. 前端不要自行推导权限，使用后端返回的权限码。

建议实施文件：

- `SecurityConfig.java`
- `SimpleTokenAuthenticationFilter.java`
- `AuthServiceImpl.java`
- `SysUser` / role / permission repository
- `plm-web/src/api/modules/auth.ts`
- `plm-web/src/router/index.ts`

建议代码方向：

```java
auth.requestMatchers("/api/v1/health/**", "/api/v1/auth/login").permitAll();
auth.requestMatchers("/api/v1/**").authenticated();
auth.anyRequest().denyAll();
```

```ts
function toPermissions(user: BackendCurrentUser): string[] {
  return user.permissions || []
}
```

### P0-4 数据库迁移入口和 schema 漂移

证据：

- `docker-compose.yml:14-18` 使用 `plm-database/postgres/V1.0-V1.3` 初始化。
- `plm-server/src/main/resources/application.yml:11-15` 使用 classpath Flyway。
- `plm-database/postgres/V1.3__workflow_locking_alignment.sql` 与 `V1.3__workflow_locking_seed_data.sql` 版本重复。
- `V20260710_1000__m4_bom_process_attachment.sql:62,84` 将 `process_param_json` 定义为 `text`。
- `V20260718_1001__process_operation_business_code.sql:10-16` 使用 `process_param_json ->>` JSON 操作符。
- `plm-database/postgres/V1.0__init_schema.sql:4-5` 使用 schema `plm`，server Flyway 未声明 schema。

问题：

同一项目存在两套建库路径；不同路径下表 schema、字段类型和迁移历史可能不一致。`text ->>` 在 PostgreSQL 中会失败，重复 Flyway 版本会阻断迁移。

优化方式：

1. 统一迁移入口：推荐 compose 只启动空 PostgreSQL，由 `plm-server` Flyway 管理全部迁移。
2. 明确 schema：配置 `spring.flyway.schemas=plm`、`spring.flyway.default-schema=plm`，或脚本显式 schema 前缀。
3. 修复重复版本：`V1.3__workflow_locking_seed_data.sql` 改为 `V1.4__...`。
4. `process_param_json` 统一为 `jsonb`，补类型转换迁移。

建议迁移草案：

```sql
alter table plm_process
  alter column process_param_json type jsonb
  using case
    when process_param_json is null or btrim(process_param_json) = '' then null
    else process_param_json::jsonb
  end;
```

## 4. P1 上线前原则上修复

### P1-1 前端大量业务入口未接真实接口

证据：

- `plm-web/src/api/modules/customer.ts:5-18`
- `plm-web/src/api/modules/product.ts:87-105`
- `plm-web/src/api/modules/foundation.ts`
- `plm-web/src/api/modules/system.ts`
- `plm-web/src/api/notConnected.ts:8-10`

问题：

客户、系统、库存、报表、产品详情、编辑、发布、冻结等入口直接 `notConnected()`。这不是假数据，但属于运行时断路。部分页面吞掉异常后展示空列表，会让用户误以为没有数据。

优化方式：

1. 已有后端接口则接入真实 `/api/v1/...`。
2. 未有后端接口则从路由/菜单隐藏，显示“未开放”而不是业务空态。
3. `mockResolve` 和 `src/mock/*` 移到测试夹具目录，生产构建禁止 import。

### P1-2 前端补默认值导致看板和列表不可信

证据：

- `plm-web/src/api/modules/project.ts:299-315`
- `ProductList.vue`、`DashboardView.vue` 使用这些字段展示。

问题：

前端将后端未返回字段补为 `customerName:''`、`frozenFlag:false`、`estimatedCost:0`、`activeBomVersion:''`、固定门禁摘要。这会把未知数据包装成真实业务结果。

优化方式：

1. 后端 DTO 返回真实字段。
2. 前端 adapter 用 `null` / `unknown` 表示未知。
3. UI 对未知值显示“未计算/未接入”，不展示 0 或 false。

### P1-3 审批中心未形成闭环

证据：

- `WorkflowTemplateController.java:33` 任务列表固定空集合。
- `ApprovalTaskList.vue` 前端已有任务界面，但缺 approve/reject 动作闭环。

问题：

审批中心 UI 存在，但后端没有真实待办生成和审批动作。发起与确认分离的权限验收无法成立。

优化方式：

1. 后端从时间轴/工作流实例生成待办。
2. 提供 `POST /api/v1/approval-tasks/{id}/approve`、`reject`、`return`。
3. 强制 `initiator_user_id != confirmer_user_id`。
4. 审批动作记录 before/after 快照和操作日志。

### P1-4 BOM 生命周期日志和真实操作人不足

证据：

- `ProductBomWorkflowService.java:181-213`

问题：

BOM 冻结/发布写 `frozenBy/releasedBy = "system"`，未注入操作日志服务，缺少真实操作人。

优化方式：

1. Controller 将 `HttpServletRequest` 和当前用户传入 workflow service。
2. `freeze/publish/submitReview/recalculateCosts/copyVersion` 均写操作日志。
3. 日志包含业务对象、动作、操作者、IP、requestId、before/after snapshot。

### P1-5 导入导出绕过状态机且不可多实例

证据：

- `MasterDataImportExportServiceImpl.java:70-81`
- `MasterDataImportExportServiceImpl.java:527-553`

问题：

导入允许 `product_type=sku`，模板示例可导入 `archived/released`，并且预览 session 存内存。多实例部署、重启、批量历史导入均不可靠。

优化方式：

1. 导入只落草案，发布/冻结走生命周期服务。
2. 禁止把 SKU 当根对象导入；如保留 `product_type=sku`，必须明确只是 Product 子版本视图。
3. 预览 session 存 Redis 或 DB。
4. 超过 100 行或大文件改异步任务 + 轮询/SSE。

### P1-6 数据约束不足

证据：

- `V20260718_1100__bom_workbench_route_cost_import.sql`
- `V20260720_1000__dingtalk_model_variant_orders.sql`
- `V20260723_1100__attachment_preview_and_mold_transfer_express.sql`
- `V20260724_1200__workflow_template_editing.sql`

问题：

新增多张业务表缺少 FK；大量状态/flag 字段为自由文本或 integer，无 CHECK 约束；软删除唯一约束不统一。

优化方式：

1. 核心关联补 FK。
2. 状态字段补 CHECK 或集中字典校验。
3. 唯一约束改为 partial unique index：`where deleted_flag = 0`。
4. 加孤儿数据审计 SQL 和迁移 contract test。

### P1-7 性能和数据流转效率问题

证据：

- `OrderServiceImpl.java:34-49` 订单全量查出后内存过滤分页。
- `WorkflowTemplateServiceImpl.java` 列表后逐个查节点，存在 N+1。
- `ProcessCenterServiceImpl.java` 工艺中心全量装载后内存聚合。
- `TimelineAttachmentPanel.vue` 固定 `page:1,size:100`。
- `SkuView.vue` 并发下载前 40 个附件缩略图。

优化方式：

1. 搜索、分页、排序下推数据库。
2. 批量查询后按 ID 分组。
3. 报表和中心页由后端聚合 API 提供分页和指标口径。
4. 附件缩略图由后端提供预览 URL/metadata，前端懒加载。

## 5. P2 可持续优化

### P2-1 文件上传下载生产化不足

证据：

- `plm-web/src/utils/file.ts:1` 前端允许 200MB。
- `plm-web/nginx.conf:8-14` 未配置 `client_max_body_size`。
- API 规范要求文件下载生成 5 分钟临时签名 URL，当前本地存储为直接资源下载。

优化方式：

1. nginx 配置 `client_max_body_size 200m`、上传超时和明确错误页。
2. 使用 MinIO/S3，下载返回短期签名 URL。
3. 上传做 MIME 嗅探、病毒扫描、文件名安全、访问权限校验。

### P2-2 代码体量过大，扩展成本偏高

证据：

- `ProjectCenterView.vue` 约 114KB。
- `DashboardView.vue` 约 57KB。
- `ProcessCenterView.vue` 约 46KB。
- `MasterDataImportExportServiceImpl.java`、`JdbcInventorySupplierService.java`、`ProcessRouteServiceImpl.java` 等服务较大。

优化方式：

1. 前端按业务区块拆 composable、组件和 adapter。
2. 后端按 parser、validator、writer、query service 拆分。
3. 保持接口层和领域服务边界，不做无说明大重构。

### P2-3 测试门禁不足

问题：

当前测试大量使用 mock 或 SQL 文本包含检查，缺少真实数据库、HTTP 契约、权限越权、并发冲突和端到端验收。

优化方式：

1. 后端引入 Testcontainers PostgreSQL。
2. 前后端共享 OpenAPI/Schema，做契约测试。
3. 核心链路覆盖：登录、权限、产品创建、时间轴推进、附件上传下载、BOM 冻结发布、导入提交。
4. CI 必跑后端 `mvn test`、前端 `npm run type-check`、`npm run test:run`、`npm run build`。
