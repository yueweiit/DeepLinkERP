# 2026-08-03 PLM 新型号工艺路线继承、新增与编码口径沉淀

## 1. 任务理解

本次只沉淀业务判断口径和后续实施建议，不修改业务代码。

当前要澄清的问题是：一个新型号创建后，系统如何判断某条工艺路线应该作为“继承自产品线的路线”继续承载关联 SKU，还是应该作为“新建工艺路线”单独存在。

按本次确认后的理解：

- 新型号创建时，先自动继承对应产品线 / 上级产品的工艺路线。
- 继承动作产生的是新型号自己的工艺路线副本，但业务含义仍然是“继承路线”，不是用户新增路线。
- 如果新型号没有额外创建工艺路线，就不应该认为它有“新的路线”；SKU / 颜色应关联到对应的继承路线下。
- 如果用户在新型号下后续手工新增了一条工艺路线，才判断为“新建工艺路线”。
- 继承路线后续被编辑，可以标记为“继承已修改”，但它仍然来源于继承路线，不等同于新建路线。
- 工艺路线编码和工序业务编码需要回到 `2026-07-27` 编码方案的规则，不能继续按当前错误逻辑拼接。

## 4. 当前系统实际逻辑

### 4.1 新型号创建时先继承工艺路线

当前新型号创建链路中，`ProductServiceImpl.create()` 会在创建新型号后调用工艺路线继承服务：

```text
ProductServiceImpl.create()
  -> ProcessRouteInheritanceService.inheritLatestReleasedFormalBomRoutesByColors(...)
```

也就是说，当前系统的默认逻辑是：

```text
新型号创建
  -> 自动继承对应产品线 / 上级产品的已发布正式 BOM 工艺路线
  -> 再处理 BOM 继承
```

这个方向和目标业务口径是一致的：新型号不是一开始就要求用户手工建路线，而是先继承。

### 4.2 当前继承方式是复制路线到目标产品

当前继承服务会把父产品路线复制成目标新型号自己的路线记录：

- 新路线记录会有新的 `process_id`。
- 新路线记录的 `product_id` 会指向目标新型号。
- 路线、工序、BOM 路线颜色等信息会按目标产品上下文复制。

因此从数据库记录角度看，继承后确实多了一条 `plm_process` 路线记录；但从业务含义上看，这条记录不是“用户新增路线”，而是“系统继承路线”。

这里需要区分两个概念：

| 角度 | 结论 |
| --- | --- |
| 数据库记录 | 继承后会复制出目标产品自己的路线记录，有新 `process_id` |
| 业务分类 | 这条路线仍应判断为继承路线，不应判断为新增路线 |

### 4.3 当前 SKU 关联主要按路线颜色关系匹配

当前工艺中心里，路线关联 SKU 的主要逻辑是：

```text
路线 -> active BOM route -> route colors -> 匹配 Product/SKU 的 color
```

也就是当前系统是按工艺路线绑定的颜色关系，再去找对应颜色的 SKU / Product 明细。

这个逻辑可以用于判断“这条路线适用于哪些颜色 / SKU”，但还不够精确。目标口径里，最终应优先用成品编码作为 SKU 精确关联主键，颜色关系作为路线适用范围和旧数据兼容依据。

### 4.4 当前继承来源标识不够稳定

当前系统能推断部分继承信息，例如通过 `process_param_json.sourceProductCode` 判断 `templateSource = inherited`。但从当前理解看，还缺少稳定、明确的来源字段：

- 来源产品 ID。
- 来源路线 ID。
- 继承批次 ID。
- 继承类型。
- 继承时间。
- 路线来源分类。

如果只靠是否有新 `process_id` 判断，会把继承复制出的路线误判为新增路线。

### 4.5 当前编码逻辑仍有偏差

参考 `2026-07-27` 编码方案，目标工序业务编码应为：

```text
N + 产品特定编码 + 工序编码 + 手机型号编码 + 颜色编码
```

示例：

```text
产品线通用路线：NFA1020000000
新型号半成品：NFA1020129101
新型号成品：NFA4030129101
```

当前路线命名中存在手机型号占位或继承来源 token 的逻辑，例如 `0000`、`INH-R{sourceProcessId}` 等，但这主要影响路线编码，不等于工序业务编码。工序业务编码不能继续复制产品线的 `0000` 结果，也不能用材料 / 状态尾段替代手机型号编码和颜色编码。

## 5. 目标业务口径

### 5.1 先继承，再判断是否新增

新型号的工艺路线判断顺序应为：

```text
1. 新型号创建时，系统自动继承对应产品线 / 上级产品路线。
2. 继承路线作为该新型号的默认工艺路线。
3. 如果没有用户手工新增路线，则该新型号没有“新增路线”。
4. SKU / 颜色默认关联到对应继承路线。
5. 如果用户后续创建了一条新的工艺路线，才产生“新增路线”。
6. 如果用户编辑继承路线，则路线状态变成“继承已修改”，但来源仍是继承。
```

一句话口径：

```text
新型号默认有继承路线；只有用户额外创建，才叫新建路线。
```

### 5.2 继承路线不是产品线原路线，也不是新增路线

继承后的路线在新型号下有自己的记录，是为了让新型号后续可以单独维护参数、工序、颜色和版本。但业务分类上，它仍然保留来源关系。

推荐分类：

| 分类 | 含义 | 判断口径 |
| --- | --- | --- |
| `inherited_base` | 继承基线 | 系统从父产品 / 产品线复制而来，尚未发生业务差异 |
| `inherited_modified` | 继承已修改 | 来源仍是继承路线，但新型号下发生过工序、参数、颜色或版本差异 |
| `new_route` | 新建路线 | 用户在新型号下主动新增，没有来源路线 |

不建议使用“是否有新 `process_id`”判断新增路线，因为继承复制也会产生新 `process_id`。

## 6. 路线分类判断逻辑

建议后续按以下优先级判断路线来源：

```text
如果 route_origin = manual，则为新建路线。
否则如果 source_process_id 有值，则为继承路线。
否则如果 inheritance_batch_id 有值，则为继承路线。
否则如果 process_param_json 中存在稳定继承来源字段，则为继承路线。
否则按历史数据兜底规则判断。
```

### 6.1 推荐元数据

后续实施时，建议在路线记录或 `process_param_json` 中保留以下来源信息：

| 字段 | 含义 |
| --- | --- |
| `route_origin` | 路线来源：`inherited` / `manual` / `imported` |
| `source_product_id` | 来源产品 ID |
| `source_process_id` | 来源工艺路线 ID |
| `inheritance_batch_id` | 一次新型号创建触发的继承批次 |
| `inheritance_type` | 继承类型，例如产品线继承、新型号复制、颜色继承 |
| `inherited_at` | 继承时间 |
| `inherited_by` | 继承动作触发人，系统自动时可为 `system` |
| `difference_flag` | 是否相对来源路线发生差异 |
| `difference_summary` | 差异摘要 |

### 6.2 差异判断

继承路线是否变成“继承已修改”，建议看以下内容是否相对来源路线发生变化：

- 工序新增 / 删除。
- 工序顺序调整。
- 工序库编码变更。
- 工艺参数变更。
- 质量要求变更。
- 适用颜色 / SKU 范围变更。
- 关键物料或 BOM 路线关系变更。
- 路线发布版本变更。

只要来源关系还在，即使发生差异，也应归为 `inherited_modified`，不是 `new_route`。

## 7. SKU 关联口径

### 7.1 当前可接受口径

在现有系统未完成成品编码改造前，SKU 关联可继续兼容当前逻辑：

```text
工艺路线 -> BOM route -> route colors -> 匹配 Product/SKU 的 color
```

这个逻辑适合回答：

```text
这条路线适用于哪些颜色 / SKU？
```

### 7.2 目标精确口径

后续应逐步调整为：

```text
最终工序 4030 生成成品编码
  -> 成品编码写入 Product 下 SKU / 颜色明细
  -> 工艺路线关联 SKU 时优先使用 finished_product_code
  -> 颜色 / BOM route 关系作为适用范围和旧数据兼容
```

成品编码公式：

```text
成品编码 = N + 产品特定编码 + 4030 + 手机型号编码 + 颜色编码
```

示例：

```text
NFA4030129101
```

### 7.3 继承路线下 SKU 的归属判断

新型号继承路线后，SKU / 颜色应这样归属：

| 场景 | SKU 归属 |
| --- | --- |
| 新型号只继承了产品线路线，没有新增路线 | SKU 关联到对应继承路线 |
| 新型号继承路线后修改了部分参数 | SKU 仍关联到这条继承已修改路线 |
| 新型号新增了一条路线，并明确绑定某些颜色 / SKU | 被绑定的颜色 / SKU 关联到新建路线 |
| 新建路线没有绑定颜色 / SKU | 不应自动吞掉继承路线下的 SKU |
| 同一颜色 / SKU 同时命中多条有效路线 | 应按有效期、版本、状态或人工指定规则解决冲突 |

关键结论：

```text
不能因为新型号存在一条继承复制出来的路线，就把它当作新增路线。
也不能因为新型号后来有新增路线，就把所有 SKU 都自动迁走。
```

## 8. 工艺路线编码与工序编码目标规则

### 8.1 路线编码与工序业务编码要分开

路线编码用于识别一条工艺路线或路线版本；工序业务编码用于半成品 / 成品 / SKU 精确追溯。两者不能混用。

| 编码 | 作用 | 是否作为 SKU 精确关联主键 |
| --- | --- | --- |
| 工艺路线编码 | 标识路线、版本、来源和管理记录 | 否 |
| 工序业务编码 | 标识某道工序产出的半成品 / 成品状态 | 最终工序 `4030` 的编码是 |
| 成品编码 | `4030` 工序业务编码 | 是 |

### 8.2 产品线通用路线

产品线没有具体手机型号和颜色时，应使用占位：

```text
N + 产品特定编码 + 工序编码 + 0000 + 00
```

示例：

```text
NFA1020000000
```

含义：

- `FA`：产品特定编码。
- `1020`：工序编码。
- `0000`：手机型号占位。
- `00`：颜色占位。

这类编码用于通用路线模板和产品线层预览，不应作为正式 SKU 成品编码。

### 8.3 新型号继承路线

新型号继承产品线路线时：

- 继承工序顺序。
- 继承工序库编码。
- 继承工艺参数和质量要求。
- 不直接复制产品线的 `0000/00` 工序业务编码。
- 必须按新型号真实 `phone_model_code` 和颜色 `color_code` 重新生成工序业务编码。

示例：

```text
产品线工序：NFA1020000000
新型号工序：NFA1020129101
```

### 8.4 新型号最终工序与成品编码

最终工序固定按 `4030` 生成成品编码：

```text
N + 产品特定编码 + 4030 + 手机型号编码 + 颜色编码
```

示例：

```text
NFA4030129101
```

该编码应作为 SKU 精确关联、BOM 反查、工艺路线反查、库存成品反查的主键口径。

## 9. 当前差距

| 差距 | 影响 |
| --- | --- |
| 继承路线有新 `process_id`，但缺少稳定来源字段 | 容易把继承路线误判为新增路线 |
| `templateSource` 主要靠参数 JSON 推断，继承服务不一定稳定写入 | 前端展示和后端分类可能不一致 |
| `inheritedFrom`、`differenceOperationCount`、`hasDifferenceOperation` 等信息不完整 | 无法准确展示“继承基线 / 继承已修改 / 新建路线” |
| SKU 关联主要按颜色匹配 | 可判断适用范围，但不够精确 |
| 工序业务编码未完全按 `N + 产品特定编码 + 工序编码 + 手机型号编码 + 颜色编码` 生成 | 继承路线和 SKU 精确关联会继续错 |
| 产品线 `0000/00` 占位编码可能被复制到新型号 | 新型号半成品 / 成品编码不能反映真实机型和颜色 |
| 路线编码和工序业务编码职责混在一起 | 容易拿路线 code 去做 SKU 关联，导致口径混乱 |

## 10. 后续实施建议

本次不改代码，后续如果落地，建议按以下顺序实施：

1. 先补路线来源元数据，明确 `route_origin`、`source_process_id`、`source_product_id`、`inheritance_batch_id`。
2. 调整继承服务，复制路线时写入稳定来源信息。
3. 调整路线列表和详情展示，区分“继承路线”“继承已修改”“新建路线”。
4. 调整差异计算，能展示继承路线相对来源路线的工序、参数、颜色差异。
5. 调整工序业务编码生成，产品线路线使用 `0000/00`，新型号 / SKU 使用真实机型和颜色。
6. 调整最终工序 `4030` 的成品编码写入逻辑。
7. 调整 SKU 关联逻辑，优先使用成品编码，兼容当前颜色 / BOM route 关系。
8. 增加唯一性约束和冲突校验，避免同一成品编码归属多个 SKU 明细。
9. 补历史数据迁移脚本，先补来源关系和编码上下文，再做强约束。
10. 补单元测试和验收用例。

## 12. 待确认问题

后续真正改代码前，建议确认以下问题：

1. 新型号创建时，如果父产品有多条已发布路线，继承哪几条：全部继承，还是只继承默认路线。
2. 新建路线和继承路线同时适用于同一颜色 / SKU 时，优先级按版本、有效期、是否默认，还是人工指定。
3. 继承路线被修改后，是否需要保留和来源路线的差异快照。
4. 产品特定编码、手机型号编码、颜色编码的正式来源字段是否已经在 Product 中固定。
5. 历史数据中已经复制出的新型号路线，是否可以通过创建时间、产品关系、路线名称、参数 JSON 反推来源。
6. 路线编码本身是否需要重新设计，还是只调整工序业务编码和成品编码。

## 13. 本次结论

本次最终口径如下：

```text
新型号先继承工艺路线。
继承路线承载默认 SKU / 颜色关联。
没有手工新增路线，就没有新路线。
手工新增才是新建路线。
继承路线被修改，是继承已修改，不是新建路线。
新型号继承工序后，工序业务编码必须按真实手机型号编码和颜色编码重新生成。
最终工序 4030 生成的成品编码，才是 SKU 精确关联主键。
```
