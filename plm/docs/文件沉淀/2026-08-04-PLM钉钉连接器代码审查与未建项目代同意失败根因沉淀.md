# PLM 钉钉连接器代码审查与未建项目、代同意失败根因沉淀

日期：2026-08-04  
范围：只读审查，不修改业务代码  
审查对象：`plm-server/src/main/java/com/yuewei/plm/module/integration/dingtalk`、相关配置、数据库迁移、测试、调试日志和既有排查文档

## 1. 结论摘要

当前“钉钉连接器调试显示 HTTP 200，但工作台没有新项目”的最高概率原因不是网络不通，而是以下几类业务问题：

1. `approvalInstanceId` 或 `approvalNo` 被固定为测试值，例如 `111`，后端命中幂等记录后直接返回历史项目，不会新建项目。
2. 连接器调用的 `processCode` 与后端当前配置不一致。代码默认仍是旧的新型号流程编码；既有排查记录显示当前使用过另一套新流程编码。
3. 调用了错误的入口。正式审批回调入口是 `/api/v1/integrations/dingtalk/approval-callbacks`；`/model-variant-approvals` 是后端专用的直接接收/模拟入口，不等同于钉钉审批回调入口。
4. 请求虽然到达，但新型号建项目前置条件不满足，例如审批状态不是精确的 `approved`、父产品不是已发布产品线、父产品没有已确认的生产颜色、表单字段缺失。此类失败会回滚项目写入。

“之前代同意失败”的最高概率原因是：

1. PLM 出站中转接口把业务失败放在 `data.status=failed`，但 HTTP 状态和顶层 `code` 仍是成功，钉钉连接器只看 HTTP 200 就会误判。
2. `DINGTALK_OUTBOUND_ENDPOINT` 未配置时，PLM 代码主动走 `dry_run`，但完成逻辑只把 `failed` 视为失败，因此可能把“没有真正调用钉钉”记录成成功。
3. 当前官方审批客户端使用旧 `topapi/process/instance/execute` 入口，但请求字段使用了 `user_id`；旧接口文档使用的是 `actioner_userid`。这会导致代同意请求被钉钉拒绝。
4. 自动代同意使用固定 `autoApproverUserId`，同时在找不到匹配操作人时回退到第一个运行中的任务，可能拿到错误任务或使用没有权限的审批人。

因此，后续排查必须同时看：

- HTTP 状态；
- 顶层响应 `code/message`；
- `data.status`；
- `data.idempotentHit`；
- `data.projectId`；
- `data.errorCode/data.message`；
- PLM 数据库中的 `plm_integration_record`；
- 服务日志中的 `requestId`。

不能只看“调试返回 200”。

## 2. 实际链路

### 2.1 钉钉入站创建新型号项目

```text
钉钉审批连接器
  -> POST /api/v1/integrations/dingtalk/approval-callbacks
  -> DingTalkApprovalCallbackController
  -> DingTalkApprovalDispatchService
  -> 按 processCode 分发
  -> DingTalkModelVariantService.receive
  -> 校验审批状态、父产品、颜色决策、表单字段
  -> 创建 plm_product
  -> 创建 requirement form、颜色快照、集成记录
  -> 工作台查询 product_type=model_variant 的项目
```

### 2.2 PLM 完成运模后的代同意

```text
工作台确认 MODEL_VARIANT_MOLD_TRANSFER
  -> PLM 主事务完成项目归档
  -> afterCommit 触发 DingTalkProjectCompletionReturnService
  -> 从入站集成记录读取审批实例 ID 和 taskId
  -> taskId 缺失时调用 outboundEndpoint 查询运行中任务
  -> 调用 outboundEndpoint 的 action=agree
  -> DingTalkOutboundRelayService
  -> DingTalkOfficialApprovalClient
  -> 钉钉审批实例查询/审批任务同意
```

## 3. 未创建项目问题

### P0-1：固定或重复审批实例 ID 触发幂等返回

证据：

- `DingTalkModelVariantService.receive` 在最前面按 `source_system=dingtalk`、`integration_type=model_variant`、`external_instance_id` 查询已有记录。
- 找到记录后直接返回 `result(existing, true)`，不会再执行项目创建。
- `externalInstanceId(dto)` 优先使用 `approvalInstanceId`，为空才回退到 `dingTalkApprovalNo`。
- 既有排查文档记录过如下返回：

```json
{
  "data": {
    "projectId": 42,
    "status": "success",
    "idempotentHit": true
  }
}
```

- 同一份记录中，审批实例 ID 为固定值 `111`。

结论：

如果连接器每次都传 `111`、审批模板编号、流程编号，或者重复使用同一个真实审批实例 ID，PLM 会认为这是同一张审批的重复回调。此时 HTTP 200 和 `status=success` 都可能出现，但不会有新项目。

正确判断新建是否发生，应满足：

```text
data.status = success
data.idempotentHit = false
data.projectId = 新项目 ID
```

### P0-2：`processCode` 默认配置仍可能是旧模板

当前代码默认配置：

```yaml
model-variant-process-code: PROC-89949932-19DE-48EB-A20B-2595CB0F804D
```

分发代码使用精确字符串比较：

```java
if (properties.getModelVariantProcessCode().equals(dto.getProcessCode())) {
    return modelVariantService.receive(toModelVariant(dto));
}
```

既有排查文档记录当前新型号流程曾使用：

```text
PROC-BD65F530-F66F-46B9-8F72-0567DD68F60C
```

如果运行环境没有通过 `DINGTALK_MODEL_VARIANT_PROCESS_CODE` 覆盖默认值，连接器传入新模板编码时不会进入新型号分支。

注意：这里只能根据仓库配置和历史排查记录判断存在高风险，最终运行值必须从启动日志、容器环境变量或部署配置确认。

### P0-3：入口地址可能配置错

代码中同时存在三个容易混淆的入口：

| 入口 | 用途 |
| --- | --- |
| `/api/v1/integrations/dingtalk/approval-callbacks` | 正式的统一审批回调分发 |
| `/api/v1/integrations/dingtalk/model-variant-approvals` | 新型号专用直接接收接口，适合后端模拟或内部联调 |
| `/api/v1/integrations/dingtalk/outbound` | PLM 出站动作中转，包括查询 taskId、agree、cc |

历史文档已记录旧地址 `/api/v1/integrations/ding` 返回 401。连接器不能继续使用旧地址，也不能把入站审批回调配置到 outbound 地址。

### P0-4：新型号建项目前置条件严格，失败时不会留下成功入站记录

`DingTalkModelVariantService.receive` 的必要条件：

1. `approvalStatus` 必须精确等于 `approved`。
2. `parentProductId` 必须存在。
3. 父产品类型必须是 `product_line`。
4. 父产品状态必须是 `released`。
5. 父产品必须存在至少一个 `selected_flag=1、status=confirmed` 的生产颜色决策。
6. `model` 和 `tipo` 必须有值。
7. `parentProductId` 需要能转换为数字。

项目、完善表、颜色快照、入站集成记录是在同一个事务中连续写入的。任何一个前置校验或后续写入失败，事务会回滚，工作台不会出现新项目。

这类失败通常应返回 HTTP 400 或 500，而不是“HTTP 200 + 项目不存在”。如果调试平台显示 200，应优先确认它调用的是否是 outbound 中转接口，或是否实际命中了旧幂等记录。

### P0-5：历史日志确认过项目编码唯一键冲突

`plm-server/.codex_tmp/dingtalk-backend-8082.out.log` 在 2026-07-20 12:41:49 记录过：

```text
duplicate key value violates unique constraint "uk_plm_product_code"
Key (product_code)=(PRD-钉钉验收产品-0001) already exists.
```

调用栈落在 `DingTalkModelVariantService.receive` 创建产品处。

当前生成器使用 JVM 内存中的 `AtomicInteger`，然后再执行一次数据库计数检查。这个组合无法抵御多实例并发、并发请求、进程重启后的序号重用和检查后插入前的竞争。已有日志证明运行时曾发生过唯一键冲突。

## 4. 代同意失败问题

### P0-6：HTTP 200 包住了业务失败

`DingTalkOutboundRelayController` 无论 `relayService.handle(dto)` 返回成功还是失败，都执行：

```java
return ResponseVO.success(relayService.handle(dto), ...);
```

所以失败响应可能是：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "status": "failed",
    "externalStatus": "failed",
    "errorCode": "DINGTALK_AGREE_FAILED",
    "message": "..."
  }
}
```

测试 `DingTalkOutboundRelayControllerTest.receiveReturnsSuccessEnvelopeForBusinessFailedResult` 已经明确把这个行为固化下来。

结论：

钉钉连接器调试显示 200，只能说明 PLM 的 HTTP 层接收了请求；必须继续读取 `data.status`。如果连接器只按 HTTP 状态判断成功，代同意失败会被错误标记为成功。

### P0-7：未配置 `DINGTALK_OUTBOUND_ENDPOINT` 时，代同意实际上是 dry-run

当前配置默认值为空：

```yaml
outbound-endpoint: ${DINGTALK_OUTBOUND_ENDPOINT:}
```

`DingTalkOutboundApprovalClient.postOrDryRun` 在 endpoint 为空时直接返回：

```text
externalStatus = dry_run
```

并且不会调用任何远程接口。

`DingTalkProjectCompletionReturnService` 只通过 `externalStatus=failed` 判断出站失败；`dry_run` 会被当成非失败状态，最终写入 `processing_status=success`。之后同一项目再次完成时，已有成功记录会被幂等命中，不会自动再试真实钉钉调用。

这是一个高风险假成功路径：

```text
没有配置出站地址
  -> 没有调用钉钉
  -> 返回 dry_run
  -> PLM 保存 success
  -> 用户看到流程完成，但钉钉没有代同意
```

### P0-8：代同意请求字段与旧官方接口字段存在不一致

当前 `DingTalkOfficialApprovalClient.agreeTask` 使用：

```text
POST /topapi/process/instance/execute
```

请求字段包括：

```json
{
  "request": {
    "process_instance_id": "...",
    "task_id": "...",
    "user_id": "...",
    "result": "agree",
    "remark": "..."
  }
}
```

旧版钉钉审批任务执行接口的字段口径使用 `actioner_userid` 表示操作人，而不是当前代码中的 `user_id`。新版流程实例执行接口又采用不同的路径和请求结构。因此当前实现存在接口版本与字段契约不一致风险，不能只凭本地 Mockito 测试认为代同意可用。

这也是“能查到 taskId，但同意仍失败”的直接候选根因。

### P0-9：固定操作人和错误任务回退会导致无权限同意

当前默认配置包含固定操作人：

```yaml
auto-approver-user-id: ${DINGTALK_AUTO_APPROVER_USER_ID:02356802443226388318}
```

任务查询逻辑：

1. 优先寻找 `task_status=RUNNING` 且 `userid` 等于 `actionerUserId` 的任务。
2. 如果找不到匹配操作人，则回退到第一条 `RUNNING` 任务。

问题：

- 配置的用户必须是当前待办节点真正的审批人，不能只是企业内任意用户。
- 回退到第一条运行中任务可能选中其他审批人的任务。
- 之后仍使用固定 `actionerUserId` 发起同意，任务和操作人可能不匹配。

这种组合会造成钉钉返回权限、任务归属或状态错误。

### P1-10：查询 taskId 时吞掉了官方错误

`DingTalkProjectCompletionReturnService.lookupWorkflowTask` 对所有异常直接返回 `null`：

```java
try {
    return outboundClient.lookupWorkflowTask(payload);
} catch (Exception ignored) {
    return null;
}
```

最终只能看到“taskId 未保存，且兜底查询未返回 taskId”，看不到真正原因，例如：

- access token 获取失败；
- IP 白名单不通过；
- 审批实例不存在；
- 没有运行中的任务；
- 出站中转返回业务失败；
- 远程响应结构不符合预期。

这会明显增加排查时间，也使代同意失败看起来像连接器没有传 taskId。

### P1-11：官方响应缺少错误码时可能被误判为成功

`DingTalkOfficialApprovalClient.ensureSuccess` 的判断是：

```java
boolean success = code == null || "0".equals(String.valueOf(code));
```

也就是说，响应中没有 `errcode` 或 `code` 时会被当成成功。对于同意接口，这可能把空响应、代理错误响应或结构变化误判为成功。

## 5. 其他已发现问题

### P1-12：钉钉集成默认开启，token 为空时跳过鉴权

默认配置：

```yaml
enabled: ${DINGTALK_INTEGRATION_ENABLED:true}
callback-token: ${DINGTALK_CALLBACK_TOKEN:}
```

两个控制器在 token 为空时直接跳过校验。结果是：

- 外部任意请求都可以尝试触发入站建项；
- 外部任意请求都可以尝试触发出站查询或代同意；
- 测试配置容易被带到非测试环境。

正式环境应明确要求 token 或其他签名校验，不能把“未配置”当成“无需校验”。

### P1-13：产品线完成抄送目前明确未实现

`DingTalkOutboundRelayService.cc` 直接返回：

```text
DINGTALK_CC_NOT_IMPLEMENTED
```

所以产品线完成后的抄送不是“偶发失败”，而是当前代码明确没有连接官方消息接口。由于同样包在 HTTP 200 中，连接器也可能误显示为成功。

### P1-14：入站失败没有稳定的失败集成记录

新型号服务在项目创建完成后才插入 inbound `IntegrationRecord`。前置校验或项目插入失败时，事务回滚，数据库里通常不会留下本次失败请求的原始报文和错误原因。

这会导致：

- 无法通过集成记录定位失败请求；
- 无法重放原始报文；
- 只能依赖应用日志；
- 钉钉重复重试时缺少清晰的失败状态。

## 7. 建议的核验顺序

以下顺序用于下一轮联调，不代表本次已经修改：

### 第一步：确认连接器入站配置

逐项确认：

```text
URL = /api/v1/integrations/dingtalk/approval-callbacks
processCode = 当前实际审批模板编码
approvalInstanceId = 动态审批实例 ID
approvalNo = 动态审批编号
approvalStatus = approved
parentProductId = 已发布产品线 ID
tipo/model = 非空
```

每次测试必须生成新的真实审批实例，禁止继续使用 `111` 或其他固定值。

### 第二步：看响应体而不是只看 200

重点记录：

```text
code
message
data.projectId
data.status
data.idempotentHit
data.errorCode
data.message
```

若 `idempotentHit=true`，先查审批实例 ID 是否重复。  
若 `status=failed`，先按 `errorCode/message` 处理。  
若没有 `projectId`，不能判定工作台已创建项目。

### 第三步：查数据库

```sql
select
    integration_record_id,
    integration_type,
    external_instance_id,
    external_status,
    processing_status,
    project_id,
    process_code,
    direction,
    error_code,
    error_message,
    created_at
from plm_integration_record
where source_system = 'dingtalk'
order by integration_record_id desc
limit 20;
```

```sql
select
    product_id,
    product_code,
    product_name,
    product_type,
    status,
    source_instance_id,
    created_at
from plm_product
where source_system = 'dingtalk'
order by product_id desc
limit 20;
```

### 第四步：单独验证 outbound

先确认运行环境确实配置了：

```text
DINGTALK_OUTBOUND_ENDPOINT
DINGTALK_APP_KEY
DINGTALK_APP_SECRET
DINGTALK_AUTO_APPROVER_USER_ID
DINGTALK_CALLBACK_TOKEN
```

如果没有 `DINGTALK_OUTBOUND_ENDPOINT`，当前代码只能 dry-run，不能验证真实代同意。

调用 outbound 后必须检查：

```text
data.status
data.externalStatus
data.taskId
data.errorCode
data.message
```

### 第五步：对照钉钉官方实际接口响应

需要抓取并脱敏保存：

1. access token 响应；
2. 审批实例查询响应；
3. 运行中 tasks 数组；
4. 代同意请求 JSON；
5. 代同意响应 JSON；
6. 钉钉侧审批实例状态变化。

重点确认当前部署使用的是旧版 `topapi` 还是新版 `v1.0/workflow` 接口，并严格按对应版本的字段契约发送请求。

## 8. 修复优先级建议

### P0

1. 连接器必须传真实且唯一的审批实例 ID，禁止固定测试值。
2. 确认并统一当前真实 `processCode`，避免代码默认值与审批模板不一致。
3. 连接器按响应体业务状态判断成功，不能只按 HTTP 200。
4. 未配置 outbound endpoint 时不能将 dry-run 标记为真实成功。
5. 统一钉钉官方接口版本和字段契约，特别是操作人字段、taskId 类型和请求包结构。
6. 代同意必须校验任务归属和操作人权限，不能无条件回退到第一条运行中任务。

### P1

1. 保留 taskId 查询和官方调用的原始错误摘要。
2. 入站请求先落原始报文和处理中状态，再执行建项，失败时保留可重放记录。
3. 生产环境默认关闭或强制配置鉴权 token。
4. 增加真实 HTTP 契约测试和脱敏回放测试。
5. 修复产品编码生成的并发唯一性问题。
6. 明确产品线完成抄送是否实现，未实现时不得返回业务成功。

## 9. 最终判断

当前最符合用户描述的组合是：

```text
连接器传入固定/重复 approvalInstanceId
  -> PLM 命中历史 IntegrationRecord
  -> 返回 HTTP 200、code=0、status=success、idempotentHit=true
  -> 没有新建 Product
```

代同意失败则最符合以下组合：

```text
连接器只看 HTTP 200
  -> 忽略 data.status=failed
```

或：

```text
没有配置 outboundEndpoint
  -> PLM 走 dry_run
  -> PLM 误记录 success
  -> 实际没有调用钉钉
```
