# PLM 工艺路线产品工序编码与基础工序编码展示一致性修复方案

日期：2026-08-11  
状态：方案沉淀，暂不修改业务代码  
任务来源：工艺路线编辑弹窗中，上方“产品工序编码”和下方“节点配置核对表”的“工序编码”显示不一致，用户疑惑上下编码为什么不同。

## 1. 任务理解

当前截图中：

- 上方“产品工序编码”显示 `NDN10101291`。
- 下方“节点配置核对表”的“工序编码”显示 `1010`。

从现有代码看，这不是同一字段显示错乱，而是两个不同业务层级的编码：

- `businessOperationCode`：产品工序编码，带产品特定编码、基础工序编码、机型编码、颜色编码等上下文。
- `operationCraftCode`：基础工序编码，表示该道工序本身，如 `1010`、`1020`、`4030`。

当前问题本质是前端展示语义不清：核对表只显示“工序编码”，没有同时展示“产品工序编码”和“基础工序编码”，导致用户误以为上下应该一致。

## 2. 所属 PLM 业务链路

- 新产品线：产品线建档后维护工艺路线、确认投产工序。
- 新型号线：继承或新增型号工艺路线，按产品特定编码、机型编码生成产品工序编码。
- 核心对象：`Product`、`Process`。
- 不新增根对象，不修改状态机，不引入外部系统集成。

## 3. 涉及前端页面

- 项目中心 / 新产品线详情 / 工序明细。
- 项目中心 / 新型号线详情 / 工艺路线。
- 工艺路线新建 / 编辑弹窗。
- 工艺路线“节点配置核对表”。

## 4. 涉及后端模块

后端接口当前已返回所需字段，本次建议不改后端业务逻辑：

- `PUT /api/v1/process-routes/{processId}`

相关后端字段已存在：

不新增字段、不新增表、不新增接口。

字段语义按现状收口：

| 字段 | 中文展示建议 | 含义 | 示例 |
| --- | --- | --- | --- |
| `businessOperationCode` | 产品工序编码 | 当前产品 / 型号 / SKU 语境下的完整工序业务编码 | `NDN10101291` |

## 6. 现状代码定位

### 6.1 前端编辑区字段

文件：

- `plm-web/src/views/project/components/ProjectProcessRoutePanel.vue`

现状：

```vue
<span>产品工序编码</span>
<span>工序名称</span>
<span>工序编码</span>
```

对应输入：

```vue
<el-input v-model="operation.businessOperationCode" />

```

说明：

- 第一列实际是 `businessOperationCode`。
- 第四列实际是 `operationCraftCode`。
- 第四列表头叫“工序编码”，容易和第一列“产品工序编码”混淆。

### 6.2 节点配置核对表字段

现状 `NodeCheckRow` 只有一个 `operationCode`：

```ts
interface NodeCheckRow {
  displayOrder: number
  operationCode: string
  operationName: string
  predecessorNodeNames: string[]
  successorNodeNames: string[]
  backendPersisted: boolean
}
```

现状构建逻辑：

```ts
const operationCode = normalizeOperationCraftCode(operation.operationCraftCode)
  || operation.businessOperationCode
  || operation.operationCode
  || `OP-${operation.sequenceNo}`
```

问题：

- 核对表表头叫“工序编码”，但内容优先展示 `operationCraftCode`。
- 如果用户正在对比上方“产品工序编码”，会看到 `NDN10101291` 对 `1010`，误以为编码不一致。

## 7. 目标效果

1. 上方编辑区保留“产品工序编码”，将“工序编码”明确改为“基础工序编码”。
2. 下方“节点配置核对表”同时展示：
   - 产品工序编码：`businessOperationCode`
   - 基础工序编码：`operationCraftCode`
3. 核对表不再用一个模糊的 `operationCode` 混合展示多个字段。
4. 新建、编辑、模板带入、保存后回显保持一致。
5. 后端接口不变，前端只使用已有字段，避免不必要的 API 和数据库变更。

## 9. 前端修改方案

### 9.1 拆分 `NodeCheckRow`

文件：

`plm-web/src/views/project/components/ProjectProcessRoutePanel.vue`

建议修改：

```ts
interface NodeCheckRow {
  displayOrder: number
  businessOperationCode: string
  operationCraftCode: string
  operationName: string
  predecessorNodeNames: string[]
  successorNodeNames: string[]
  backendPersisted: boolean
}
```

### 9.2 调整已保存路线映射

现状：

```ts
operationCode: item.operationCraftCode || item.businessOperationCode || item.operationCode || item.processCode || `OP-${item.sequenceNo}`,
operationCraftCode: item.operationCraftCode || '',
businessOperationCode: item.businessOperationCode || '',
```

建议改为保持原始字段清晰传递：

```ts
operationCode: item.operationCode || item.processCode || `OP-${item.sequenceNo}`,
operationCraftCode: item.operationCraftCode || '',
businessOperationCode: item.businessOperationCode || '',
```

说明：

- `operationCode` 保留工序库 / 后端工序编码来源。
- `operationCraftCode` 单独给基础工序编码列。
- `businessOperationCode` 单独给产品工序编码列。

### 9.3 调整 `buildNodeCheckRows`

建议代码：

```ts
function buildNodeCheckRows(operations: ProcessOperationSavePayload[], persisted: boolean): NodeCheckRow[] {
  const sorted = [...operations].sort((left, right) => left.sequenceNo - right.sequenceNo)
  return sorted.map((operation, index) => {
    const operationCraftCode = normalizeOperationCraftCode(operation.operationCraftCode)
      || findOperationCraftCode(operation)
      || '--'
    const businessOperationCode = stagedBusinessOperationCode(operation)
      || operation.businessOperationCode
      || '--'
    return {
      displayOrder: index + 1,
      businessOperationCode,
      operationCraftCode,
      operationName: operation.processName,
      predecessorNodeNames: index > 0 ? [sorted[index - 1].processName || '上一道工序'] : [],
      successorNodeNames: index < sorted.length - 1 ? [sorted[index + 1].processName || '下一道工序'] : [],
      backendPersisted: persisted
    }
  })
}
```

注意：

- 新建 / 编辑弹窗里使用 `stagedBusinessOperationCode(operation)`，确保用户调整基础工序编码、材料状态、机型后，核对表能同步预览完整产品工序编码。
- 已保存路线打开编辑时，`routeForm.operations` 会经过 `refreshBusinessOperationCode`，因此核对表能继续展示刷新后的业务编码。
- 如果历史数据缺少某个字段，用 `--` 展示，不使用另一个字段冒充，避免再次混淆。

### 9.4 修改核对表列

现状：

```vue
<el-table-column prop="operationCode" label="工序编码" min-width="150" />
<el-table-column prop="operationName" label="工序名称" min-width="150" />
```

建议替换为：

```vue
<el-table-column prop="businessOperationCode" label="产品工序编码" min-width="180" />
<el-table-column prop="operationCraftCode" label="基础工序编码" min-width="140" />
<el-table-column prop="operationName" label="工序名称" min-width="160" />
```

需要同时修改两个核对表：

- 已保存路线详情下方的“节点配置核对表”。
- 新建 / 编辑弹窗底部的“节点配置核对表”。

### 9.5 修改编辑区列名和占位

现状：

```vue
<span>工序编码</span>
...
placeholder="输入工序编码，如 1010"
```

建议改为：

```vue
<span>基础工序编码</span>
...
placeholder="输入基础工序编码，如 1010"
```

可选优化：把校验提示里的“工序编码”也改成“基础工序编码”：

```ts
if (!operationCraftCode) return `顺序 ${operation.sequenceNo} 的基础工序编码不能为空`
if (!/^[A-Z0-9_-]{1,20}$/.test(operationCraftCode)) return `顺序 ${operation.sequenceNo} 的基础工序编码格式不正确`
```

## 13. 目标效果示例

修改前：

| 区域 | 展示 |
| --- | --- |
| 工序明细 | 产品工序编码：`NDN10101291`；工序编码：`1010` |
| 节点配置核对表 | 工序编码：`1010` |

修改后：

| 区域 | 展示 |
| --- | --- |
| 工序明细 | 产品工序编码：`NDN10101291`；基础工序编码：`1010` |
| 节点配置核对表 | 产品工序编码：`NDN10101291`；基础工序编码：`1010` |

用户理解：

- `NDN10101291` 是当前产品 / 型号下的业务编码。
- `1010` 是基础工序编码。
- 两者不同是正常的，但页面会明确说明，不再让用户误判为上下编码不一致。

## 14. 风险点

1. 核对表新增一列后，弹窗横向宽度可能更紧，需要确认 `operation-editor` 和 `el-table` 在 1366px 宽度下不挤压。
2. 历史数据可能缺少 `businessOperationCode` 或 `operationCraftCode`，需用 `--` 展示，不要用另一个字段兜底冒充。
3. 单测里原来断言“工序编码”的用例需要更新，否则会因为文案变化失败。
4. 不建议后端把两个字段合并；合并会破坏现有编码规则和后续 BOM / 投产确认逻辑。
