# Procurement Task1 remediation: compatibility and safety boundary

This candidate replaces the reviewed Task1 guards on `5fd416534ad2735e507414f4639407296d4fc5d2`. It does not implement batch execution, DingTalk draft creation, the Kingdee UI, an Operating adapter, or an ERPNext core repost executor. It does not deploy, merge, push, or process historical business records.

## Reused native capabilities

- The existing procurement controllers, drawer services, PO → PR → PI source locks, Integration Request kernel and managed fulfilment-review invalidation remain the owners of the flow.
- China Finance's existing company `_enabled(..., "auto_submit_purchase_invoice")` and invoice hook remain the only automatic invoice writer. No company setting is changed by application code. Caller PI ACLs are checked independently of `ignore_permissions`; enabled PI workflows requiring an automatic write are explicitly refused, not bypassed.
- Auto PI completion requires posted, correctly sourced quantities covering the native billable amount of accepted/rejected/returned quantities. Existing manual drafts are not rewritten or replaced with parallel invoices; an incomplete draft or posted result rolls back the receipt operation.
- Native status-updater source fields, PR billed-amount/FIFO helpers, native billing-percentage calculation, native payment-ledger plans and native PO advance queries verify results. The billing calculator runs on an inert document copy, including the invoice-rate landed-cost branch; its DB, valuation and repost callbacks cannot write.
- A no-update return compares locked source billed rows/parent percentages with their pre-call values. A subsequent normal PI clears that preservation policy and uses the native aggregate of submitted rows, including earlier returns.
- Accepted plus rejected `received_qty`, direct-stock PI receipt quantities, native currency/field precision and the System Settings rounding policy are retained.
- Zero-value native PI submission is legitimately non-financial only when the native GL plan and stored GL/PLE are empty and outstanding is zero. Missing PLE for a real payable still refuses submission. Manual and company-auto PI use this same proof.
- Cancellation compares the captured original GL with native original/reverse allocations under both mutable and immutable ledger settings, verifies retained original and reverse PLE/advance amounts and delinking, and checks the synchronous China Finance original/reversal/source association. Native PE plans retain the transient advance-voucher metadata absent from persisted GL. Finance headers, totals and dynamic accounting dimensions must match the real native evidence. Application code does not change immutable-ledger settings or existing posted entries.

## Native form request compatibility

The existing `purchase_payment_form.js` installs one per-form token bridge around native `frappe.ui.form.save`, with a synchronous jQuery prefilter. It only changes same-origin `frappe.desk.form.save.savedocs` and `frappe.desk.form.save.cancel` requests for PO, PR, PI and PE from the current form. Different local form identities remain distinct. External-origin URLs, background calls, unrelated doctypes/endpoints and explicit existing request IDs are not rewritten.

The same form/action/full business snapshot retains its UUID while the result is uncertain. Confirmed native `response.docs`, an explicit different action, or changed business content rotates the key. Both client and server exclude only `__onload`, `__last_sync_on` and `__unsaved` display bookkeeping. Names, local identity, modified/docstatus, flags, quantities, prices, accounts, references and taxes stay bound.

The whitelisted wrappers call the native savedocs/cancel functions directly, preserving normal native permissions, workflows, localname and return/response shape. Rolled-back attempts also restore response documents and native messages, so only the surviving attempt can reach the client. The durable request is bound to actor + request ID + normalized complete-content digest; it does not retain another raw copy of remarks, attachments or incoming flags. Nested controllers inherit the active operation.

Unkeyed programmatic calls use a distinct invocation UUID, not content deduplication. This is not cross-HTTP lost-response replay. Other controller/workflow routes keep the controller transaction boundary but are not claimed to have this native Desk transport retry guarantee.

Resource PUT/PATCH classification includes persisted old PI/PE procurement identity, so incoming cleared sources cannot escape the boundary. A submitted-to-cancelled transition binds all persisted business and child identities/facts; only cancellation state, timestamps and the configured root workflow-state field may differ. Old sources still pass existing read ACL and locks. Unrelated native documents retain their native path.

Native queued Submit is refused only when the original endpoint would actually queue: action `Submit`, `meta.queue_in_background`, and native `!is_scheduler_inactive()`. This pre-call guard also applies without a request key. Other doctypes retain native behavior; no queue, scheduler or DocType configuration is changed.

## Durable replay and authorization

Successful Integration Requests contain the primary response identity and complete affected-document artifacts, versions, action permissions and hashes of persisted document/ledger/Bin evidence. Current native read and applicable submit/cancel/write permissions are rechecked before reuse. Native updater effects on source PO/PR and payment-updated PI require read access, not permission to re-submit those source documents. New automatic PI documents also pass actual document ACL checks independently of the hook's ignore-permissions flag.

PO's actual native stock/MR item-warehouse Bin evidence is included even without PO SLE. The existing native status-updater mappings resolve and lock MR and receipt-source PI identities; their actual persisted child/parent changes and managed fulfilment invalidations are acknowledged as read-authorized source effects, without a second quantity or inventory writer.

China Accounting Posting/Cancellation vouchers and their original `reversed_by` effect are system-generated artifacts. Their integrity is rechecked internally after native business authorization, without giving the procurement actor CAV permissions, returning voucher content, or rerunning Finance synchronization. Native completed repost artifacts use the same system-effect distinction. A changed voucher, source, ledger or action permission refuses replay.

Finance's returned resolved cancellation issue and actual cash-flow assignment effects are also internal system artifacts. Voucher dates follow native `get_posting_date(source)` and CAV's calendar year/month validation, not immutable GL's cancellation date. A Posted voucher cannot already have `reversed_by`. Zero-GL cancellation that still produces a pending Finance issue fails closed; it is not reported as N/A or silently queued.

Failure file logs retain operation/actor/document/stage/before/after/amount/currency/quantity identities and fixed safe error identifiers. Unknown native exceptions retain type/category and a generic safe identifier; raw exception text and request payloads are not logged. A rollback connection error is recorded separately while preserving the original failure.

## Explicit production limitations

ERPNext's real `Repost Item Valuation.on_submit` only executes immediately in test mode. In production it leaves a queued task; its executor contains internal commits and cannot be called inside this kernel.

Accordingly, a real repost created inside the procurement operation must already be `Completed`; otherwise the entire operation rolls back with `native_stock_repost_incomplete`. An unproved `Skipped` status is also refused: native item/warehouse deduplication may assign it without a successful covering reference, including after a caught repost failure. This includes PR/stock PI cancellation and PI invoice-rate cost adjustment whenever native logic requires a repost. The error does not advise completing the rolled-back new task: that task must not survive.

Existing unfinished native reposts affecting the current stock scope also refuse the forward operation with `native_stock_repost_pending`. Transaction-based references join actual SLE voucher identities; item-based references join actual SLE item/warehouse identities, scoped by company and the current purchase/source stock pairs. Related records are locked, not processed or changed. No date-only or fictional voucher association is inferred.

Native Sales Order Item/Packed Item links, PO inter-company order headers, PR Delivery Note item/header references, PI Sales Invoice item/header references and PR-created stock reservations are detected by the existing Sales guard. Persisted old and incoming identities are checked before native writes: native PO/PI cancellation otherwise clears both procurement and opposite Sales headers, so a fresh post-cancel header alone cannot prove N/A. Receipt sources reached through PI items or PE invoice references retain current read ACL and source locks before the same Sales guard. They safely refuse an unsupported Sales dependency; managed Purchase Fulfilment Link review invalidation is retained. Real standalone nonstock DN→PR and SI→PI plus a compatible PO are not N/A. Parent-only PO/PI cancellation is verified against synthetic existing associations created with only this guard paused during fixture setup; native mapping, validation, posting and cancellation effects remain real. Existing custom Operating associations also remain fail-closed. These restrictions are not full Sales/Operating compatibility.

The guarded QA harness keeps the actual top-level `frappe.in_test=False`, so RIV creation follows the production branch. (The separate `frappe.flags.in_test` flag does not enable the immediate executor.) Synchronous non-stock PI/PE cancellation is verified separately from PR/stock PI cancellation and invoice-rate cost adjustment requiring queued reposts. The latter are explicitly refused. Native `dont_execute_stock_reposts`/`dont_run_in_test` switches also make pending-task fixtures explicit. Original PR/PO/PI/PE, SLE/Bin, GL, CAV and durable audit evidence are verified after rollback; existing pending reposts stay unchanged. No test sets `frappe.in_test=True` to turn asynchronous production work into apparent synchronous success.

## Exit conditions and remaining work

No copied business posting flow or ERPNext core patch was introduced. The transport bridge can be removed only when an equivalent native stable-request transport is available and its lost-response/new-document/cancel compatibility is verified. The repost guard is this patch's prerequisite safety restriction. Only the separately authorized narrow cancellation stages in `2026-10-08-purchase-reversal-progress-design.md`, their real scope and final acceptance may relax it; this patch does not implement that exception. Sales/Operating guards require real association adapters and native regression evidence before relaxation. A Finance reader that omits a used native accounting dimension fails this comparison; this patch does not rewrite that reader or fabricate missing evidence.

This candidate needs independent specification then quality review, integration with the owner's newer operating baseline, final integrated tests/CI and authorized production/browser acceptance. Those steps, the full Kingdee plan and production synchronous stock-repost support are not claimed complete by this remediation.
