## 用户可见行为

原生单据的“已取消”与本次业务的“冲销完成”是两个不同事实。页面并列显示单据状态和冲销处理进度：

| 处理进度 | 含义 | 相关后续业务 |
| --- | --- | --- |
| 待库存重算 | 取消已受理，原生重算尚未完成 | 禁止 |
| 重算中 | 原生任务正在处理，可能分块提交 | 禁止 |
| 校验中 | 重算结束，正在核对库存与账务 | 禁止 |
| 冲销完成 | 全部必要核对通过 | 恢复原生业务规则下的操作 |
| 失败待处理 | 原生任务失败、证据缺失或核对不一致 | 继续禁止，显示明确原因 |

取消请求成功返回时，文案为“取消已受理，库存重算未完成”，不能把 HTTP 成功、`docstatus=2`、队列已执行或一个任务 Completed 当作最终成功。列表、现有采购办理抽屉和标准表单采用同一个服务端进度来源。

重复点击、丢响应后重试或重新打开原单，返回同一操作的**当前进度**，不再次取消或重复冲销。无库存重算的取消维持现有同步完成语义。

失败显示安全的原因、操作标识和处理建议；没有权限的用户不能重试任务、修改进度或解除拦截。原生可恢复重试不计为业务完成。成功后自动刷新进度；刷新失败时不把旧缓存推断为完成。

Integration Request 是唯一冲销流程记录。原生 status 没有“重算中”，中文业务阶段保存在应用进度数据中：处理中为 Queued，失败为 Failed，只有最终完成才为 Completed。受理事实、根任务及范围不可由普通表单/API 改写。只增加必需的范围指针/索引元数据，不建立另一套业务账、库存流水或中国凭证。

## 事务与阶段

### 阶段一：原子受理

按实际来源锁定 PO、PR、PI、PE，重新检查当前取消权限、工作流和下游依赖。结合原单和请求数据读取范围，不能通过修改来源引用或仓库逃离拦截。

取消前计算并保存可证明的受影响闭包：来源单据、物料/仓库，以及原生未来重算可能沿调拨、拆装、制造等传播的凭证。闭包覆盖所有受影响的库存和账务来源；无法安全确定的路径在提交前明确拒绝，不能先取消再猜范围。保存必要版本/来源证据，限制无界查询；超过可安全核查的范围也在提交前拒绝。

相交范围的操作须采用同一持久化锁协议。优先复用现有 Bin 和来源行的事务行锁，按统一顺序取锁并验证范围不变；只读操作指针指向 Integration Request，真实库存仍由原生 Bin/SLE 管理。缺少可证明的锁对象不能降级成 Redis 或无锁检查。取消与并发业务必须串行核对，不能出现双方先检查后分别通过。

调用原生取消控制器，捕获本调用链**实际创建**的 RIV 根任务身份，包括没有 voucher 字段的 Item/Warehouse 任务。仅服务端识别的真实 Submitted→Cancelled 路径可以注册此例外。原生数量、同步账务及中国冲销检查仍执行；任一失败整笔回滚。

原生取消、同步关联写入、范围拦截、全部根任务和“待库存重算”受理记录在一个事务中提交。提交前不运行包含内部 commit 的重算执行器。排队加速通知仅在提交后发送；通知失败不丢数据库受理记录。

### 阶段二：沿用原生重算

保持 ERPNext scheduler、时间窗、并行配置与恢复机制，不修改公司配置或改写重算算法。不额外直接 enqueue 同一 `execute_reposting_entry`，避免与原生 scheduler 形成两个竞争执行路径。

应用对账任务通过持久记录观察原生进度；服务重启、Redis 丢失、通知失败后，定期扫描本功能未完成记录恢复对账。只扫描本次新受理操作，不扫描并修复历史取消。

原生重算本身可能分块提交。该阶段失败不能回滚已经提交的受理与重算分块；必须保留中间状态和拦截，不自动“取消取消”或伪造恢复成功。

### 阶段三：核对后完成

递归收集根任务和 `reposting_reference` 关联任务，核对已保存的受影响闭包。原生 GL 子任务创建可能吞掉异常，因此“现有子任务都完成”不足以证明完整；还需验证所有应重算凭证的实际结果。

原生 Skipped 也不等于完成：Item/Warehouse 去重可能没有覆盖引用，甚至由失败的前序任务触发。只有已完成任务的真实覆盖关系、最终库存和总账核对都能证明一致时才能接受替代。裸 Skipped、Cancelled、缺失任务、无法证明覆盖均保持失败待处理。

进入“校验中”后，在提交完成状态前，重新锁定范围并核对：

- 原生来源取消、收货/开票/付款状态与本次受理匹配，没有重复办理；
- SLE 数量与估值、Bin 数量/价值、原生订单来源量及仓库公司归属一致；
- 受影响凭证 GL 四列金额、会计维度和原生账务计划一致，覆盖重算传播的未来凭证；
- 适用 PLE/应付/资金余额与本次动作匹配，不因库存重算推断付款已完成；
- 中国 Posting/Cancellation 来源、原反向关联、四列金额及借贷平衡匹配。

中国财务旧 Posting 快照不会自动跟随原生未来 GL 改写。若重算造成已有快照漂移，记录失败并保留拦截，**不自动修历史账**；进一步修复属于另行授权处置。

全部通过后，还须证明与相交的在途原生 worker 隔离、任务终态稳定，防止已观察到 Completed 后，另一份预先读取的任务继续写账。缺少可证明的隔离机制不能发布或确认完成。最终证据、Integration Request Completed、业务阶段“冲销完成”和拦截解除在同一事务中提交。校验失败记录安全原因及关联 Sync Issue，保持失败待处理，不能先解锁后补校验。

## 后端、权限与审计

使用同一个范围服务检查标准表单、批量办理、REST/import，以及会直接改变相交库存的原生 Stock Entry、Delivery Note、stock Sales Invoice、Stock Reconciliation 等入口。原生 RIV 创建、`restart_reposting/bulk_restart` 及相交但不属于本操作的重算也须遵守同一范围协议，不能绕过受理与完成锁。未完成的来源 PO/PR/PI/PE 办理也被拦截。只限制真正相交的单据或物料/仓库，不冻结无关公司或业务。

原单与请求内新范围都检查。后台拦截是权威；隐藏按钮不构成安全保障。保留原生权限和工作流，不能用 `ignore_permissions`、客户端 flags 或“内部请求”参数逃过检查。

若原生后台重算确需通过范围拦截，必须基于服务端实际任务身份、已持久化闭包和原生运行环境证明可信，且只允许该任务需要的范围；不能给普通 API 或其他后台业务通用绕过开关。未证明的路径失败关闭，并由集成测试阻断发布。

进度接口按原生来源 read 权限返回必要阶段、原因、操作 ID，不开放完整审计 data/output。重试需当前原生任务办理权限，且只能续跑原任务，不再次取消源单。

每个阶段日志保留操作 ID、用户、来源/目标 ID、金额/币种、数量、状态变动、耗时和安全错误标识。成功审计与所在阶段同事务，失败结构化运行日志独立保留。敏感凭据、原始请求和不受控异常文本不得写入应用日志。

保护受理记录和未完成流程需要的 RIV 证据不被普通删除/修改或原生日志保留任务清走。完成后在 Integration Request 持久保存必要任务闭包、终态和核对摘要，不依赖临时 reposting_data_file 永久存在。

## 跨模块联动清单

| 触发动作 | 影响模块 | 单据/字段 | 状态规则 |
| --- | --- | --- | --- |
| 原子受理取消 | 采购、库存、内部 WMS、适用应付/总账/中国财务 | 原生取消与同步冲销、RIV、受理/范围元数据 | 同事务；存在未完成重算只显示待库存重算 |
| 原生后台重算 | 库存、内部 WMS、原生未来库存账务 | 原生 SLE/Bin/GL、关联 RIV | 保持处理中，未最终核对不得解锁 |
| 最终核对 | 原动作真实影响的模块 | 受理记录、最终证据、适用 Sync Issue、范围指针 | 全部一致才原子改为冲销完成并解锁 |
| 失败/重试 | 原动作真实影响的模块 | 失败阶段、原因、原生任务恢复信息 | 失败不宣告完成，不重复取消，不自动改历史账 |

销售或运营支出只按实际关联处理；未实现的关联适配保持明确拒绝，不虚构分摊或“不适用”。

## 验收与交付

在隔离数据库运行真实原生控制器，实际顶层 `frappe.in_test=False`，不能用测试标记把生产异步任务伪装成同步成功。逐项覆盖：

1. 不需要 RIV 的取消仍同事务完成；需要 RIV 的取消原子受理，不提前完成。
2. 实际根任务、跨物料/仓库传播和 GL 子任务均被覆盖；缺失子任务、失败前序导致 Skipped、覆盖不明均拒绝完成。
3. 五种业务阶段与 native Cancelled 并列；最终一致后自动完成；校验失败及原生永久失败保持拦截。
4. 标准表单/API/import/批量入口、来源改换逃逸、无权限状态读取/重试和客户端伪造 bypass 均被限制；无关范围仍可正常办理。
5. 两连接并发取消/办理、scheduler 并行、重复对账、丢响应、重启/丢 Redis/排队失败不重复取消、不丢持久进度；应用不新增重复执行队列或冲销流程。允许原生任务幂等恢复/重做分块，不承诺重算物理执行 exactly-once。验证相交 RIV 创建/重启被限制，最终核对与在途 worker 隔离，终态提交后不会被旧任务继续改账。
6. 原生可恢复错误继续原任务；不恢复为成功、不回滚已提交阶段、不擅自重写历史快照。
7. 受理事务、最终完成事务分别故障注入，验证各自整体回滚；独立失败日志留存；审计/依赖任务不被提前清理。
8. 同步 AP/付款及正常 save/submit 的严格保护未退化；真实浏览器检查列表、抽屉、标准表单及刷新/取消窗口。

每个独立行为先有失败测试再实现，规格审查通过后再进行质量审查。测试、集成 CI、构建与真实浏览器验收分别报告。原始工作簿和生产历史记录不修改。只有通过完整采购候选验收后交给既定唯一负责人串行部署 Vultr；此规格及局部安全补丁不单独冒充完整发布。

交付按既有计划报告新增/修改/删除、重复逻辑、手写业务/测试/文档行数、独立业务场景与参数化展开、兼容退出和技术债。

## 本次替代与兼容退出

新功能只替代已批准范围内“新库存取消产生 RIV 即整体拒绝”的安全限制；普通提交/改价、已有未完成历史重算、销售/运营未支持关联保持原来的失败关闭保护。

保留原生调度器、标准取消入口和无需 RIV 的同步路径，它们仍有真实调用者，不属于废弃实现。对账扫描是进度恢复能力，不是第二个库存执行器。现有 Finance 只读 `get_gl_entries(cancelled=...)` 兼容层继续按原退出条件保留。

范围锁、稳定请求桥和受理审计属于本功能安全契约；只有原生功能提供等价持久状态、权限、并发保护及丢响应保证，并完成实际调用迁移与回归后才可删除。不虚构兼容截止日期。
