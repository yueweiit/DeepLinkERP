# 部署工作流代码检出与脚本传输修复设计

## 背景

生产部署工作流的服务器升级与数据库迁移已经成功，但随后执行前端资源同步时，GitHub Runner 报错找不到 `.github/scripts/sync_and_verify_assets.sh`。原因是 `deploy` 作业没有检出仓库，却直接读取仓库内脚本。

补充验证发现，即使检出仓库，使用 `ssh ... bash -s < script` 传输脚本仍不可靠：远端脚本中的 Docker 命令可能消费标准输入，使脚本在完成部分操作后提前结束并返回成功。因此需要同时修复代码检出和脚本传输方式。

## 目标与范围

- 让 `deploy` 作业在读取仓库脚本前获得当前提交的工作区。
- 确保资源同步脚本作为完整文件执行，并且成功状态代表所有资源校验均已完成。
- 保留现有测试、SSH、服务器升级、数据库迁移、资源同步和登录页检查逻辑。
- 不修改业务代码、服务器目录、密钥配置或回退分支。

## 方案

在 `Deploy to DeepLinkERP` 作业的第一步增加 `actions/checkout@v4`。这样资源同步步骤读取的脚本与本次部署提交完全一致，也沿用测试作业已经使用的官方检出方式。

资源同步时，先通过 SCP 将脚本上传到包含 GitHub Run ID 和重试次数的远端临时路径，再通过独立 SSH 连接执行该文件，并保留脚本退出状态后删除临时文件。这样 Docker 子进程无法消费 Bash 的脚本来源，也不会在多次运行之间复用同一个临时文件。

不把资源脚本内联到工作流，避免形成两份需要同步维护的实现。

## 验证

1. 增加回归检查，验证 `deploy` 作业在引用 `.github/scripts/sync_and_verify_assets.sh` 前包含代码检出步骤。
2. 增加回归检查，禁止通过标准输入执行资源脚本，并要求 SCP 上传、远端文件执行和临时文件清理均存在。
3. 先确认回归检查能复现当前缺陷，再实施最小修复并确认检查通过。
4. 运行现有测试和 Python 编译检查。
5. 推送到实际生产构建源 `yueweiit/DeepLinkERP` 后跟踪 GitHub Actions，要求测试、升级迁移、资源同步及线上登录页检查全部成功。

## 回退

若线上效果不符合预期，使用生产仓库远端分支 `backup/overseas-costing-before-density-20260902`（提交 `3276f6f`）恢复。发布前需要确认该回退分支已同步到 `yueweiit/DeepLinkERP`。
