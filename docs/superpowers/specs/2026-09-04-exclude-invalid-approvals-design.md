# 撤销与拒绝审批排除设计

## 目标

综合成本系统不得让已经撤销、终止、取消、拒绝或驳回的钉钉审批参与批次导入、采购数据同步、成本计算或 ERP 推送，同时保留必要的审批追溯信息。

## 已确认的问题

- PostgreSQL 中 2026-01-01 至 2026-09-04 的国际物流审批共 72 条，其中 7 条状态为 `TERMINATED`，现有代码已经将它们排除，剩余 65 条有效或进行中审批。
- 同期关联采购审批中有 49 条记录为 `status=COMPLETED`、`result=refuse`。
- PostgreSQL 适配器已经把 `result` 放入审批载荷，但物流和采购摘要只读取 `status`。因此 `COMPLETED + refuse` 会被错误识别为已完成审批，并可能参与采购字段同步。
- Frappe 当前 133 个国际物流批次的主审批状态只有 `RUNNING` 和 `COMPLETED`，不存在需要物理删除的已撤销主物流批次。

## 统一审批判定

新增一个统一的审批判定入口，同时读取流程状态和审批结果：

- 流程状态属于 `TERMINATED`、`CANCELED`、`CANCELLED`、`REVOKED`、`ABORTED`，或对应中文状态时，判定为无效。
- 审批结果属于 `refuse`、`rejected`、`denied`，或对应中文拒绝、驳回、不通过时，判定为无效。
- `COMPLETED + agree` 判定为已通过。
- `RUNNING` 保持进行中；数据库中个别 `RUNNING + agree` 仍以流程状态为准，不把它提前当作已完成。
- 为兼容已有字段，摘要中的 `approval_status` 返回可直接用于业务判断的有效状态；同时保留原始 `process_status` 和 `approval_result` 供界面和审计使用。

## 主国际物流审批

- 新拉取时，无效主审批不进入匹配结果，也不创建或更新成本批次。
- 已存在的无效主审批批次不物理删除，而是从工作台列表、异常统计、成本核对和 ERP 队列中排除。
- 通过批次名称直接访问历史详情时仍可查看追溯信息，但所有确认、重新计算和 ERP 推送入口继续由现有无效审批保护逻辑阻止。

## 关联采购审批

- 无效关联采购审批不产生采购明细候选，不同步单价、币种、采购数量或货值。
- 一个合法物流批次同时关联有效和无效采购审批时，只使用有效审批，物流批次本身继续保留。
- 全部关联采购审批均无效时，物流批次继续显示，但采购资料状态为待补；不得沿用被拒绝审批作为有效采购依据。
- 钉钉审批详情保留无效审批的编号、原始状态、结果和拒绝信息，并标记为“已排除审批”，用于审计，不混入有效采购审批列表和成本来源。

## 历史数据修正

- 发布后重新读取 2026-01-01 至当天的 PostgreSQL 审批状态与结果。
- 刷新主物流批次和关联采购审批追踪状态。
- 对已经从无效采购审批写入的字段，只在来源能够明确追溯到该无效审批时撤销或以有效审批结果重建；人工录入、附件解析和无法证明来源的数据不自动清空。
- 所有历史修正记录操作日志，包含批次、审批实例、原状态、原结果、受影响字段和处理结果。

## 接口与界面

- 审批详情接口返回 `process_status`、`approval_result`、`effective_status` 和 `excluded`。
- 工作台默认不返回无效主物流审批批次，因此列表总数和异常卡片统计口径保持一致。
- 钉钉审批 Tab 将无效关联采购审批放在独立的“已排除审批”区域；不为它们提供“作为成本来源”操作。

## 测试与验收

- 覆盖 `COMPLETED + refuse`、`TERMINATED + agree`、`RUNNING + agree`、中文拒绝/撤销状态和空结果。
- 验证无效主审批不会进入拉取结果、保存结果、工作台列表或统计。
- 验证无效关联采购审批不会产生采购映射数据，混合关联时只使用有效审批。
- 验证历史修正不会清除人工或来源不明的数据。
- 重新拉取 2026-01-01 至当天，核对国际物流有效审批数量、已排除数量及关联采购排除明细。
- Vultr 仍只读 PostgreSQL/MinIO，不因排除逻辑直接调用钉钉 API。

## 安全与回退

- 不删除 PostgreSQL 审批、MinIO 附件或 Frappe 历史审计记录。
- 不修改或移除现有 SSH 公钥、私钥和服务器 `authorized_keys` 记录。
- 如新判定出现异常，可回退代码并重新显示保留的历史记录，无需恢复被删除的数据。
