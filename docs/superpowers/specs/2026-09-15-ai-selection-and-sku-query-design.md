# AI 填充确认与 SKU 查询修复设计

## 目标

修复两个生产故障：

1. 当本次所选物料并未采用某个未校验的历史合并金额组时，该组不得阻塞“确认填充”。
2. SKU 明细查询不得将仅存在于 `extra_json` 的 `package_count` 和 `packaging_type` 当作 MySQL 列查询。

## 设计

### 合并金额校验范围

- 预览仍返回全部合并金额组，用于来源审计和界面展示。
- 仅当一个未校验组与本次投影中真正采用的 `shipment_value_rmb` 变更同时匹配物料、来源 ID 和工作表时，才禁用确认。
- 仅更新重量、体积、数量等非货值字段时，历史工作表中的未校验金额组只作警告，不阻塞。
- 缺乏来源标识的旧数据采取安全策略：只有所选货值变更的物料与该组成员重合时才阻塞。
- 确认阶段继续依赖服务端保存的预览与修订指纹，客户端不能绕过。

### SKU 虚拟装箱字段

- 服务端列定义仍可包含箱数和包装类型，供前端显示。
- 生成 `frappe.get_all` 的 `fields` 时排除虚拟字段，并确保查询 `extra_json`。
- 读取后继续通过既有 `project_batch_items` / `project_source_values` 从元数据投影箱数和包装类型。
- 不新增数据库列，不修改保存格式。

## 验证

- 新增服务层回归测试，分别覆盖无关金额组、同物料但不同来源、以及真正相关的未校验组。
- SKU 分页测试要求 SQL 字段列表不含虚拟字段，但返回行仍能从 `extra_json` 得到箱数和包装类型。
- 运行受影响测试、Python 编译检查和 `git diff --check`，再推送部署。
