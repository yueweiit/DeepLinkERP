# 采购订单紧凑列表

本次只扩展品牌应用的 Purchase Order 原生 ListView：沿用 ERPNext 的筛选、权限、单据、工作流及批量操作。不修改原本地站点或线上业务数据，不修改 Frappe/ERPNext 核心文件。用户单独批准的测试订单只在独立 QA 站点生成。

## 显示与数据口径

- 默认 13px / 30px 紧凑行，表头 32px；标准密度为 14px / 40px。
- 日期、单号、供应商、状态、需求日期、公司、币种、订单金额、已预付、预付款状态、已收货%、已开票%、项目、创建人均来自现有字段。
- 已预付使用 `party_account_currency`，不是订单 `currency`；不自动换算。
- 合计使用同一筛选及权限查询，按订单币种汇总全部结果，不使用当前页数据相加，不混合币种。
- 每页 20/100/500/2500 条，默认 100 条。Excel 导出全部筛选结果及预付款币种。
- 列与密度偏好只保存到当前站点、当前用户、采购订单的浏览器本地设置；不改全局列表或物料主数据。
- 页面级样式随路由进入/退出；经典导航收窄，DL 导航结构不变；移动端取消冻结并允许表格内部横向滚动。

## 原生接口兼容

- 常规筛选用原生服务端按币种 `SUM`；明细表条件触发原生订单分组时，复用原生查询读取去重后的最小金额字段，再按订单号去重汇总，防止一张订单多条明细重复合计。该分支会读取全部匹配金额记录。
- 原生 OR 高级条件无法与另一组“订单号或供应商”条件嵌套。出现冲突时保留高级条件、清空快捷搜索并显示提示，不擅自改为更宽松的条件。
- 列表的行点击、Ctrl/Meta 选择、拖选、工作流指示器和批量操作继续调用 Frappe 原生逻辑。列设置重绘时先恢复原选择，不重新绑定业务动作。
- 原生 Excel 查询会无条件追加用于权限处理的 `owner`。本页面仍调用该原生接口，只在下载前校验并移除额外尾列，保留原生单元格类型、样式和当前所选创建人列；未选择创建人时不额外导出它。
- Excel 适配只接受已验证的原生单表 XLSX：检查 ZIP 结构、CRC、列数和尾列标题，异常时显示错误而不下载错误文件。压缩包上限 64 MiB、解压数据上限 128 MiB，不支持 ZIP64；需要支持 `DecompressionStream("deflate-raw")` 的浏览器。

## 验收边界与技术债

- 原站点没有采购订单，因此其保留真实空状态；非空验收均使用明确标识的独立 QA 数据。实际提交、付款、关闭等业务工作流不在本轮验收范围，线上真实记录仍需部署后只读检查。
- 页面适配依赖当前 Frappe ListView 的实例方法与 DOM 合约，升级 Frappe 后需重跑交互验收。
- 明细表高级筛选的合计分支读取全部匹配订单的最小金额字段，超大结果集可能较慢；每次翻页重新校验计数/合计，没有新增缓存或自定义后端。
- Excel 尾列清理依赖当前原生 XLSX 结构与浏览器解压能力，结构不符合时会显式报错；没有为旧浏览器增加第二套导出实现。
- Python 自动发现存在基线已具备的 fake-frappe 模块缓存/测试顺序耦合：`unittest discover` 为 3 个失败、3 个错误；在未改造基线同样可复现。现有文档指定顺序运行的 18 项基线测试及 2 项新增资源注册测试通过。本次未修改这些无关的测试隔离机制。
