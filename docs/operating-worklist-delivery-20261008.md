## 算法思路与复杂度

输入约 372 条运营申请，完整只读快照现为 374 条；来源有界分页。暴力逐申请扫描出纳/人员、反复分类与排序会导致 O(NC+NU) 和逐单 IO。现在一次解析来源投影、哈希关联企业+实例及姓名，分类/页数量/合计同次扫描，审批事件只排序一次；不逐单查询人员。

列表时间 O(N)，空间 O(N)；来源目标 O(N+C+U+E log E)，空间 O(N+C+U+E)，按批有界。付款余额所需保存前后快照各 O(P)，结果复用后置快照；精确关联键查找 O(1)，原生凭证行匹配沿用 O(L log L)；撤销事件后置检查 O(E)。不把写前和写后的必要两次读取当作可删除的重复计算。

## 数据一致性校验点

1. 写前重新检查权限、法律公司、来源版本、审批必审证据、冻结历史与实际余额。企业+实例精确关联，不按重复业务号猜企业。
2. 同一 Frappe RPC 内锁 Source/Takeover/Payment/Event 及原生凭证父子项。任一后置断言异常向上抛出，由原生请求事务回滚；没有异常分支 commit。
3. 写后读取持久化字段与期望请求、付款余额、币种/账户/往来方一致。只读未知提示保留，但写后不把失败降级成成功提示。
4. Event↔Journal Entry 检查源单、公司、操作、付款身份、关联键、指纹、日期及账户借贷；新建必须草稿，不能把新建伪装成历史关联。反向关联当前读避免旧快照越过新关联。
5. 撤销后检查 Event 集合完整、关联已解除、原草稿确实不存在、弃用审计的原生 docstatus=0 及身份完整；损坏或外部依赖使原付款/凭证/Event 一起回滚。
6. 记录 operation/source/document/amount/result；失败加异常类型、固定错误码和阶段，不复制敏感银行/表单/异常原文。成功为 validated，不能假称 RPC 已 committed。422 不保证生成原生 ErrorLog 快照。
7. 阿里云 SQLite 与 Vultr MariaDB 不可能共享一个本地 SQL 事务。沿用唯一 OA 身份、稳定请求身份、冻结所有权及幂等恢复；本地失败保留上游冻结，禁止自动解冻导致双付。超时/业务失败不能盲重试；已有有界死锁重试重新执行完整权限/事实检查。这不是跨库原子事务，也不是全 ERP 已全面合规的声明。
