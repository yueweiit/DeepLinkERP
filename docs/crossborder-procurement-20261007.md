> 实施顺序：来源角色 → 原生单据关联与进度 → 列表/抽屉 → 本地验收 → 串行发布。
> 部署目标：Vultr 的 `deeplinkerp.com`；阿里云仅为采购/运营审批与出纳数据来源，不承载本次 ERP 发布。

## 已确认边界

- 国内采购公司/外部供应商付款、最终使用或销售公司、集团内部供货公司是不同角色。钉钉归属子公司是最终受益公司，不自动改写外部 PO.company。
- 原料、国内模具及贸易品沿用原生 PO、SO、PI、SI、PR、PE。YW MODELS 本地模具也可关联；拉丁购拥有贸易品，Amigo 仅保管时不生成内部应付。
- 内部应付必须采用用户确认的真实内部价格与币种；关联或报价草稿不成为应付。外部供应商已付款不代表工厂内部已付款。
- 物流审批、评论、附件保留来源和作者时间。“报告到货”与原生 ERP 入库分开；预计到货、否定、数量/目的地含糊和冲突不自动确认到货。
- 不批量改历史订单公司，不自动提交、付款、入库或生成总账。只在用户明确点击后按原生权限保存草稿或执行原有业务操作。

## 复用与替代

## 算法与测试入口

每批最多 100 张订单。N 为订单数，E 为关联明细/付款引用数，C 为审批和评论文本长度。批量读取和字典索引时间 O(N + E + C)，空间 O(N + E + C)；JSON 投影另计实际字节量，不把大文本当常数。

原生草稿核查：已有 PR→PI、PO→PR、部分付款/原生预付款及重试保护，必须扩展同一入口而非复制流程。新增 PO→PI 使用 ERPNext 的 `make_purchase_invoice`（`po_detail` 为订单明细身份，`update_stock=0`），自己维护的最新数量上限一次批量读取并建立索引，时间 O(I + B)、空间 O(I + B)，I 为来源明细、B 为已提交应付明细。避免能力查询和预览重复调用昂贵映射。ERPNext 上游映射闭包本身仍有逐明细开票数量查询，保留原生税费/预付款抵扣规则，不修改核心；不能把整条原生映射误报为严格常量查询。

先订单应付、后入库的读取也复用同一链路：后续 PR 能通过原生采购订单找到先开的 PO 应付及付款记录，但仍标明整单/共享余额，不假装精确分摊到本次入库。已开应付数量必须与直接 PO 和旧 PR 路径一起核对，避免后入库时重复开同一订单的应付。

列表与导出的实现分为共用数据投影、再接现有前端两步，不改变已确认草图。默认七组列保留原生 `name`、`supplier_name` 身份（分别显示订单/审批、供应商/采购公司），其余为项目/归属、供应商付款、内部结算、收货物流及操作。原有单字段列仍可选择；只迁移旧默认列偏好，不覆盖用户自定义列序。

已有统一查询的主要重复工作是每条 OA 再查询私有来源、同一来源重复解析 JSON、循环中重查出纳字段权限，以及列表/展开/导出各自计算进度。新路径先对已有权限筛出的身份批量取受限来源投影，每条 JSON 只解析一次；三条进度复用任务 2 的请求内原生记录索引。最终公司、进度和“待核对”筛选在分页之前执行，不能在当前页前端过滤而误报总数。普通页只计算当页进度；进度筛选和导出对筛选全集计算一次并复用。P 为授权采购及 OA 数，E 为关联/付款/收货边数，J 为来源 JSON 和评论字节数，投影时间 O(P + E + J)、空间 O(P + E + J)；既有稳定排序另计 O(P log P)。原生权限与未确定值保持保守，不把隐藏关系用于筛选或计数。
