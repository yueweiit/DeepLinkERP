基线：Branding `1648ff0`；出纳集成 `911162a`。保留工作区原有文档和截图改动。

## 已批准设计

复用 `/desk/operating-expenses` 的紧凑列表和原生凭证草稿；新增简版钉钉审批流、真实原单入口、ERP 部分付款登记。新付款只由 ERP 管理，历史付款保持只读。登记实际支付，不转账、不自动提交或记账。

## 实施顺序

- [x] 来源保护：出纳按跨周稳定申请根锁住全部付款写入口，冻结可核验历史；精确鉴权的预览、接管、审批流缓存接口。
- [x] 付款核心：精确十进制校验、冻结历史加 ERP 本地付款的统一余额、幂等、申请级锁、撤销审计、私有回单。
- [x] 接入现有服务：列表/导出一致、现有费用和结算草稿复用；接管失败保持禁用，不推测零历史。
- [x] 前端：推荐紧凑列、分类/付款状态切换、原单/简版时间轴、页签化办理、部分付款表单及登记后预览。
- [x] 本地验收：纯契约/Node/原生隔离事务/跨系统 HTTP/浏览器；没有真实付款或提交凭证。
- [x] 独立规格及质量复核。
- [ ] 串行发布：先来源保护，再 Vultr ERP；备份/版本/完整业务不变审计/回退/线上只读验收。

## 共享接口约定

出纳复用 schema_version=1、source_system=cashier-payment-archive、items 数组。POST `/api/integrations/erp/operating-expenses/takeover-preview` 及 `/takeover-claim` 使用 `source_id`、`expected_version`、`request_id`；返回完整单条历史事实，claim 增加 `takeover`（owner、claim_token、claimed_at、history_fingerprint）。GET `/operating-expenses/workflow?source_id=...` 返回 source_id、lookup_status、last_synced_at、events、original_url。来源写能力默认关闭，需要显式启用，原只读 token 不应在默认配置下获得写能力。

ERP 接管状态和本地付款分别使用专用受控 DocType；来源申请、财务映射和已有事件不迁移或覆盖。列表付款合计是历史有效付款加本地有效付款；凭证草稿不参与支付合计。公司、往来方、银行和辅助核算引用遵循原生权限。

## 效率与安全边界

不用每行访问来源或逐条查凭证。批量查询/字典索引 O(N+P+E)，时间轴排序 O(E log E)。金额保存十进制字符串，不在显示四舍五入后参与财务计算；申请级锁与幂等键一起校验，幂等重试不能绕过身份或公司权限。

## 变化及保留事项

- 新增：受控接管/付款模型、精确金额契约、付款登记面板和原生付款/并发测试；不新增平行运营支出页面。
- 修改：既有列表、抽屉、费用/结算草稿服务、资源版本和受限发布元数据工具。
- 删除/替换：旧抽屉一次展示全部内容和重复付款汇总，替换为四页签及批量历史/ERP 付款覆盖；不删除业务历史或主数据。
- 重复逻辑：共用列表控制器、权限上下文、财务映射、导出和原生凭证；每条申请不重复访问来源系统。
- 技术债：历史零付款和未分类收款方必须人工核对；审批流是带同步时间的来源缓存，不冒充实时；银行实际付款由财务确认登记，不调用银行；凭证仍为原生草稿。
