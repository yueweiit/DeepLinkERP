## 1. 算法思路与复杂度

- 输入：普通页面默认 100 张订单；原生内部候选最多 100 张。全集查询 / 导出记 P 为授权采购与 OA 记录数、E 为付款 / 关联 / 收货明细数、J 为来源 JSON 与评论字节数。
- 旧瓶颈：每订单全量扫描付款与入库、逐 OA 查询私有来源、重复解析相同 JSON、循环内重查字段权限，列表与展开重复请求进度。暴力方式可产生 O(P×E) 扫描与逐条 IO；字段权限、排序及不可变表达式也会重复计算。
- 替代：批量读取受权限约束的投影，单次解析与字典 / Set 索引；请求内缓存权限、来源与明细。派生筛选在分页前执行；普通页只计算当页进度，导出与进度筛选复用全集的一次投影。
- 自有查询投影时间 O(P+E+J)、空间 O(P+E+J)；原有稳定排序另计 O(P log P)。数据库索引 / 原生权限查询成本取决于实际执行计划，不承诺所有查询都为常量时间。
- 原生 PO→PI 自有数量上限验证按来源 I 与已提交应付 B 一次索引，时间 / 空间 O(I+B)。ERPNext 映射闭包仍有逐明细查询；为保留税费、预付抵扣及原生规则，本轮不改核心文件、不将上游 N+1 误报为已消除。
- 抽屉记 L 为关联、I 为授权候选明细、E 为证据条数、B 为显示文本字节，加载 / 渲染时间与空间 O(L+I+E+B)。身份 / 版本 / 过期请求判断使用 Map、Set 与代数令牌；单次状态检查 O(1)。相同角色候选只请求一次，明确重载时清缓存。
- 原生 Link 验证期间的写入边界只扫描当前 F 个可编辑关联控件一次：时间 O(F)、额外空间 O(1)、不新增 RPC。沿用原生标题→ID 映射，验证中、输入未确认或同步未完成均不提交；验证完成后需再次明确点击，不自动重试。
